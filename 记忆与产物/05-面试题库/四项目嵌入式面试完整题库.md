## 第0章 使用方法

### 0.1 三轮复习法

1. **第一轮只看题目**：每题先闭卷说30秒，再展开答案。说不出主链路就标红。
2. **第二轮追问复述**：A级必须能回答至少两个追问；B级要能说清“为什么”；C级只需理解，不宣称亲自实现。
3. **第三轮随机模拟**：按第10章索引混抽项目题、基础题和故障题，强迫自己在不同上下文间切换。

### 0.2 状态标签

- `[源码确认]`：当前唯一源码能够直接证明。
- `[用户实测]`：用户明确完成过上板或仪器验证。
- `[已修改已编译]`：代码已改且编译通过，但不等于烧录实测。
- `[软件测试通过]`：可在主机运行的协议/逻辑测试通过，但不代表目标板或RF链路通过。
- `[已修改未验证]`：已改代码，尚缺完整编译或硬件验证。
- `[已发现未修]`：已从代码或现象确认，尚未修复。
- `[方案未实现]`/`[方案未实施]`/`[拓展未实现]`：只有设计方案，题目重要等级不代表完成程度。
- `[部分实现]`：已有部分机制，答案会逐项说明尚缺什么。
- `[团队接口]`：团队工程中存在，但不属于用户个人完成范围。
- `[拓展理解]`：用于展示工程思维，不宣称项目已经实现。
- `[待确认]`：源码、原理图或实测证据不足。

## 第2章 综合仪器（28题）

### 项目理解地图：综合仪器

#### 1. 一句话定位与输入输出

综合仪器围绕“信号采集、测量换算、波形输出和人机交互”组织多条异步链路。输入包括被测波形、DMM输入、稳压输出反馈和按键操作；输出包括LCD测量结果、屏幕曲线和AWG模拟波形。理解重点不是孤立背ADC、DMA和定时器，而是知道它们在每条链中如何连接。

#### 2. 四条必须能闭眼复原的主链

1. **示波采集链：** 模拟前端 → 比较器边沿 → EXTI3 → TIM3 TRGO → ADC1常规组 → DMA1 Channel1采1024点 → 完成回调 → 数据换算/事件位 → LCD绘图 → SPI DMA/完成信号量。
2. **DMM测量链：** TIM2 10Hz触发 → ADC1注入序列四个Rank → 注入完成中断 → VREFINT反推VDDA → 档位GPIO选择公式 → 邮箱保存最新值＋事件组通知 → LCD局部重绘。
3. **AWG输出链：** 按键/GUI修改参数 → `RestartDAC()`停止旧链 → 更新TIM5参数和波形表 → DAC DMA循环搬运 → TIM5 TRGO逐点触发DAC → PA4 → 模拟后级 → 输出端口。
4. **交互显示链：** 按键GPIO → Key任务/回调 → GUI状态变化 → 事件位置位 → LCD任务按区域绘制 → SPI DMA → 完成回调给二值信号量 → 片选释放。

#### 3. 板块衔接表

| 上游板块 | 连接方式 | 下游板块 | 真正传递的内容 |
|---|---|---|---|
| 比较器 | EXTI3边沿 | 示波采集控制 | 一帧开始时刻，不是波形幅值 |
| TIM3 | TRGO硬件触发 | ADC1常规组 | 逐点采样节拍 |
| ADC1常规组 | DMA请求 | 原始帧缓冲 | 1024个转换结果 |
| DMA完成 | ADC完成回调 | 数据处理/LCD通知 | “一帧已采满”状态 |
| TIM2 | 注入触发 | ADC1注入组 | DMM周期测量节拍 |
| DMM回调 | 邮箱＋事件组 | LCD任务 | 最新测量值＋哪个区域要刷新 |
| 按键/GUI | 参数变量＋`RestartDAC()` | AWG硬件链 | 新波形形状和频率配置 |
| SPI完成回调 | 二值信号量 | LCD发送函数 | 当前屏幕块传输已结束 |

#### 4. 容易混淆但必须连起来的关系

- 比较器只决定“从哪里开始采”，ADC常规组才测真实幅值；触发ADC与波形ADC不能混成一个概念。
- 常规组负责示波帧，注入组负责DMM周期测量；二者共享ADC1，但触发源、寄存器和软件用途不同。
- 邮箱保存最新数据，事件组保存“发生了什么”；二值信号量表达一次SPI DMA完成，它们不能互相替代。
- 波形表决定形状，TIM5决定逐点速度，DAC完成数模转换，DMA只搬运数据，模拟后级决定最终幅度、偏置和带宽表现。

#### 5. 细节锚点与题号导航

| 主链 | 必须记住的锚点 | 继续复习 |
|---|---|---|
| 示波采集 | 比较器、EXTI3、TIM3、常规组、1024点、DMA Normal | I03～I05、I22～I25 |
| DMM | TIM2 10Hz、四Rank、VREFINT、档位GPIO、邮箱＋事件组 | I06～I12、I24 |
| LCD | SPI DMA、CS/DC、完成回调、二值信号量、局部重绘 | I13～I14、D02 |
| AWG | TIM5、波形表、DAC DMA循环、500kHz上限、Restart顺序 | I15～I21 |
| 现存风险 | 三角波公式、采集显示共享缓冲、高频数字/模拟失真 | I18～I19、I25、I28 |

> 回忆失败时不要从ADC原理开始散讲：先判断问题属于四条主链中的哪一条，再从上游向下游复原连接点。

### [I03][A][示波采集][源码确认] 从输入波形到屏幕曲线的完整链路是什么？

**关键词：** 模拟前端、比较器、EXTI3、TIM3 TRGO、ADC1、DMA、1024点、事件组

**口述骨架（记顺序，不背句子）：** 先区分“比较器定起点、ADC测幅值” → 再按模拟前端、EXTI、TIM3、ADC/DMA、回调、事件组、LCD复原整链 → 最后补共享缓冲和ISR计算风险。

<details><summary>30秒版本</summary>

输入先经耦合、衰减/放大、偏置和滤波，一路进ADC1常规组，另一路进入比较器。波形越过阈值后比较器边沿触发EXTI3，回调启动1024点ADC DMA；TIM3持续提供采样TRGO，DMA满后回调换算数据并置波形重绘事件，LCD任务完成绘图。
</details>

<details><summary>完整答案</summary>

比较器只决定一帧从哪里开始，真正的波形幅值来自ADC常规组。触发回调启动`HAL_ADC_Start_DMA(...,1024)`并暂时屏蔽EXTI，避免一帧内重复启动；Auto模式同时启动10ms Hold-Off和100ms强制触发兜底。TIM3更新事件触发逐点转换，DMA1 Channel1以Normal模式写入`rawDataBuffer`。满1024点进入ADC完成回调，当前源码在ISR中把原始值换成电压写入共享`waveform`，再置事件组通知LCD。
</details>

**追问：** ①为什么比较器不能代替ADC？比较器只输出二值边沿。②强制触发作用？没有真实触发时仍周期刷新。③风险？ISR浮点循环较重且LCD可能读写同一数组。

**常见误区：** 说EXTI直接采1024点；把触发阈值ADC与波形ADC混成一个通道。

**来源/证据：** `APP/BSP/Src/waveform_capture.c`、`Core/Src/adc.c`、`Core/Src/tim.c`。

**面试贡献边界：** 模拟前端具体器件参数需以原理图为准。

### [I04][A][触发][源码确认] 比较器触发、Hold-Off和强制触发分别解决什么问题？

**关键词：** 起点稳定、抑制重复触发、Auto兜底、One-Shot

**口述骨架（记顺序，不背句子）：** 先分别给出比较器触发、Hold-Off和强制触发的一句话作用 → 再按一帧从开始、采集中到无触发兜底的时间顺序串起来 → 最后区分Auto与One-Shot。

<details><summary>30秒版本</summary>

比较器让每帧从相近阈值边沿开始，提高显示稳定性；Hold-Off在采完一帧后短暂禁止新触发，避免密集边沿重复启动；强制触发保证无有效边沿时Auto模式仍有刷新。One-Shot则捕获一帧后保持EXTI关闭，直到重新武装。
</details>

<details><summary>完整答案</summary>

EXTI回调首先启动ADC DMA，再用NVIC屏蔽对应EXTI IRQ。Auto模式启动一次性10ms Hold-Off，到期清EXTI标志和NVIC pending后重新使能；周期100ms的Force Trigger通过软件生成EXTI作为兜底。One-Shot停掉强制触发，真实触发一次后不启动Hold-Off，保持冻结。这里NVIC控制的是“中断请求是否送入内核”，并没有关闭GPIO电气输入或比较器本身。
</details>

**追问：** ①TRGO是不是ARR？不是，ARR决定计数周期，TRGO是由选定事件导出的内部触发信号。②为什么先清pending？避免旧标志导致刚使能就误进中断。③Hold-Off是否保证波形绝对稳定？不能，还受噪声、阈值和缓冲一致性影响。

**常见误区：** 把Hold-Off当采样定时器；认为禁用NVIC等于关闭EXTI线路。

**来源/证据：** `waveform_capture.c`中的EXTI、两个软件定时器及运行模式函数。

**面试贡献边界：** 可讲源码状态；触发抖动实测指标为`[待确认]`。

### [I05][A][ADC/DMA][源码确认] 为什么一帧是1024点，DMA Normal模式如何工作？

**关键词：** ADC1 DR、DMA1 Channel1、外设不自增、内存自增、CNDTR

**口述骨架（记顺序，不背句子）：** 先回答1024点是一帧容量选择 → 再讲TIM3逐点触发、DMA Normal递减到0、满帧回调 → 最后说明Normal与Circular的适用差别。

<details><summary>30秒版本</summary>

ADC1每次转换把结果写入同一个DR，DMA固定读取DR并递增SRAM地址，搬满1024个半字后CNDTR到0并停止，随后进入完成回调。Normal模式适合“触发一次采一帧”，下一帧由新的触发再次启动DMA。
</details>

<details><summary>完整答案</summary>

### [I20][B][定时器计算][源码确认] PSC、ARR为什么都要加1？

## 第3章 智慧农场（22题）

### 项目理解地图：智慧农场

#### 1. 一句话定位与系统角色

智慧农场是一个FreeRTOS环境感知与自动控制终端。它把“采集环境 → 形成统一状态 → 与安全阈值比较 → 控制执行器/产生告警 → 屏幕和BLE反馈”拆给Input、Sensor、Screen和BLE四个任务。外设只是数据入口或输出手段，`farmState`、`farmSafeRange`和任务间通信才是板块连接中心。

#### 2. 四条关键业务链

1. **采集数据链：** SensorTask周期运行 → ADC/AHT20等传感器读取 → 换算并检查有效性 → 写入`farmState` → Screen、控制和告警逻辑读取。
2. **自动控制链：** `farmState`实时值 → 与`farmSafeRange`比较 → 滞回/状态判断 → 水泵或风扇GPIO/PWM → 再由下一轮采集观察环境变化。
3. **告警通信链：** 正常/异常状态发生边沿变化 → 分配消息内存 → 队列传递`char*`所有权 → BLETask取出 → UART DMA发送 → 发送完成后释放；蜂鸣器由软件定时器组织响停节拍。
4. **人机交互链：** 按键/编码器 → InputTask消抖和编辑状态 → 修改`farmSafeRange`或页面 → ScreenTask读取共享状态 → OLED显存准备 → 获取I²C互斥锁并刷新。

#### 3. 任务与资源衔接表

| 上游 | 连接点 | 下游 | 需要特别说明 |
|---|---|---|---|
| ADC/AHT20等驱动 | SensorTask | `farmState` | 数据生产者集中，失败值不能冒充有效值 |
| `farmState` | 共享状态 | Screen/控制/告警 | 简单直接，但快照一致性仍需考虑 |
| InputTask | `farmSafeRange` | SensorTask判断 | 输入任务修改阈值，Sensor负责执行控制决策 |
| AHT20与OLED | I²C1互斥锁 | Sensor/Screen | 锁保护总线事务；优先级继承不解决长时间持锁 |
| SensorTask | 指针队列 | BLETask | Put成功才转移所有权，失败仍由Sensor释放 |
| UART DMA完成 | HAL回调/状态 | BLETask | 启动成功不等于线上发送完成，缓冲区必须保持有效 |
| 告警状态变化 | 软件定时器/队列 | 蜂鸣器/BLE | 边沿告警避免持续重复入队，滞回避免水泵临界抖动 |

#### 4. 三个系统级理解重点

- RTOS不是让四段代码同时运行，而是按优先级、Ready/Blocked状态和IPC组织执行机会。
- `farmState`解决“多模块都要读最新环境状态”，队列解决“每条告警都要按序消费”，互斥锁解决“I²C事务不能交错”，用途不同。
- 当前最重要的真实性边界是：水泵滞回和队列失败释放已有代码/验证记录；AHT20分段锁＋`osDelay`仍是未实现方案；UART DMA启动失败路径仍有缺陷。

#### 5. 细节锚点与题号导航

| 主题 | 必须记住的锚点 | 继续复习 |
|---|---|---|
| 四任务 | Input High、Sensor Normal、Screen BelowNormal5、BLE Low；阻塞点决定实际运行 | F02、F12、F15 |
| 模拟采集 | ADC1两Rank＋Circular DMA；ADC2单通道最近结果；经验百分比非标定量 | F03、F10～F11 |
| I²C/OLED | 共享总线互斥、AHT20锁内75ms问题、整帧刷新时间 | F04、F09、F17 |
| BLE所有权 | malloc → Put → Get → DMA完成 → free；失败路径只释放一次 | F06～F07、F14、F16 |
| 控制闭环 | 阈值、状态边沿、5%滞回、GPIO高不等于水泵真的转 | F08、F18、D04～D06 |

> 回答农场问题时优先判断它属于“数据、控制、告警、显示”哪条流，再说明由哪个任务生产、通过什么共享对象传递、谁最终消费。

**追问：** 回调里适合做什么？翻转GPIO或通知任务。适合I2C整帧发送吗？不适合。

**常见误区：** 把翻转频率2Hz称为完整蜂鸣周期2Hz。

**证据：** `BeepTimer.c`、`freertos.c`。

### [F14][B][UART DMA缺陷][已发现未修] 当前HAL_BUSY路径为什么会丢消息？

**关键词：** 启动返回值未检查、READY轮询、未真正发送、最终释放

**口述骨架（记顺序，不背句子）：** 先说HAL_BUSY表示本条DMA根本未启动 → 再沿当前等待READY后free的路径说明消息为何丢失 → 最后给有限重试、重排队或明确丢弃并记录的修复策略。

**答案：** BLETask无条件调用`HAL_UART_Transmit_DMA`，若返回HAL_BUSY，本条DMA根本没有启动；代码随后等待UART最终变READY并释放`msg`，所以消息未发出却被释放。正确做法是检查返回值：OK才等完成；BUSY有限重试/重新排队；ERROR恢复并记录，所有退出路径明确释放所有权。

**追问：** 这是内存泄漏吗？该路径最终释放，所以主要是消息丢失；若永远BUSY则任务卡住且队列中其他消息长期占堆。如何确认完成？回调/通知优于轮询状态。

**常见误区：** 把HAL_READY等同“这条消息发送成功”。

**证据：** `Core/App/Tasks/BLETask.c`。

### [F15][B][周期][源码确认] `osDelay(1000)`为什么不等于严格1Hz采样？

**关键词：** 相对延时、执行时间叠加、漂移

**口述骨架（记顺序，不背句子）：** 先列已知量和单位 → 围绕“相对延时 → 执行时间叠加 → 漂移”写公式并代入 → 检查边界与数量级 → 最后说明结果在项目中的实际含义。

**答案：** 每轮先采集、计算、发消息，再从调用`osDelay`时延迟1000ms，因此起始间隔为“本轮执行时间+1000ms”。长期会漂移。严格周期应基于绝对基准延时或硬件定时通知，并监测超期。

**追问：** AHT20当前75ms是否算进去？算，所以周期至少约1075ms再加其他开销。是否一定要严格1Hz？取决于控制需求。

**常见误区：** 只看延时参数就声称采样周期精确1000ms。

**证据：** `SensorTask.c`。

### [F16][B][队列][源码确认] 为什么队列长度16、元素为`char*`仍可能耗尽堆？

**关键词：** 队列只存指针、正文动态分配、生产快于消费、背压

**口述骨架（记顺序，不背句子）：** 先用一句话给核心结论 → 再围绕“队列只存指针 → 正文动态分配 → 生产快于消费 → 背压”建立因果或分工关系 → 落到项目中的具体用法 → 最后补一个不适用边界或风险。

**答案：** 队列槽只占16个指针，但每个指针背后还有约100字节动态消息。若UART消费慢、BLE卡住或多异常同时产生，已入队消息继续占heap_4；队列满后的新消息虽已修复释放，积压仍会造成瞬时堆压力。

**追问：** 如何减少动态分配？队列直接存固定结构体/固定字符数组或使用内存池。如何观察？最小剩余堆、队列深度和丢弃计数。

**常见误区：** 只按`16×4`估算全部内存。

**证据：** `freertos.c`、`SensorTask.c`。

### [F17][B][数据有效性][已发现未修] AHT20读取失败为何会显示极限值？

**关键词：** 零数组、0%RH、-50℃、返回状态、保留旧值

**口述骨架（记顺序，不背句子）：** 先给结论并定位所属主链 → 再按“零数组 → 0%RH → -50℃ → 返回状态 → 保留旧值”从上游向下游展开 → 说明关键连接点为什么这样设计 → 最后补风险、验证或贡献边界。

**答案：** 接收缓冲初始化为0，若I2C失败但仍解析，湿度原始值为0得到0%，温度原始值为0得到约-50℃，进而误报警。应同时检查HAL发送/接收返回值、Busy位、CRC/有效范围，成功才覆盖`farmState`，失败保留上次有效值并记录故障状态。

**常见误区：** 把极限值当真实环境突变。

**证据：** `aht20.c`与`SensorTask.c`。

### [S03][A][温湿度采集][源码确认] AHT20如何读取，失败为什么不能直接拿数据计算？

**标准答案**

`AHT20_Measure()`发送测量命令；发送失败就返回，不继续假定传感器已经开始转换。发送成功后当前先等75ms，再接收6字节，检查I²C返回值和Busy位；仍忙时有限次检查，不能把75ms当作任何条件下都足够的保证。

转换完成后提取20位原始湿度、温度，按`H=rawH/2^20×100%`、`T=rawT/2^20×200−50℃`换算并检查范围。成功才更新保留的温湿度，失败保留旧值且清除本轮有效标志。

若接收失败后仍计算全零数组，会得到0%和−50℃，容易被误当成环境异常。数值看似合理也不能代替通信状态检查；当前读取没有传感器CRC校验，仍可完善。

**口述思路：** 命令成功 → 等转换 → 接收成功且不忙 → 换算 → 成功更新、失败标无效。

**追问：等待转换期间总线一直忙吗？** 不是，转换在传感器内部进行；但当前裸机的`HAL_Delay()`仍让主流程忙等，不能直接照搬农场的`osDelay()`。

### [S04][B][光照与器件待机][源码＋方案对照] BH1750怎么测光，为什么要考虑单次模式？

**标准答案**

BH1750在芯片内部完成光电转换和数字测量，STM32不使用自己的ADC测它，而是通过GPIO模拟I²C读取两字节结果。当前初始化选择连续高分辨率模式，首帧先等180ms，之后读取最近完成的结果，代码按`raw×10/12`换算lux。

连续模式是传感器自行连续测量，不是每隔180ms主动向MCU发送数据；读得太快可能得到同一份结果。MCU进入Stop也不代表BH1750停止测量。

升级可采用单次测量模式，每轮触发、等待完成、读取；芯片单次测量结束后自动进入掉电模式。不能沿用“初始化一次以后直接读”的逻辑。内部掉电也不等于整个模块断电，板载器件仍可能耗电。

**口述思路：** 芯片内部转换 → I²C读数字量 → 当前连续模式 → 单次测量降低无效工作。

**追问：AHT20也应每轮断电吗？** 不必一律断电；应比较自身待机电流与重新上电、初始化的成本。BH1750单次模式仍未实施；雨滴门控已写入代码但尚未实测收益。

### [S05][A][雨滴采集与供电][源码确认＋硬件待验证] 雨滴数据如何获得，按需供电后流程有什么变化？

**标准答案**

雨滴板AO接PB1/ADC1_IN9，当前用软件启动ADC，轮询取值后停止，共读8次求平均，不用DMA。原始码按`(dry−raw)×100/(dry−wet)`映射并限幅为0～100；默认dry=4095、wet=0只是占位端点，必须用实物干湿读数标定。

当前3d751c6用PB14控制外部高边开关EN，采样链是“模块上电→等待20ms供电及AO稳定→8次采样平均→保存有效结果→停止ADC→模块断电”。PB14只驱动开关EN，不能直接给模块供电；停止ADC也不等于切断传感器电源。代码和链接产物已有，20ms是否足够、断电漏电和读数重复性仍需实物验证。

上电稳定时间应测AO或比较不同等待时间的读数，平均不能代替稳定等待。雨滴板与OLED独立控制，避免查看屏幕时雨滴板持续耗电。实际供电电压及AO范围须单独确认，不能套用OLED的3.3V条件。

**口述思路：** AO到ADC → 平均与标定 → 加入上电/稳定/断电 → 有效性和检测延迟。

**追问：断电时能读吗，能即时知道下雨吗？** ADC可能仍返回HAL_OK甚至低码，但没有真实干湿含义，低码还可能被误算为100%湿润。模块断电时也不能依靠DO即时唤醒，只能接受周期检测延迟。这里测的是板面相对湿润程度，不是毫米降雨量。

### [S06][A][UART DMA][源码确认] 为什么启动成功、DMA完成和消息送达不是一回事？

**标准答案**

`HAL_UART_Transmit_DMA()`返回HAL_OK，只证明启动被接受。DMA完成表示数据已搬到UART，最后一部分还可能在线上发送；本工程Normal发送最终经UART TC处理后进入发送完成回调，才能确认本地串口发送结束。

本地UART完成也不代表无线模块发完，更不代表网关收到。AUX提供模块状态，匹配的应用ACK才确认对端处理了本次帧。代码清除完成/错误标志后启动，等待回调或超时，超时中止发送，避免缓冲区过早失效。

当前发送帧是函数内数组。函数在发送结束或中止前不能返回，DMA期间不能改写该数组。DMA只负责搬运，当前轮询等待仍占CPU，不会自动进入低功耗。

**口述思路：** 启动被接受 → DMA搬完 → UART发完 → 模块状态 → 网关ACK。

**追问：9600、8N1发送18字节至少多久？** 每字节10位，`18×10/9600=18.75ms`；11字节ACK约11.46ms。仅是本地串口线路时间，不含无线传输和对端处理。

### [S07][A][RTC与Stop][源码确认] RTC如何唤醒，为什么唤醒后还要恢复时钟？

**标准答案**

进入Stop前，先结束本轮工作、设置未来的RTC Alarm，并处理相关标志和中断使能，再暂停SysTick并执行WFI。RTC使用保留工作的低速时钟，到达Alarm后经EXTI17和NVIC产生中断，使CPU退出Stop。

Stop保留SRAM和必要状态，但高速时钟与PLL停止。退出后不能假定原来的72MHz已经恢复，需要重新执行系统时钟配置并恢复SysTick，否则UART波特率、延时及其他依赖时钟的外设可能不符合原配置。

普通TIM和SysTick不能直接替代本工程Stop期间的RTC计时；按键EXTI是未来增加的另一种唤醒原因。唤醒只是恢复执行的机会，还要判断此次该采样、开屏还是关屏。

**口述思路：** 设置Alarm → 暂停不必要时基 → WFI/Stop → RTC中断唤醒 → 恢复时钟与业务。

**追问：调试器里看见程序停住，能证明省电吗？** 不能，要确认确实进入Stop，再脱离调试器测整板电流；外部模块也可能一直耗电。

### [S08][B][周期与报警][源码＋方案对照] 正常30秒、异常10秒，是否就是严格采样周期？

**标准答案**

当前`normal`同时检查传感读取有效和固定阈值，正常选择30秒休眠，失败或越界选择10秒。通信失败会影响状态灯，但不单独把传感正常时的30秒改为10秒。

代码先完成本轮采集、显示和通信，再设置相对休眠时间，因此两次采样间隔包含工作时间，不是严格30秒或10秒。超时重试会增加本轮活动时间，不能只按休眠秒数计算采样率。

新版增加按键查看后，应把下次采样期限单独保存，用RTC时间判断到期；查看动作不能重新从头计一个采样周期。若要严格定周期，还应约定错过期限时跳过还是补采，不能仅改一个数字。

**口述思路：** 谁决定30/10 → 工作时间也算周期 → 按键不能改变采样期限。

**追问：异常就无限快采集、一直重发吗？** 不应；更短间隔和重试都要有预算，否则故障会耗尽电量。当前整帧重试规则见S15。

### [S09][A][数据有效性][源码＋方案对照] 采集失败、环境异常和屏幕上的旧值怎样区分？

**标准答案**

采集失败表示本轮不知道真实值；环境异常表示有效值超过阈值。当前代码保留上一次成功值，另用本轮valid位标识读取结果。任一传感器失败或越界都可能使整体进入alert，但接收端可以结合valid辨别原因。

旧数值可能仍在上报帧中，不能不看valid就报警或当作实时值。OLED当前没有完善的陈旧提示；新版按键显示最近数据时，应同时显示有效性和更新时间，未成功采集过应显示“无有效数据”，而不是把初始0当测量值。

当前使用固定阈值，不启用远程修改。以后完善时可记录最后成功时间与连续失败次数，按失败类型决定保留、重试或提示；不要让错误数据覆盖有效记录。

**口述思路：** 先看是否测到 → 再看是否越界 → 旧值保留但标清 → 显示与上报口径一致。

**追问：关屏后还要保存新数据吗？** 要。数据属于采集业务，不属于屏幕；关屏只是停止显示，不能停止更新业务数据。

### [S10][A][按键显示与上下电][源码确认＋硬件待验证] OLED怎样由按键控制，而不是每次采集自动刷新？

**标准答案**

当前3d751c6将OLED默认关闭。PC13低有效按键用下降沿EXTI记录事件，ISR不做I²C；主循环约20ms消抖后维护显示状态。关闭时不发送绘图数据；打开时显示最近缓存数据，查看期间有新值再按需更新；30秒到期或关闭请求后退出显示，不影响周期采集上报。

“关闭显示”和“切断供电”不是同一件事。软关屏保留供电，停止刷新并发送CH1116 Display OFF，恢复时按对应方式开屏；硬断电还要控制电源和信号支路，重上电后重新初始化，不能假定屏幕RAM仍在。

当前关屏顺序是：停止刷新并结束I²C事务→发送0xAE→等待1ms→PB13隔离OLED信号支路→PB12关闭高边电源。开屏顺序是：PB12上电→等待10ms→PB13接通信号支路→等待1ms→重新初始化→重画数据。该顺序已写入代码，但还需测供电、I²C支路、反向灌电和整板电流。

**口述思路：** 按键决定显示状态 → 数据独立更新 → 软关屏或硬断电 → 遵守恢复顺序。

**追问：为什么有链接产物仍不能说功能已经完成？** 编译和链接只能证明语法、符号及静态连接成立，不能证明高边开关极性、供电稳定时间、I²C隔离和屏幕重新初始化在实物上正确；仍需烧录和分测点验证。


### [S11][B][共享总线与反向供电][源码确认＋硬件待验证] OLED断电为什么还要检查I²C信号？

**标准答案**

OLED与AHT20共享硬件I²C1；BH1750使用另一组GPIO模拟I²C。当前裸机顺序访问，不存在多个任务同时争用总线，不能把农场的互斥锁照搬过来作为本项目已实现的机制。

OLED断电后，共享SCL/SDA仍可能被上拉或由AHT20通信驱动。电流可能通过未供电器件的输入保护路径流入，造成反向供电、漏电或总线异常。只切VCC不一定真正省电。

当前代码用PB13控制OLED专用I²C支路隔离，公共总线及AHT20继续工作；PB12单独控制OLED高边电源。不能把整条总线拉低、断掉公共上拉，或长期把共用引脚改成模拟模式来代替支路隔离。代码存在不等于已证明没有反向供电，仍要在关屏时测OLED VCC、支路电平、整板电流，并确认AHT20通信不受影响。

**口述思路：** 共用总线仍带电 → 未供电器件可能被信号供电 → 只隔离OLED支路 → 验证电流与AHT20通信。

**追问：用GPIO直接给屏幕供电可以吗？** 不应把GPIO当负载电源；GPIO控制合适的电源开关。雨滴AO是否也需隔离，要根据模块供电、输出结构和断电漏电路径判断，不能机械套用OLED方案。

### [S12][A][按键与RTC调度][源码确认＋硬件待验证] 按键唤醒后，怎样避免打乱采样和休眠？

**标准答案**

按键EXTI中断只记录事件，主循环在恢复必要时钟后消抖、处理显示。不能在中断里完成I²C初始化、整帧绘制或长时间等待。一次按键查看默认读取缓存，不自动追加一轮采样或LoRa发送。

当前代码分别保存下一次采样期限和显示关闭期限。每次处理完事件后检查哪些期限已经到达；设置RTC Alarm时选择仍需等待的较早期限。按键只改变显示状态及其期限，不把采样时间重新向后推。不过采样期限仍按一轮工作结束时的RTC值加间隔，实际采样间隔包含活动时间，不是严格固定相位。

屏幕显示静态内容时，MCU不必一直运行；若没有传输或其他待办，可保留OLED显示并让MCU进入Stop，到显示期限再唤醒关屏。MCU是否休眠与OLED是否亮屏是两个状态，不能混为一谈。

**口述思路：** ISR记事件 → 主循环处理 → 两个独立期限 → 最近期限唤醒 → 无事再休眠。

**追问：按键与RTC同时到来怎么办？** 保留并处理两类事件，不用互斥的单一标志覆盖另一类；完成必要采集并按显示状态决定是否画屏。当前实现已采用事件和双期限，但并发到达、按键消抖、30秒超时及唤醒后时钟恢复仍需上板验证。

### [S13][A][LoRa端到端链路][源码确认] 你实现了什么，LoRa模块和PC网关分别做什么？

**标准答案**

节点先把有效数据交给协议层编码，再由通信层控制模块工作状态、调用UART DMA发送并等待ACK。物理链路是“STM32串口→节点LoRa模块→无线链路→网关LoRa模块→USB转串口→PC程序”，确认沿反方向返回。

协议层负责帧格式、字段编码、CRC与ACK解析；节点通信层负责AUX等待、M0/M1模式、UART收发和有限重试。PC网关负责串口组帧、校验、解析、重复帧处理、记录和回复ACK。

无线调制解调由LoRa模块完成，我没有在STM32上编写射频基带算法，也不是直接驱动裸射频芯片寄存器。此项目是模块通信加自定义应用协议，不能称为已经实现LoRaWAN。

**口述思路：** 一条上行和反向ACK链 → 协议层 → 节点通信层 → 网关 → 明确模块承担的工作。

**追问：无线参数配好就算软件通信可靠了吗？** 不算，还要处理数据边界、校验、身份和序号匹配、超时及重复消息；无线实物链路也仍需单独验证。

### [S14][B][数据帧与CRC][源码确认] 为什么不用直接发送结构体，18字节帧包含什么？

**标准答案**

遥测帧固定18字节：帧头2、版本1、类型1、节点ID2、序号2、标志1、温度2、湿度2、光照2、雨滴1、CRC2。标志包含数据有效性与报警信息；温湿度用定点数传输，例如温度按0.1℃表示。

代码逐字段按约定字节序编码，不直接发送C结构体。这样可避开结构体填充、平台字节序和浮点表示差异，也便于Python端按同一规则解析。温度还要保留符号，不能当作无符号数解释。

CRC覆盖前16字节，代码使用初值0xFFFF和多项式0x1021。接收端先检查长度、帧头、版本、类型和CRC，再解释业务字段。CRC验证传输数据是否符合校验规则，不代表传感器测量正确，也不提供加密或身份认证。

**口述思路：** 固定字段与长度 → 明确字节序和单位 → CRC检查 → valid决定数据能否使用。

**追问：面试是否要背每个字节偏移？** 先讲清帧头、身份、序号、数据和CRC各自用途；详细偏移能根据协议定位即可。

### [S15][A][ACK与有限重试][源码确认] 如何判断本次上报成功，重试如何避免失控？

**标准答案**

本地UART发送结束后，节点等待固定11字节ACK。解码通过后，还要匹配节点ID、本次序号及成功状态，不能收到任何字节就判成功。若ACK丢失，即使网关已收到数据，节点也可能认为本次未成功。

当前主循环配置最多重试1次，即整帧最多发送2轮。通信函数内HAL_BUSY时最多尝试启动3次，是本地UART启动层的处理，不是3次完整无线重发；两类计数不能混淆。

整帧重试沿用本次序号，网关可以识别重复。处理完本次上报后推进序号并尝试让模块休眠。失败需要记录并结束本轮，不能无限等待ACK；当前最后的模块休眠返回值被忽略，还需补充失败处理。

**口述思路：** CRC与身份序号匹配 → 有限等待 → 同序号有限重试 → 收尾并记录结果。

**追问：当前ACK接收足够健壮吗？** 尚不充分。节点用固定长度阻塞接收，没有网关那样的流式重同步；噪声、错位或残留数据可能使本轮校验失败，应作为后续改进而非已解决功能。

### [S16][B][模块控制引脚][源码＋方案对照] M0、M1、AUX分别起什么作用？

**标准答案**

本工程参考DX-LR22模块及其AT+SWITCH=1控制方式：M0/M1组合选择模式，当前约定00工作、11休眠；AUX按项目配置解释为高忙、低空闲。不同模块或配置可能不同，不能推广成所有LoRa模块统一规则。

软件切换模式后短暂等待，并用AUX检查模块是否结束忙状态；UART发完但模块仍忙时，不能直接认为无线处理已经结束。AUX等待要有超时，超时不能当作成功。

当前源码控制脚是PA8、PA9、PA1；新版硬件规划是PA0、PA1、PB8，尚未落入初始化。代码中还存在固定GPIOA的初始化写法，若只改引脚宏，跨端口的AUX可能配置错误。

**口述思路：** 模式选择 → 模块忙闲 → 有限等待 → 以具体模块和实际初始化为准。

**追问：这些脚号要放进项目介绍吗？** 不需要；追问硬件联调时再讲，并区分当前代码与新版接线方案。

### [S17][B][PC网关][源码确认] 网关怎样处理串口分包、重复帧和记录？

**标准答案**

串口一次读取可能只得到半帧，也可能包含多帧。PC网关维护接收缓冲，寻找帧头、等待完整18字节并校验，遇到错误数据重新同步；不能把一次read等同于一条完整消息。

网关按节点ID和序号识别重复，重复帧不应重复作为新数据记录，但仍需回复ACK，否则节点会继续重试。解析后的数据可输出并记录到CSV；接收时间是网关观察到的时间，不应冒称传感器精确采样时间。

当前重复记录缓存在进程内，重启后不保留。已有主机协议测试不能证明射频距离、抗干扰和双模块收发成功，也不能证明节点固定长度ACK接收具有同样的流式能力。

**口述思路：** 字节流拼帧 → 校验解析 → 重复判定并确认 → 记录与边界。

**追问：ACK丢了，第二次数据到达怎么办？** 识别为同一条，避免重复入库并再次回复ACK；这正是序号和去重配合的意义。

### [S18][B][低功耗验证][源码＋方案对照] 怎样证明省电，而不只是“调用过Stop”？

**标准答案**

测整板一个完整周期的电流，分清采集、屏幕、无线发送及等待、休眠等阶段。平均电流按各段电流乘持续时间后求和，再除以完整周期；不能只报MCU休眠瞬间的最低值。

新版应比较OLED关闭与开启、雨滴常供电与采样供电、BH1750连续与单次模式，并检查LoRa是否真正进入休眠。还要考虑稳压器静态电流、指示灯、模块待机和信号反向供电，不能只优化CPU。

测试应覆盖正常周期、异常短间隔、ACK丢失重试及传感器失败。先脱离调试器建立基线，再逐项改动对比；测量电源和串入仪表不能使供电不稳，否则结果没有可比性。

**口述思路：** 测整板完整周期 → 分阶段 → 检查外设 → 覆盖失败场景 → 用实测评价收益。

**追问：关得越彻底越好吗？** 不一定。频繁上电有初始化时间和能量成本，还可能增加首次测量延迟；要比较平均功耗与响应速度，未实测不能编造续航或微安数值。

### [S19][B][故障定位][源码＋方案对照] 不休眠、收不到ACK或屏幕不亮，怎样分层排查？

**标准答案**

先确认是哪一段停住，再选择证据，不把所有现象都归结为硬件。常见问题可沿以下路径检查：

| 现象 | 优先检查的链路 |
|---|---|
| 没进入Stop | 主循环是否走到睡眠入口；OLED的无限等待I²C、UART/AUX/ACK等待是否卡住；不能先断言RTC坏了。 |
| 已进入Stop但不唤醒 | RTC是否计时、Alarm是否在未来、相关标志与EXTI17/NVIC是否配置；唤醒后再检查时钟恢复。 |
| 网关无数据或节点无ACK | 先分正向和反向：UART返回值/TC→AUX与模块模式→无线配置→PC收到的字节和CRC→ACK生成、返回及节点身份序号匹配。 |
| 新版关屏或开屏异常 | 默认关屏但数据仍上报是正常设计；确有查看请求却不亮，再查事件、供电/隔离、初始化和I²C，不因采集完成就要求自动亮屏。 |

当前OLED发送仍使用HAL_MAX_DELAY且可能忽略返回值，可能让循环根本走不到休眠；模块初始化及收尾返回值也要检查。按键、PB12/PB13供电隔离和PB14雨滴门控已经进入代码，但未上板，因此排查时必须先验证真实引脚极性、供电和时序，不能凭链接成功假定硬件链正常。

**口述思路：** 明确预期行为 → 找最后一个成功环节 → 观察返回值、状态与引脚 → 缩小边界 → 验证修复。

**追问：雨滴断电后显示100%，是下雨了吗？** 不一定。先查模块是否供电、AO是否稳定及软件是否允许这时采样；ADC读成功不证明传感器有有效输出。

### [S20][A][个人贡献与完成状态][源码＋验证边界] 最值得讲的亮点和仍需完善的地方是什么？

**口述思路：** 一个闭环亮点 → 自己具体做了什么 → 已有证据 → 尚未完成 → 下一步如何验收。

**追问：是否必须说“全部独立原创、已经量产”？** 不需要，也不真实。讲清自己设计和集成的部分、使用的库及证据边界，比堆功能名更经得起追问。

4. **慢速交互链：** 主循环/按键 → 页面或调试参数变化 → OLED缓存绘制 → 屏幕显示模式、传感器位图和参数；它服务于调试，不应塞进1ms中断。

### [C04][A][误差映射][源码确认] 五路状态怎样映射成位置误差？

**关键词：** 00100=0、01100=+2.3、00110=-2.3、01000=+7、00010=-7、10000=+20、00001=-20

**口述骨架（记顺序，不背句子）：** 先用居中状态建立0误差基准 → 再按线落在左/右侧说明误差正负和幅值增大 → 最后补位序验证以及特殊状态不能硬套普通误差。

<details><summary>30秒版本</summary>

中央00100映射0；相邻偏差01100/00110映射约+2.3/-2.3；再外侧01000/00010映射+7/-7；最外侧10000/00001映射+20/-20。误差绝对值越大，差速修正越强。
</details>

<details><summary>完整答案</summary>

这些数值不是几何毫米，而是离散控制权重，正负方向取决于传感器位序和左右轮公式。连续变化的权重给PID一个近似位置量，比只用左/中/右三态更平滑；但图样缺失、交叉线和急弯不能强行当普通误差，需要先分类状态再决定是否调用PID。
</details>

**追问：** ①+7时怎么修？按当前`left=base-correction,right=base+correction`，使车向对应方向回线，最终方向需以轮/误差符号实测确认。②数值怎么调？低速标定、记录图样和轨迹，逐步增大分离度。③多点同时压线？按映射或转弯状态处理。

### [C07][A][1ms定时][源码确认] MSPM0的1ms控制节拍怎样算？

**关键词：** 80MHz、/8、/(255+1)、LOAD=38、LOAD+1、0.9984ms

**口述骨架（记顺序，不背句子）：** 先写80MHz经分频后的计数频率 → 再用LOAD+1得到约1ms周期 → 接着说明中断里触发哪些最小工作 → 最后检查单位和ISR预算。

<details><summary>30秒版本</summary>

定时器输入80MHz，先除8，再除`255+1`得到39062.5Hz；LOAD=38代表计数39拍，所以周期`39/39062.5≈0.9984ms`，接近1ms。LOAD也要加1，因为计数从0开始。
</details>

<details><summary>完整答案</summary>

通用公式是`T=(divider×(prescaler+1)×(LOAD+1))/Fclk`。此中断每1ms左右读取五路状态并运行相关控制；每10个中断还可能执行AHRS和电机测量等团队逻辑。因此不能只看平均周期，还要保证所有ISR路径最坏执行时间显著小于约1ms，否则会累积延迟或丢中断。
</details>

**追问：** ①LOAD写39会怎样？40拍，约1.024ms。②为何不是直接80MHz/38？遗漏两级分频与+1。③如何实测？ISR入口/出口翻转GPIO并用逻辑分析仪量周期和脉宽。

**常见误区：** 把RTOS Tick概念套到裸机定时器；说38就是38拍。

**来源/证据：** `ti_msp_dl_config.c`及定时器IRQ。

**面试贡献边界：** 中断周期可源码计算，最坏执行时间尚未量化。

**追问：** ①裸机能异步DMA吗？能，DMA/中断与RTOS无关。②RTOS保证实时吗？需正确优先级、短ISR和时序分析。③超级循环缺点？长函数会阻塞后续步骤。

**常见误区：** 把裸机等同“没有中断”；把RTOS等同多核并行。

**来源/证据：** 四项目主入口和调度结构。

**面试贡献边界：** 架构选择依据可讲，未做跨架构重写。

### [X02][A][DMA比较][源码确认] 四个项目里的DMA分别解决什么问题？

**关键词：** ADC采帧、DAC循环、SPI LCD、UART TX、搬运非计算

**口述骨架（记顺序，不背句子）：** 先说DMA只解决搬运 → 再按综合仪器ADC/DAC/SPI、农场ADC/UART、节点UART、小车GPIO逐项比较 → 最后说明Normal/Circular和缓冲生命周期。

<details><summary>30秒版本</summary>

综合仪器用ADC DMA收1024点、DAC DMA循环输出波形、SPI DMA刷屏；农场用UART DMA发BLE，节点用UART TX DMA向LoRa模块送帧、阻塞接收ACK，农场ADC1还用Circular DMA交织两通道；小车核心五路GPIO不需DMA。DMA减少CPU逐项搬运，但触发、完成同步和缓冲生命周期仍由软件管理。
</details>

<details><summary>完整答案</summary>

DMA是否合适取决于数据量和节拍。示波帧与屏幕/波形表属于大块或高频搬运，收益明显；UART低波特率下DMA减少逐字节搬运而不缩短线速；节点发送完成等待仍为轮询，DMA不会自动让CPU休眠；五路GPIO每1ms只读少量位，使用DMA反而复杂。Normal用于边界清晰的一帧，Circular用于持续最新数据或周期输出；两者都要避免生产者覆盖消费者正在使用的缓冲。
</details>

**追问：** ①DMA完成是否等于外设物理完成？视外设而定，UART还需TC语义，HAL回调负责抽象。②DMA会计算ADC电压吗？不会。③如何诊断？返回值、寄存器/CNDTR、中断、目标内存、线上信号。

**常见误区：** 说DMA让传输速度无限提高；所有小数据都上DMA。

**来源/证据：** 四项目DMA配置与回调。

**面试贡献边界：** 小车团队其他DMA用途不归个人贡献。

### [X03][A][ADC比较][源码确认] 综合仪器、农场和节点的ADC设计目标有何不同？

### [D01][A][示波故障][源码确认] 示波界面菜单正常，但一直没有波形，怎么查？

### [R01][B][Tick][源码确认] 100Hz Tick是时间片流转频率吗？

**关键词：** 系统节拍10ms、调度时基、时间片边界、不是唯一切换原因

**口述骨架（记顺序，不背句子）：** 先给100Hz=每Tick 10ms的结论 → 再说明它服务延时、超时和同优先级时间片 → 接着列高优先级唤醒/任务阻塞可立即切换 → 最后区分CPU主频。

**答案：** 100Hz表示内核每秒产生100个Tick，即1 Tick=10ms，用于延时、超时和同优先级时间片计数。任务切换不只发生在Tick：高优先级任务被ISR唤醒、当前任务阻塞/让出时都可立即切换。因此不能把100Hz简单等同“所有任务每10ms轮一次”。

项目经历可以进一步说明：综合仪器不是只调用现成RTOS API，用户还完成了FreeRTOS移植和`FreeRTOSConfig.h`项目配置。当前源码配置72MHz CPU、100Hz Tick、抢占和同优先级时间片，heap_4为7000字节，并启用事件组、互斥锁、计数信号量和栈溢出检查。表述应为“完成过项目级移植与配置”，不夸大为“精通内核移植”。

**追问：** 主频72MHz如何生成Tick？SysTick按内核时钟分频并周期重装，具体LOAD约由配置计算，不是计到71999999。高优先级就绪要等时间片吗？抢占开启时不等。

**常见误区：** 把CPU主频、定时器采样率和RTOS Tick混用。

**证据：** 综合仪器FreeRTOSConfig 100Hz与调度配置。

### [R06][C][拓展理解，不宣称个人实现] 为什么ISR不能获取互斥锁？

**项目关联：** 农场动态消息关注堆，任务局部变量/调用深度关注各自栈。

**边界：** `[拓展理解]`，当前监控覆盖度待核对。

### [R08][C][拓展理解，不宣称个人实现] 软件定时器回调为什么必须短小？

**关键词：** 共享Timer Service Task、串行回调、不可阻塞、通知任务

**口述骨架（记顺序，不背句子）：** 先定义核心概念 → 再围绕“共享Timer Service Task → 串行回调 → 不可阻塞 → 通知任务”说明任务状态、时序或调度结果 → 落到当前项目举例 → 最后纠正一个常见误区。

**答案：** 多个软件定时器的命令与回调由同一服务任务串行处理，一个回调阻塞会推迟其他定时器。回调只做GPIO、小状态更新或通知任务，长I/O放到普通任务。

**项目关联：** 农场蜂鸣器500ms回调适合翻转引脚；综合仪器Hold-Off回调只清标志/使能IRQ。

**边界：** 通用设计原则。
