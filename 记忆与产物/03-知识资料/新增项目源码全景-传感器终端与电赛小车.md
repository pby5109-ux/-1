## 2. 传感器终端（用户独立项目）

### 2.1 项目定位与结构

这是一个以低功耗周期采集为主的环境监测终端：采集温度、湿度和光照，显示在OLED，依据阈值点亮状态灯，通过BLE串口透传状态文本，然后进入Stop模式，5秒后由RTC闹钟唤醒继续下一轮。

- MCU：STM32F103C8T6，HSE 8MHz经PLL×9得到72MHz；RTC由32.768kHz LSE供时。
- 软件：STM32CubeMX/HAL生成工程，裸机超级循环，无FreeRTOS。
- 目录：`Core`保存Cube生成初始化、中断和主流程；`BSP`保存AHT20、BH1750软件I²C、OLED与字体驱动。
- 共享总线：AHT20与CH1116 OLED顺序使用I2C1；由于没有并发任务或中断访问，不需要RTOS互斥锁。

### 2.2 外设和引脚

| 功能 | 外设/引脚 | 关键参数 |
|---|---|---|
| AHT20 | I2C1：PB6 SCL、PB7 SDA | 400kHz；HAL地址0x70，对应7bit地址0x38 |
| CH1116 OLED | 同一I2C1 | HAL地址0x7A；128×64，`OLED_GRAM[8][128]` |
| BH1750/GY-30 | PA11 SCL、PA10 SDA，GPIO模拟I²C | 写地址0x46；连续高分辨率命令0x10；原始值÷1.2得到lx |
| 雨滴模拟量 | PB1 / ADC1_IN9 | ADC时钟12MHz；软件触发；239.5周期；每轮8次平均 |
| BLE串口 | USART3：PB10 TX、PB11 RX | 9600、8N1；TX DMA1 Channel2，RX DMA1 Channel3，Normal |
| 状态灯 | PA7绿色、PB0红色 | PA6蓝色存在于原理图但当前应用未使用 |
| 低功耗唤醒 | RTC Alarm / EXTI17 | 每轮Stop 5秒后唤醒 |

### 2.3 一轮数据流

1. 上电或RTC唤醒后直接进入传感器采集；当前不再启动USART3 RX DMA或开放300ms命令窗口。
2. `AHT20_Measure()`发送`AC 33 00`，等待75ms，检查I²C返回值和Busy，必要时有限重读；仅在20bit换算值通过量程检查后更新温湿度。
3. BH1750初始化阶段只发送一次连续高分辨率命令0x10并等待180ms，循环中`Light_Read()`只读取最新2字节并按`raw/1.2`换算。GY-30上的BH1750芯片内部已经集成PD光电二极管、积分运放、16bit ADC、内部振荡器和Logic/I2C数据寄存器，不使用STM32 ADC；高分辨率转换120ms典型、180ms最大，连续模式每次转换完成只更新内部数据寄存器，不会主动把数据推给MCU。MCU读得更快会重复读到同一最新值，读得更慢则只得到最近一次完成结果，中间结果不排队。
4. `Rain_Read()`软件触发ADC1_IN9，取8次平均并按干湿标定点映射为0～100%；默认4095/0只是待替换的占位值。
5. 清空OLED帧缓冲，绘制温度、湿度、光照和降雨四行；全部采集成功且处于固定阈值内才发送`normal`并亮绿灯，否则发送`warning`并亮红灯。
6. UART TX DMA启动后检查HAL返回值，并等待本次完成回调；BUSY有限重试，错误或500ms超时则中止，避免永久忙等。
7. 设置RTC绝对计数闹钟并进入Stop；5秒后恢复系统时钟和SysTick，再进入下一轮。当前应用没有串口接收流程。

#### 历史实现：已停用的蓝牙GET/SET远程阈值链

> 2026-08-25最终决定：下述链路曾编译、烧录和上板验证，但已从当前构建与主循环停用。保留内容仅用于理解历史方案，不应在当前项目介绍中称为现行功能。

- USART3以9600 8N1和RX DMA1 Channel3运行，`HAL_UARTEx_ReceiveToIdle_DMA()`接收不定长文本；串口出现Idle空闲间隔后，HAL用`HAL_UARTEx_RxEventCallback(huart,size)`报告本帧实际长度。
- ISR回调把DMA缓冲复制到单槽`pending_command`并置`pending_command_ready`，随后立即重启RX-to-IDLE DMA。若上一条pending尚未被主循环取走，新帧不覆盖旧帧而是被丢弃；这不是多消息队列。
- 主循环唤醒后的300ms窗口每1ms调用`RemoteConfig_TakeCommand()`；取命令时短暂关中断，原子地复制文本并清ready，随后在普通主循环上下文解析，避免在ISR中执行`strtol/snprintf`等重逻辑。
- `GET`返回当前温度、湿度、光照和降雨阈值。`SET,tmin,tmax,hmin,hmax,lmin,rmax`解析6个整数，要求温度落在-40～85℃且min<max、湿度0～100%且min<max、光照下限0～65535lx、降雨上限0～100%；全部合法才一次性提交到`thresholds`，失败回复ERR且不部分修改，成功回复ACK。
- 窗口内先处理的SET会立刻影响本轮后续阈值判断；采集/显示期间到达的命令可在入睡前最后一次处理，但刚完成的那次normal/warning已经使用旧阈值，新阈值从下一轮判断起生效。
- 阈值保存在SRAM：普通Stop后仍保留，复位/断电后恢复`SENSOR_THRESHOLDS_DEFAULT`。Stop前主动Abort RX，故Stop期间命令不会缓存；300ms窗口长度是交互成功率与活动功耗的直接取舍。

##### 数据分别存在哪里

| 阶段 | 数据载体 | 生命周期/所有权 |
|---|---|---|
| DMA正在接收 | 静态`uart_rx_dma_buffer[96]` | 模块私有SRAM；每次启动接收前清零，DMA最多写95字节 |
| 等主循环处理 | 静态`pending_command[96]`＋length/ready | 单槽邮箱；ISR发布，主循环消费，未消费时下一帧丢弃 |
| 本次解析 | `Process_Remote_Command()`栈上的`command[96]`与`response[128]` | 仅本次函数调用有效 |
| 六个解析值与候选配置 | `values[6]`和局部`proposed` | 栈上临时数据；全部校验通过前不改正式阈值 |
| 当前正式阈值 | `main.c`静态`thresholds` | SRAM运行时状态；Stop保留，复位/掉电由启动代码恢复默认值 |
| 回复/周期状态文本 | 栈上`response`或全局`uart_buf` | TX DMA使用期间必须保持有效；当前发送函数等待完成/失败/超时后才返回 |

##### 命令到达时刻与生效轮次

- 在每轮开头300ms窗口到达并处理：先更新`thresholds`，随后采样得到的数据使用新阈值判断，本轮立即生效。
- 在采集、OLED绘制或状态TX期间到达：RX中断可先把完整帧放进pending；睡前`Process_Remote_Command()`再处理，但本轮`normal/warning`已经算完，所以从下一轮判断生效。
- 在Stop期间发送：RX DMA已经Abort，通常丢失；RTC唤醒并恢复时钟后才重新启动接收。若一条完整命令恰好已在Stop前发布到pending但还未消费，pending属于SRAM，唤醒后的窗口仍可消费；只收到半帧而被Abort则不能形成有效命令。

### 2.6 LoRa软件变体（提交`d46bd46`）

为使低功耗深化具备源码支撑，工程新增独立`LoRaDebug`构建，默认`Debug`仍保留BLE路径。新增事实如下：

- `lora_protocol.c/.h`：18字节遥测帧、11字节ACK、CRC16-CCITT、大端字节序、NodeID/Sequence/valid/alarm。
- `lora_node.c/.h`：PA8 M0、PA9 M1、PA1 AUX参考控制；USART3 TX DMA完成、AUX低完成、ACK匹配、300ms超时、最多一次重试；正常30秒、异常10秒。
- `tools/lora_gateway.py`：PC侧离线协议解析、CRC拒绝和ACK生成；当前只接受固定帧/命令行`--hex`输入，没有打开真实串口、持续接收第二块LoRa模块或把ACK写回串口，不能称完整在线RF网关。
- 在线网关的最小硬件是第二块LoRa模块＋USB转TTL＋PC，不强制增加网关MCU。Python应以字节流缓存搜索`A5 5A`、凑满18B、校验CRC、按NodeID/Seq去重并生成11B ACK后写回串口；普通串口助手只适合观察或手工固定帧验证，除非支持脚本，否则不能可靠动态回复ACK。
- 实物验证应以节点UART TX/RX、M0/M1和AUX逻辑分析仪时间轴配合PC日志；300ms是未实测初值。默认2148bps下29B上下行净荷载位时间约108ms且尚有空中协议/切换开销；336bps时净荷载已约690ms，因此超时必须随速率实测调整。
- 距离/RSSI/丢包测试必须固定信道、速率、功率、天线与环境，用Sequence统计首发成功、重试成功和最终失败。手册`AT+DRSSI1`可在接收包末附加RSSI字节，换算为`-(0xFF-rssiByte)`dBm；该功能会改变接收帧长度，节点/PC解析器需同步适配后才能启用。
- 验证：2项Python测试通过；LoRaDebug Flash 45832B/RAM 4040B，默认Debug Flash 43584B/RAM 4112B，均编译通过。

当前没有购买LoRa模块，所以准确口径是“LoRa节点软件和网关协议已实现、测试并编译；RF收发未上板”。`AT+SWITCH=1`、AUX真实时序、实际距离、RSSI、丢包和功耗仍待硬件验证。该边界不能因为源码存在而取消。

## 3. 电赛小车（团队工程）

### 3.1 系统上下文

### 3.2 用户贡献边界

用户明确只参与两块：

1. **屏幕和按键绘制/交互**：`Hardware/key.c/.h`、`User/main.c`中的`keyloc()`与`OLED_Show_Proc()`是直接相关实现。四键用于切换六个有效页面、选择题目/模式、修改圈数和启动/停止；页面显示主状态、姿态角、灰度、左右轮数据、串口坐标及右轮PID参数。
2. **五路循迹**：`Hardware/gw_gray.c/.h`及`datafun()`中的调用链。五个GPIO被拼成5bit状态，映射为偏差或左右转标志，再接入已有位置PID与电机接口形成差速控制。

OLED底层软件I²C/字库、PID、电机PWM、编码器、MPU6050、UART视觉坐标与舵机等默认只作为用户参与工程时需要理解的接口，不归为个人实现。`datafun()`中状态机究竟由谁编写，源码无法单靠时间和文件名证明；后续陈述以用户给出的边界为准，不扩大归属。

### 3.3 五路循迹真实链路

| 从左到右 | GPIO | 拼位 |
|---|---|---|
| IN1 | PB24 | bit4 |
| IN2 | PB20 | bit3 |
| IN3 | PA27 | bit2 |
| IN4 | PB19 | bit1 |
| IN5 | PB18 | bit0 |

主要映射：00100→0，01100→+2.3，00110→−2.3，01000→+7，10000→+20，00010→−7，00001→−20；11000/11100置左转标志，00111/00011置右转标志。`datafun()`在1ms定时器中调用`Track_err()`和位置PID，用`left=set_speed-pid_out`、`right=set_speed+pid_out`形成差速；达到路程或转弯图样后，结合MPU6050 Yaw完成约±70°转向再回到循迹。

目录里还有一套地址0x5D的UART `LineFollow`模块，可读取状态、模拟量和阈值，但当前主程序没有引用，Keil项目也未包含该C文件。实际比赛主线是`gw_gray`的五路GPIO方案，二者不能混为一套实现。

### 3.4 屏幕、按键与节拍

- `KEY_Scan()`低电平判定四键。按住期间只返回一次；松开后连续5次扫描才允许下一次触发。它没有固定时间延时，因此更准确地称为释放门控/扫描计数，不是严格的“5ms消抖”。
- `keyloc()`：KEY1切换`UI_shift`的0～5页；KEY2切换`flag_ti`的0～5模式；KEY3在模式1增加圈数；KEY4在UI页1切换启动并复位步骤，或在模式1减少圈数。
- 主循环只做按键扫描和OLED整页更新；控制逻辑放在1ms TIMER_0中断的`datafun()`中。每10个中断更新姿态/测速，实际是10ms，源码旁“100ms”注释错误；每100ms和1s翻转LED。

### 3.5 已确认状态与风险

- 实际生成配置位于`MCU_Drivers/ti_msp_dl_config.*`：四键、五路灰度、UART0 115200、CPU 80MHz等与当前代码匹配。`Keil/M0_G3507.syscfg`只有三键且部分PWM参数不同，是冲突/旧副本，不能作为当前引脚事实。
- 旧Keil构建日志显示0错误0警告，但`main.c`在构建后27分钟又修改；当前文件级状态尚未重新编译。
- `Track_err()`的四个转弯case没有给局部变量`error`赋值便返回，属于未定义值；应在后续允许修改时给出确定的当前偏差/保持策略。
- `error_flag`只按`error==0`设置，导致居中00100和丢线00000都被视为同一状态，与“未寻道标志”注释不一致。
- `N`为无符号8位且减少时无下限保护，可能从0下溢到255。
- 1ms ISR直接执行状态机，部分模式还会调用UART解析、`sscanf`和浮点PID，最坏执行时间和中断实时性尚无测量证据。
- OLED灰度页标签显示`e_hd`/`hd_pid`，实际传入的是`servo_x`/`servo_y`，究竟是临时调试还是变量接错需要用户/实测确认。
