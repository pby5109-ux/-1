# 两个项目融合学习总纲：智慧农场 × 综合测量仪器

> 使用方法：这份总纲把两个项目放在同一坐标系里。学任何一个知识点时，先看"对比表"里两个项目各自怎么做，再回答"为什么不同"。所有结论以各自源码为准。
>
> 素材来源：SmartFarm《从零理解智慧农场项目》《智慧农场项目面试讲义》《速记卡》+ 波形项目《面试问答手册》《项目全景理解清单》+ 两个项目的历史会话成果。

---

## 一、为什么这两个项目适合放在一起学

两个项目看起来完全不同——一个是"农业物联网"，一个是"口袋仪器"——但它们是**同一技术栈的两端**：

- 同一个芯片家族（STM32F103）、同一套 HAL + CubeMX 开发方式、同一个 FreeRTOS 内核；
- 面对同一批工程问题（任务划分、共享资源、数据搬运、事件检测、实时性），却给出了**不同的答案**。

把答案摆在一起对比，"为什么这样设计"才变得可见。这是这份总纲的核心学习方法：**每个知识点，先分别说清两个项目的做法，再问"差异来自什么需求约束"**。

## 二、共同技术底座（两个项目都要求能讲）

| 层面 | 共同点 |
|---|---|
| 主控 | STM32F103 系列：农场 C8T6（中容量）/ 仪器 RCT6（大容量），72MHz（HSE 8M × PLL 9），APB1 36M、APB2 72M |
| 开发方式 | CubeMX 生成初始化 + HAL 库 + 手写 BSP/App 层，ARM GCC 工具链（CLion/VSCode） |
| RTOS | FreeRTOS：农场走 **CMSIS-RTOS2 封装**（`osDelay/osMutexAcquire/osMessageQueuePut`）；仪器完成FreeRTOS移植并配置`FreeRTOSConfig.h`，业务层使用**原生 API**（`vTaskDelay/xEventGroupSetBits/xQueueOverwrite`）——同一内核两套接口 |
| 分层思想 | 都是 BSP（硬件驱动）→ App/Task（业务）→ HAL（外设）三层，BSP 不关心业务，任务不碰寄存器 |
| 双时基 | 两个工程都把 SysTick 让给 FreeRTOS，但节拍不同：农场为1000Hz（1ms/tick），仪器为100Hz（10ms/tick）；HAL 另用1ms硬件时基（农场TIM3、仪器TIM4）——这是“RTOS 与 HAL 时钟分离”的做法 |
| 调试环境 | ST-Link（克隆版，Under Reset 不稳可降 SWD 频率）、CLion/VSCode、串口预留 |

**第一个融合问题（入门自测）**：同一块内核，为什么农场用 CMSIS-RTOS2 接口而仪器用原生 API？两者能混用吗？各自优缺点是什么？

## 三、核心对比总表（背诵级）

| 主题 | 智慧农场 | 综合仪器 | 差异的本质 |
|---|---|---|---|
| 任务数量与优先级 | 4 任务，优先级分档：Input(High) > Sensor(Normal) > Screen(BelowNormal5) > BLE(Low) | 3个业务任务：KEY(2) > LCD(1)=LED(1)，另有软定时器服务任务(4)和空闲任务(0) | 两个项目都使用优先级抢占；同优先级的LCD/LED还可能时间片轮转，实际能否运行取决于各自阻塞点 |
| 任务触发方式 | Sensor/Screen/Input 全部周期轮询（1s / 10ms / 10ms） | LCD 阻塞在事件组、KEY/LED 阻塞在延时，**事件驱动为主** | 周期性任务 vs 事件驱动任务两种建模 |
| 共享资源保护 | **互斥锁**保护 I2C1 总线（OLED+AHT20 共用） | **事件组**通知重绘、**邮箱**传测量值、**信号量**同步 SPI DMA；互斥锁想用但 ISR 不能阻塞而放弃 | 锁保护的是"资源"，事件组保护的是"通知"——场景不同 |
| 生产者-消费者 | SensorTask →（指针队列）→ BLETask，消息 `pvPortMalloc` 动态分配、对端 `vPortFree` | 注入 ISR →（长 1 邮箱 Overwrite）→ LCD 任务，永远只要最新值 | "每条报警都要送达" vs "只要最新读数"——队列语义选择 |
| ADC 用法 | ADC1 **扫描 2 通道 + DMA 循环**（雨滴+NTC）、ADC2 **连续转换**直读（土壤）；经验公式映射 0~100，**无标定** | ADC1 **常规序列**（CH1，TIM3 触发，DMA 采 1024 点）+ **注入序列**（4 通道，TIM2 10Hz 触发，可抢占常规）；**VREFINT 校准 VDDA** | 采集型应用 vs 测量型应用的精度要求 |
| DMA | USART3 TX DMA 发 BLE；完成后**轮询** `HAL_UART_GetState()` + `osDelay(1)` | 三路：ADC→RAM（NORMAL）、RAM→DAC（CIRCULAR）、RAM→SPI LCD（完成中断 → **二值信号量**） | 同是 DMA 完成通知，一个轮询一个信号量——仪器的写法正是农场文档建议的改进方向 |
| 定时器角色 | TIM1=EC11 编码器解码；TIM2=风扇 PWM（10kHz/85%）；TIM3=HAL 时基；TIM4=蜂鸣器 PWM | TIM2=10Hz 触发注入序列；TIM3=采样时钟（TRGO 触发 ADC）；TIM5=DAC 输出时钟 | 农场把定时器当"输出/解码器"，仪器把定时器当"**时钟发生器**" |
| 显示 | I2C1 OLED 128×64：单个RAM帧缓冲`OLED_GRAM[8][128]`，完成RAM绘制后以400kHz整帧发送；线速理论下限约25ms/帧，AHT20/OLED共享总线 | SPI1 LCD 320×240：DMA 传输，事件组 9 位**按需局部重绘** | 整帧刷新 vs 脏区重绘；I2C 共享总线 vs SPI 点对点 |
| 事件检测 | **软件**：SensorTask 每秒比较阈值 → JSON 报警 + 蜂鸣器 + 水泵/风扇 | **硬件**：比较器 → EXTI3 触发采样，10ms Hold-Off 防重触发 + 100ms 强制触发兜底 | 秒级环境事件 vs 微秒级波形对齐——事件速度决定软硬分工 |
| 数据一致性风险 | `farmState` 单写多读（基本安全但浮点非原子）；BLEQueue满时的动态消息泄漏已修复并上板验证，UART DMA启动失败处理仍未修 | `waveform[]` ISR 写/LCD 读，**互斥锁被注释**，可能半新半旧画面撕裂 | 两个项目仍各有共享状态或异步生命周期风险，但农场队列Put失败泄漏已关闭 |
| 内存 | heap_4 10240B，报警字符串动态分配（每次 malloc/free） | heap_4 7KB，全部静态缓冲（rawDataBuffer/waveform/波形表），已做预算（≈5KB 占用） | 动态分配便利 vs 静态预算可控——嵌入式内存哲学 |
| 已知缺陷 | 队列满泄漏已修复并完成编译、烧录和用户上板验证；warning/recovered与5%滞回也已由用户确认上板，AHT20持锁延时和UART DMA返回值仍未修 | 三角波公式、波形竞争等仍未修；低频ARR和频率更新时序已由用户确认上板 | 两份缺陷清单必须持续区分代码修改、编译、烧录和实测状态 |

## 四、六大深度对比专题（按这个顺序学）

### 专题 1：FreeRTOS 任务设计——抢占 vs 时间片

- 农场：优先级是设计核心。InputTask 高优先级保证按键手感；SensorTask 普通；ScreenTask/BLETask 低。理由："错过截止时间的代价越大优先级越高"。
- 仪器：用户完成FreeRTOS移植并配置`FreeRTOSConfig.h`；当前源码为72MHz CPU、100Hz Tick、抢占和同优先级时间片开启、5级优先级、heap_4总量7000字节，并启用事件组、互斥锁、计数信号量和栈溢出检查。KEY优先级2，可抢占优先级1的LCD/LED；LCD和LED同优先级，二者就绪时可时间片轮转，同时依靠事件等待和`vTaskDelay`等阻塞点让出CPU。Hold-Off/强制触发由**软件定时器服务任务（优先级4）**处理。
- 对比问题：农场为何把Input、Sensor、Screen、BLE分成四档，仪器为何只把KEY提高到2而让LCD/LED同为1？如果农场OLED刷屏时间突然变长10倍，会怎样？仪器如果KEY任务优先级设成4，会对软件定时器服务造成什么影响？

### 专题 2：IPC 全景——同一本工具箱，不同用法

| 原语 | 农场用法 | 仪器用法 | 一句话区分 |
|---|---|---|---|
| 互斥锁 | 保护 I2C1 事务完整性 | 未使用（波形数组本应用，但 ISR 不能阻塞 → 放弃） | 保护资源，有所有者 |
| 消息队列 | BLEQueue 存 `char*` 指针，16 深度，阻塞接收 | 邮箱（队列长 1）+ Overwrite/Peek | 队列按序缓冲；Overwrite 只留最新 |
| 事件组 | 未使用 | 9 位对应 9 个 UI 区域，多生产者独立置位 | 只传"发生了什么"，不传数据 |
| 二值信号量 | 未使用 | SPI DMA 完成中断给信号量，任务同步等待 | 事件通知，无数据 |
| 软件定时器 | BeepTimer 500ms 周期（当前函数体注释保留） | Hold-Off 10ms 单次 + 强制触发 100ms 周期 | 定时逻辑放"任务上下文"回调 |

- 对比问题：农场的 BLEQueue 为什么存指针而不是 100 字节本体？仪器的邮箱为什么用 Overwrite 而不是 Send？如果农场报警改用"只保留最新一条"，存什么合适？

### 专题 3：ADC 信号链——从"能读数"到"读数可信"

- 农场（采集型）：ADC1 扫描模式 2 通道 + DMA1_CH1 循环（PB1 雨滴、PA4 NTC），CPU 零参与搬运；ADC2 连续转换 + `HAL_ADC_GetValue()` 直读。土壤/雨滴用 `100 - adc/40` 经验映射，采样时间 239.5 周期（≈20μs）。**没有标定，数值是相对量**。
- 仪器（测量型）：一个 ADC 两个序列——常规序列给示波器（TIM3 TRGO 触发，DMA 1024 点，最高 500kHz），注入序列给万用表（TIM2 10Hz 触发 4 通道，**可抢占常规序列**）。用芯片内部 1.205V VREFINT 反推真实 VDDA 做校准。硬件前端把 ±2.4V 搬进 ADC 量程，软件再 `×2-2.5` 还原。
- 对比问题：注入序列"抢占"常规序列，和 FreeRTOS 高优先级任务抢占低优先级任务，异同点在哪？农场的 ADC 为什么不校准也能用，仪器的万用表为什么必须校准？

### 专题 4：DMA 与完成通知——轮询 vs 信号量

- 农场：`HAL_UART_Transmit_DMA()` 之后 `while (HAL_UART_GetState() != READY) osDelay(1);` 轮询等待。优点：简单、每 1ms 让出 CPU；缺点：不是真正的"阻塞到完成"。
- 仪器：SPI DMA 传输完成中断里给二值信号量，LCD 任务 `xSemaphoreTake` 等待——"异步发起 + 同步等待"标准模式。
- 对比问题：把仪器的信号量方案搬到农场 BLETask 应该怎么写？DMA 完成前为什么不能 `vPortFree(msg)`？两个项目里哪个缓冲区有"DMA 期间被改写"的风险？

### 专题 5：定时器——输出、解码与时钟发生器

- 农场（面向外设）：TIM1 编码器模式（TI1 边沿计数 + B 相定方向 + Filter=15 硬件滤波）解码 EC11；TIM2 CH1 PWM 10kHz/85% 驱动风扇；TIM4 CH4 PWM 2kHz/20% 驱动无源蜂鸣器（对照手册 2700Hz/50% 有偏差）；TIM3 兼作 HAL 时基。
- 仪器（面向系统）：TIM2/3/5 全部通过 **TRGO 输出触发信号**——TIM2 10Hz 触发注入序列、TIM3 可调 ARR 触发采样（12 档时基查表，默认 128kHz）、TIM5 触发 DAC。定时器在这里不输出波形，是"节拍器"。
- 对比问题：定时器的 TRGO、PWM 输出、编码器输入三种模式各改变了定时器的什么功能？农场把 TIM3 用作 HAL 时基、SysTick 给 RTOS，这个"双时基"设计的动机是什么？`HAL_Delay` 和 `osDelay` 在这个设计下行为有何不同？

### 专题 6：显示系统——I2C 整帧 vs SPI 按需重绘

- 农场：OLED 128×64（CH1116，I2C 地址 0x7A = 0x3D 左移）与 AHT20 共用 I2C1 → 必须互斥锁；RAM 帧缓冲先绘制后整帧发送；ScreenTask 周期 10ms 全量重绘。
- 仪器：LCD 320×240 走 SPI1（18MHz，DMA）；事件组 9 位按需重绘，只画"脏"的区域；早期全屏重绘版因 CPU 浪费和闪烁被改造为事件驱动。
- 对比问题：为什么农场的 OLED 不也改成"事件驱动按需重绘"？为什么仪器的 LCD 不用整帧缓冲？I2C 与 SPI 的总线特性如何影响这两个选择？

## 五、两个项目的缺陷清单（融合版，改进题题库）

### 农场（12 项，来源：从零理解 §12）

1. BLEQueue满时不释放字符串：**已修复并完成编译、烧录和用户上板验证**；Put失败时所有权仍在SensorTask，由`QueueBleMessageOrFree()`立即`vPortFree`
2. 异常持续时每秒重复报警：**2026-08-21已改代码并编译**，每类报警只在进入/恢复边沿发送warning/recovered；待上板验证
3. 雨滴报警JSON传阈值而非实值：**2026-08-21已改代码并编译**，现发送`farmState.rainGauge`；待上板验证
4. 蜂鸣器音调 2kHz/20% 偏离手册 2700Hz/50% 谐振规格（蜂鸣器 2026-08-15 起已启用）
5. 单阈值控制水泵：**2026-08-21已改代码并编译**；低于`minSoilMoisture`开启，达到`min+5%`关闭（不超过配置的max），滞回区保持原状态；待上板验证
6. ADC 经验映射 `100 - adc/40` 未做干湿点标定
7. `farmSafeRange` 被 InputTask 写、SensorTask 读，无同步保护
8. 传感器通信错误未检查 HAL 返回值、无故障上报
9. AHT20 驱动里 `HAL_Delay(75)` 忙等占用任务（可改为触发后 `osDelay(75)` 让出 CPU）
10. 蜂鸣器 2kHz/20% 偏离手册 2700Hz/50% 谐振规格
11. OLED当前每10ms尝试一次完整重绘与整帧发送，I2C1已配置400kHz；仍可从按需刷新、降低重复整帧发送、DMA/完成通知等方向优化总线占用
12. `low_power.h` 只有声明无实现——不是"有低功耗"，是"预留接口"

### 仪器（5 项，来源：全景清单 §6）

1. `waveform[]` ISR 写 / LCD 任务读，互斥锁被注释 → 双缓冲或转换移入任务
2. ISR 内做 1024 次浮点转换（≈0.3ms@72MHz）→ ISR 只置事件位，任务里转换
3. `AutoSampleRate()` 低频分支不更新 PSC/ARR → 50/100/200Hz 档实际恒 500Hz
4. `lcd.a` 是加密商业库 → 教学版 `lcd_edu.c` 已实现等价功能
5. DAC 方波幅度 ±1V 与正弦 ±2V 不一致

### 跨项目共同规律（学会这类问题的通用解法）

- **缓冲区生命周期**：谁分配、谁使用、何时释放（农场 BLE 指针 / 仪器 DMA 缓冲）
- **ISR 最小化**：中断只做"启动/置位/搬运结果"，重活交给任务（两个项目都有反例可讲）
- **事件边沿化**：连续状态用边沿触发（农场报警去重 / 仪器 One-Shot 正是边沿思想）
- **标定与精度**：读数≠真值，比例测量需要基准（仪器 VREFINT 已是范例，农场 ADC 待标定）
- **滞回与死区**：阈值附近的抖动（农场水泵 / 可类比仪器触发电平稳定性）

## 七、跨项目自测题库（提问学习用）

以下问题全部需要"先答一个项目、再对比另一个项目"。建议每节课后先自测，答不出再提问。

1. 两个项目为什么一个用 CMSIS-RTOS2、一个用原生 FreeRTOS API？同一工程里能混用吗？
2. 农场的 I2C1 为什么需要互斥锁，而仪器的 SPI LCD 不需要？仪器的 `waveform[]` 为什么"想用互斥锁却用不了"？
