FreeRTOS：谁能竞争CPU，ISR退出后换不换人

本课只解决三个盲区：Blocked任务不参加调度；同优先级Ready任务才使用时间片；xHigherPriorityTaskWoken是FromISR API写出的切换请求，不是事件检测器。

任务状态与调度资格

Running调用vTaskDelay或等待未满足的事件/信号量 → Blocked → 条件满足或超时 → Ready → 被调度器选中 → Running。

  • Ready：具备运行条件，正在等待CPU。
  • Running：当前占用CPU；单核同一时刻只有一个。
  • Blocked：等待时间、事件、队列或信号量，不参加优先级和时间片竞争。
  • Suspended：被显式挂起，也不参与调度，直到被恢复。

KEY执行vTaskDelay(pdMS_TO_TICKS(10))后至少阻塞一个tick。调度器马上从Ready集合选最高优先级任务。10ms到期后KEY回到Ready；因为它的优先级2高于LCD/LED的1，所以在允许抢占的调度点会优先运行。

72MHz与100Hz分别管什么

configCPU_CLOCK_HZ=72MHz表示内核/SysTick输入时钟；configTICK_RATE_HZ=100表示FreeRTOS每秒只产生100次系统节拍。因此端口层把SysTick重装值设为72,000,000 / 100 - 1 = 719,999，最终得到每10ms一次tick。

100Hz也是时间片轮转的检查节拍：若最高就绪优先级存在多个同优先级Ready任务，tick处理可请求切换。但它不是“只代表时间片”，还推进Delay/超时/软件定时器等内核时间；任务也能因阻塞、Yield、更高优先级就绪或ISR退出切换而在两个tick之间换人。

pdMS_TO_TICKS(ms) = ms × configTICK_RATE_HZ / 1000。毫秒转tick看100Hz，不直接看72MHz。

相对延时与固定周期

API基准周期效果
vTaskDelay(period)从“本次调用Delay的时刻”往后数启动间隔≈本轮处理时间+Delay，处理时间变化会形成周期漂移
xTaskDelayUntil(&lastWake, period)从“上一次计划唤醒时刻”计算下一绝对截止点只要任务在截止前完成，启动时刻保持固定周期

例如周期100ms：本轮处理2ms时，vTaskDelay(100ms)使下一次约在102ms开始；处理15ms时约在115ms开始。xTaskDelayUntil则分别等待约98ms和85ms，使下一次都瞄准100ms周期边界。若处理时间超过整个周期，它不会倒退时间等待，可通过返回pdFALSE识别本次没有真正延时/可能错过截止时间。

TickType_t lastWake = xTaskGetTickCount();
const TickType_t period = pdMS_TO_TICKS(100);
for (;;) {
    DoPeriodicWork();
    BaseType_t delayed = xTaskDelayUntil(&lastWake, period);
    /* delayed == pdFALSE：检查是否发生周期超时 */
}

当前FreeRTOS版本的正式函数名是xTaskDelayUntil()并返回BaseType_t；旧名称vTaskDelayUntil()仍作为忽略返回值的兼容宏存在。若当前时间已经越过本次目标点，函数返回pdFALSE并且本次不阻塞，但只把lastWake推进一个周期；它不会在一次调用中自动跳过所有逾期周期并等待最近的未来边界。

同优先级时间片不是“固定排队”

LCD和LED同为优先级1，并且二者同时Ready时，开启时间片后可以在tick边界轮转。轮转不是随机抽签：FreeRTOS沿该优先级的Ready链表循环选择下一个任务，结果由链表位置、任务插入和此前阻塞/唤醒历史决定，因此是确定性的，但不能简单假定始终按任务创建顺序。

LCD通常阻塞在xEventGroupWaitBits(..., portMAX_DELAY)；此时它不在Ready列表中，LED不需要和它分享时间片。LCD是由事件位置位唤醒，不是必须等待一段固定时间。

本工程一个tick恰好是10ms，而KEY也只Delay 10ms。如果KEY阻塞时LCD和LED都Ready，调度器先选其中一个优先级1任务；若LCD很快再次等待事件，LED会立即获得CPU。到下一个tick时KEY已经恢复Ready并以优先级2抢占，因此这10ms窗口里未必能观察到LCD/LED完成一次纯粹的时间片轮转。

FromISR的两个步骤

BaseType_t xHigherPriorityTaskWoken = pdFALSE; → 调用...FromISR(..., &xHigherPriorityTaskWoken) → portYIELD_FROM_ISR(xHigherPriorityTaskWoken)。

  1. ...FromISR()完成中断安全的发送/释放；如果它让一个比被中断任务优先级更高的任务变为Ready，就把输出标志写成pdTRUE。
  2. portYIELD_FROM_ISR()根据该标志请求在ISR退出后进行上下文切换，使高优先级任务无需等到下一个tick。

xHigherPriorityTaskWoken不会自己检测硬件事件，也不表示高优先级任务已经运行；它只记录本次FromISR操作是否产生了“ISR退出后应立即换任务”的需要。

比较条件是“严格更高”，不是“大于等于”。例如LED优先级1运行时，中断唤醒同为优先级1的LCD，标志通常仍为pdFALSE，ISR退出后不会因此立即抢占；LCD可在后续tick时间片，或LED阻塞/主动让出时运行。若唤醒优先级2任务，标志才会置为pdTRUE并请求ISR退出切换。

为什么ISR不能阻塞

ISR不是FreeRTOS任务，没有可供调度器保存并放入Blocked列表的任务上下文，也不能像任务一样等待资源后再恢复。ISR必须有有界、尽量短的执行时间，并使用专用FromISR API。普通可能阻塞的API在ISR中可能触发断言、破坏内核状态或造成不可预测行为；这不是正常意义上的“ISR进入Blocked”。
