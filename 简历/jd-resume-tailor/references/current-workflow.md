## 一、目录与命名（2026-09-26 用户确认，硬约束）

### 1.1 目录结构

- **最新版简历**放`简历/简历修改版本/模板简历（随时跟新）/模板简历/`；
- 被替换的旧版整体移入`模板简历（随时跟新）/旧版简历/<修改日期>/`，日期用"月.日"格式（如`9.26`）；同一天多个版本在文件名后加`-2`、`-3`序号，单日单版不加。仅归档本次实际被替换的同方向、同选择版本，不移动其他岗位或组合。先在暂存目录生成并验证、用户确认最终版后，再在规定分类锁内归档旧件并发布新件；失败保留旧件可用，不先清空模板目录。归档前后核对路径/哈希并记录映射；若日期目录已有同名文件，使用序号，禁止覆盖。
- JD 定制生成的成品放`简历/定制投递/<公司>-<岗位>-<日期>/`。公司名未提供时不阻塞生成，可用描述性占位目录名（如"无人机配套MCU嵌入式-深圳-20260928"），获得公司名后即时把目录与文件一并改名。

### 1.2 文件命名

- **技术岗（核心）**：`彭博裕-<岗位>-<两位数字>.pdf`。两位数字第一位是校园、第二位是实习：`00`＝都不写；`10`＝写校园不写实习；`01`＝写实习不写校园；`11`＝两者都写（合法，基本不出现）。项目经历默认写。
- **销售岗**：不带数字后缀，如`彭博裕-客户经理.pdf`；版式与模板基本一致。
- JD 定制版沿用上述命名（岗位名按 JD 填写），放在对应公司投递文件夹内；同日同岗位多版本加序号。
- 两位数字只表示校园/实习是否存在，不表示校园长短。预览及本次`selection.json`或已有交付记录须另记`campus_variant=long|short|none`、`internship=yes|no`、项目组合、模板路径/哈希及输出文件；同一编码的长短两版用序号区分并记录映射，不覆盖。不能仅由文件名推断长短。

## 二、每轮工作规则

### 2.1 两种工作模式（2026-09-26）

1. **优化简历**：先给出修改方向（嵌入式／客户经理等）与逐项修改内容（项目经历、实习经历、校园经历等），把涉及栏目的几版内容依次替换；新版放`模板简历/`，被替换的旧版移入`旧版简历/<修改日期>/`。
2. **JD 定制**：每份JD先按2.6判断不改/小改/大改；不改沿用，小改给手改清单，大改按授权检查全文适配并生成。只有项目/校园/实习变化先审批，其余栏目无需逐项审批。公司未提供不阻塞分析与生成，不虚构公司。

### 2.2 单组合生成与增量更新（2026-09-28）

1. **只生成一个组合**：JD 定制与优化简历都可指定技术岗四组合中的任意一个（`-00`／`-10`／`-01`／`-11`），**只按该一版修改与生成，不产出其他组合**；未指定的组合保持原有文件不动。
2. **增量更新省 token**：以匹配的最新用户手改PDF为底，只列差量，不重读全部历史、不重复输出未改内容；大改可以检查全文适配，不为定制而重写全篇。语义深审集中在变更段落，但仍验收整页视觉和全文完整性，核对未改栏目没有误删/误改。无实质差量建议沿用。
3. 差量与底版本的对应关系记入交付记录（基准文件、哈希、差量清单），保证可回溯；禁止用缓存整稿覆盖基准中用户较新的手改。

### 2.3 版本与权威标准（2026-09-28）

1. 先选岗位方向，再选实习与校园长/短/无，在匹配的候选内确认最新版；不按全目录修改时间选择。无完全匹配版时提出最近适合的基准和差量，用户确认后使用；不能将最新客户经理稿当技术稿，或用无校园版覆盖用户选定的校园长版。
2. **用户规则（2026-10-01补充）：用户修改PDF即表示主动优化，以该岗位/栏目组合的最新PDF作为内容与版式基准。** Word/JSON落后时按PDF合并或重建，不回退旧稿。使用前检查表达、重复、逻辑、HR可读性及事实一致性；保留用户有意修改，列出必要修正理由。PDF证明用户选择的措辞，不自动证明量化测试；真正新增的事实冲突按下一条局部核对。核对PDF与Word对应关系不能只看时间。
3. 所选模板决定措辞和排版，但不自动证明每项工程事实。沿用已有后期核验确认，不因过时源码快照反复质疑；出现真正新增、未解决的证据冲突时，遵守 AGENTS 与 truth-policy，只核对该项并显示差异，待确认/补证或采用有依据的限定表达后再进入最终稿，其余部分继续。不能静默改稿，也不能规定无论冲突均不拦截。明显笔误/键入错误先说明再修。
4. 最近公司定制交付稿只用于继续该投递，不自动提升为通用母版；**定制中新增的技能词（如某 JD 专用的 IAR、TCP/UDP/HTTP）同样不回写母版技能行**，除非用户明确要求。只有用户明确指定设为通用，才进入优化简历的发布流程。

### 2.4 每次核对模板（2026-09-18，动态模板优先）

模板目录为`D:\APP\project_practice\codex-project\简历\简历修改版本\模板简历（随时跟新）/模板简历/`（最新版简历所在处，命名规范见§一），相对此文件为`../../简历修改版本/模板简历（随时跟新）/模板简历/`。名称按磁盘原样使用。

- 列出当前文件与修改时间，读取相关正文和结构，选定后记录 SHA256；**不能仅按时间认定最新 PDF 与某份 Word 对应**。
- 告知本次基准文件、项目组合、实习及校园选项。用户已指定则执行，不重复询问；多份内容冲突或对应关系不明才问必要问题。
- 所选模板中的最新正文、栏目、样式及实习内容优先于旧 JSON/投递包。`current-content.json`只是结构化快照，不能覆盖用户较新的手改；生成前再核对模板哈希，变化则合并差量，不使用缓存全文覆盖。

- 用户 2026-09-18 确认后期版本正确且已经核验，沿用该定稿，不让旧排名/奖项/熟练度口径回退。记录为用户核验确认，不等于本 Agent 独立硬件测试或证书核验，也不扩大指标适用条件。

### 2.5 项目池与栏目选择

- 素材池始终保留：综合测量平台、智慧农场、低功耗 LoRa 节点、MSPM0＋K230 瞄准系统。默认组合为综合测量平台＋低功耗节点＋瞄准系统，不自动把四项都放进一页；未入选不代表素材应删除。按 JD 比较四项的相关性；有明显更合适的项目时，提出替换谁及理由，JD定制须列替换前后及理由并获批后执行；通用母版更新仍需发布确认。不因某项目暂未进入 JSON 就视为不可选。
- 来源：当前入选项目先读动态模板；农场读取`resume-content-library.md`第 3 节与讨论记录中的最新农场确认；校园长版读取素材库第 7 节及讨论记录 32.7；视觉补充读取工作区`项目集合/电赛视觉加灰度/简历项目经历草稿.md`。技术事实必要时增量核对`project-evidence.json`及新记录，不退回旧的仅灰度/OLED 贡献限制。避免每轮重读全部历史。

### 2.6 JD 匹配与表达

- 先提炼最重要的硬性技能、核心职责和产品场景，区分必须与优先，不机械按出现次数排序。用简短的"JD重点→适合项目→对应事实/结果"比较项目，不为匹配编造能力。
- 每个项目名后保留三个加粗、凝练关键词；由 Agent 选择替换哪些，预览给出"原三词→新三词＋理由"。只选该项目真实支撑的词，可保留旧词，不要求三个全换或所有项目同词。正文须能支撑关键词；无证据关键词列缺口，不塞入标题。
- 正文兼顾 HR 与技术面试官：做了什么＋关键方法＋产生什么结果，突出用途和价值，同时保留 1～2 个能讲清的技术钩子。避免堆 API、抽象术语或没有基线的"大幅提升"；指标沿已核验边界，不扩张为任意工况保证。
- 每份JD先输出简短评判：资格/匹配、重要关键词、基准PDF、改动量与理由。小改通常1～3处，给位置/原文/替换文由用户手改；不能只数处数，项目重排或影响版面可判大改。大改评估全篇适配，按事实优化意向、技能、荣誉等非保护栏目，无需审批这些栏目；无项目/校园/实习变动时简述差量后直接生成；有保护栏目差量时先审批。
- **项目/校园/实习保护门（2026-10-02）：** 项目选择/增删/顺序、名称、三个关键词、简介、职责、正文、指标及日期的变动，以及校园/实习文字、职务、日期、顺序、删除/新增、写/不写、长短切换均先给准确原文→新文及理由，等待批准后才能生成整份。未变无需再问；用户当轮明确指定的变动视为该准确变动已批准，不能扩张为任意新文。只需等待这三类变动，不恢复全篇审批。其他栏目遇新事实/指标冲突仅核对该项，不编造；审批不能替代证据。
- **给后续Agent的优化提示：** 基于用户最新PDF检查内容和表达，而不是默认PDF毫无问题或回退旧底稿。手改建议、代理授权生成、用户逐条审批、用户确认最终文件是不同状态，应分别记录。每代仍执行单组合、命名、灰线、一页验收、归档与最终文件确认后清理；定制不自动回写母版。详见`preview-contract.md`。

1. 仅改措辞：读取该字段及来源，不遍历四项目源码；保留语义、贡献和验证边界。
2. 新事实/指标：记录用户陈述或材料的具体来源、日期、状态；需要源码才能判断的，只查相关增量。历史"未实现"与新确认冲突不能静默继承。
3. 改 JSON 时提高`content_revision`，清除旧批准标志；用户已明确给出并要求使用的新内容可以记录其当轮批准。改变指标/职责时不得沿用旧批准。
4. 已批准原文生成：以 JSON 为输入，开启/关闭实习和校园；不用重复提出相同问题。历史全文不回写。
5. JD 定制：保留通用 JSON，复制成该投递包的工作内容，只改岗位、关键词、项目顺序及有依据的对应条目；通用源仅在用户确认"设为通用"后更新。

```powershell
<bundled-python> scripts/build_current_resume.py --check
<bundled-python> scripts/build_current_resume.py --content <已批准JSON> --out-dir <新目录> --internship yes --campus both
# 单版示例：--internship no --campus no
```

生成脚本拒绝覆盖已有 Word，选择新修订目录。正文哈希锁定的 20260917 基准是视觉源；更换模板需先检查结构及渲染，不直接改哈希绕过。PDF 使用本机 Word 导出并检查一页 A4，随后看图和提取文字。默认不缩小源 8pt 字体/页边距；超页先收紧重复措辞或栏目间距，必要时请用户取舍。

### 5.3 现有 schema v2 实现边界

根字段：`schema_version=2`、`approved`、`content_revision`、`approval_record`、`sources`、`header`、`education`、`honors`、`projects`、`enterprise`、`campus`、`skills`、`layout`、`review_notes`。条目包含`label/text/source_refs`；校园仅`text/source_refs`。项目包含`id/name/keywords/intro/duty/bullets`，日期与角色不在标题中。项目 3 个、条目默认 3+3+3，生成器可容纳每项目 1～4 条；必须渲染验证而非以固定总数代替版面判断。

`source_refs`检查可追溯性，不能证明措辞真实或批准有效。沿用已选基准的文字可保留，新增 JD 主张必须人工对照事实证据，禁止为过校验而挂一个宽泛来源。当前 54µA 是用户报告实测，8 个月是 1100mAh 和既定工况下估算；视觉整机指标不扩大为纯算法精度或全部条件保证。
