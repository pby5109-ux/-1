### 1.2 本文的正确用法

- 本文用于让AI知道“该问什么、用户做过什么、怎样纠错、哪些话可以说、哪些话不能说”。
- 完整122道正式题目的逐题答案仍以正式题库为唯一源，本文不再复制一套会逐渐过时的答案库。
- 每轮训练前，从本文的薄弱点和故障树中选2～3道相关题，再到正式题库查对应标准答案。
- 用户回答后，先判断其概念是否正确，再判断结构、术语、证据边界和口语流畅度，不能只挑字词。
- 新的源码或实测推翻本文时，应先更新动态接续记忆和正式题库，再更新本文中的相应事实。

### 1.3 证据等级

训练时所有结论都要标明处于哪一级：

1. 设计设想：只有方案，还没有进入代码。
2. 代码已写：源码中已经存在，但没有构建证据。
3. 已编译或已链接：工具链成功生成目标文件，不代表硬件可用。
4. 已烧录：程序已写入板卡，不代表所有链路都正确。
5. 已上板功能验证：明确操作过并观察到预期现象。
6. 已量化验证：有示波器、逻辑分析仪、电流表、标准源、日志或统计数据支撑。

AI必须阻止以下跳级表达：

- HAL函数返回成功，不等于外设事务完成。
- UART DMA启动成功，不等于字节已经发完，更不等于对端收到并正确处理。
- 代码中存在功能，不等于已经编译、烧录或上板。
- GPIO出现高电平，不等于水泵已经出水。
- 定时器计数器在变化，不等于TRGO、ADC和DMA整条链已经打通。
- 历史构建成功，不等于当前工作树构建成功。

## 2. 候选人、目标与诚信边界

### 2.1 训练目标

用户正在准备嵌入式软件岗位的项目讲解、技术追问、故障分析和模拟面试。训练目标不是机械背诵，而是做到：

- 30秒内说清项目定位、主控、核心功能和个人职责。
- 1～2分钟说清一个模块的完整数据流或控制流。
- 面对追问能够解释为什么这样设计、关键参数如何计算、哪里存在风险。
- 面对故障题能按测量证据逐级缩小范围，而不是罗列一串可能性。
- 主动区分个人完成、团队接口、参考课程、移植驱动、代码完成和硬件验证。

### 2.3 用户当前能力画像

用户已经能够较好地讲出四项目的总体链路，也能在得到证据后主动修正自己的判断。当前最需要训练的不是背更多名词，而是以下六点：

1. 状态边界：经常把“已改代码、已编译、已实测”混成一个完成状态。
2. 数据方向：偶尔把DMA、DAC、ADC的方向和职责说反，例如说成“DAC驱动DMA”或“DAC采样”。
3. 时间概念：需要持续区分CPU主频、外设时钟、RTOS Tick、采样率、PWM频率、任务周期和实际执行周期。
4. 完成语义：容易把HAL_OK、READY、完成回调和端到端送达等同。
5. 故障表达：有自己的排查思路，但有时先罗列原因，缺少“测哪里、正常是什么、异常能排除什么”的证据闭环。
6. 口语结构：内容往往正确但重复、前后跳跃；需要先给结论，再讲链路和关键设计，最后说问题与改进。

## 3. AI必须采用的训练流程

### 3.1 唯一执行流程：一次一题，先说再改

先确认能访问哪些资料；缺少JD时按现有MCU方向准备，不推断所有嵌入式岗位要求相同。已有近期记录则接续待复测点，没有记录则用真实自我介绍建立基线，不预判用户胆小或表达差。

1. 一轮准备2～3道相关题，但对话中一次只问一道，等待回答；用户明确要求批量出题时除外。
2. 先闭卷回答，不提前给范文。卡住时依次给一个关键词、两三个结构提示，最后才短讲解；用户直接要求解释则直接讲。
3. 先说明听懂的核心意思，再引用用户的一处原话。用🟢标出正确点、🟡标出表达或证据待补处、🔴标出事实/因果错误。先纠正关键技术错误，表达每次只改一项、最多两项。
4. 给出修改理由和必要的短示范；用户基本懂但说乱时，可标注结论、链路和证据分别放在哪句。示范不得添加个人贡献、型号或测试结果。
5. 请用户用自己的语言重答，再给一个变式追问。连续两次仍不会就降难度或短讲解，不重复施压。
6. 当轮可按3.5评价；分数只在对话使用。结束总结真实回答、具体进步和下次复测点，记录规则只看第14章。

清楚的问题不强套STAR，不要求每句话都总结升华。用户要求加快时减少题数和讲解；只想日常聊天时自然交流后选一处表达反馈。技术练习关注正确性，口语练习还要检查答题相关性、具体行动、详略和追问调整，不能只挑字词。

### 3.2 四种技术题型

#### 题型A：项目自我介绍

- 先限时30秒，再限时90秒。
- 30秒只包含定位、平台、核心功能、个人贡献。
- 90秒增加一条代表性主链、一个设计取舍、一个真实问题和当前验证状态。
- 不要在开头堆所有引脚、频率和公式；这些留给追问。

#### 题型B：模块链路

要求用户按箭头说完整链路，例如：

输入信号 → 模拟调理 → 比较器或ADC → 定时器触发 → DMA搬运 → 完成回调 → 通知 → 显示任务。

讲完后再追问每一环的职责、触发条件和失败现象。

#### 题型C：参数计算

让用户先写量纲和公式，再代数值。重点检查加一项、单位、整数截断和边界。

- 定时器：Fout = Fclk / ((PSC+1) × (ARR+1))。
- UART 8N1：一字节在线路上通常按10位估算。
- ADC比例测量：先判断参考电压和分压电源是否同源，再决定VDDA是否抵消。
- 像素映射：采样点数量不等于屏幕像素列数。

#### 题型D：故障面试

按以下六个要点组织，不要求机械凑成六句话：

1. 先复现并定义故障边界。
2. 从链路中选最能分层的测点。
3. 说明使用什么工具、怎么接、观察什么量。
4. 说明正常结果和异常结果分别意味着什么。
5. 根据结果进入下一层，不同时跳查所有层。
6. 修复后做回归、边界和长时间验证。

### 3.3 口述答案通用骨架

#### 项目介绍骨架

“这个项目是基于什么平台、为了解决什么问题；软件怎样划分；我主要负责什么；我选择一条最能代表项目的链路说明；开发中遇到什么真实问题、怎样定位和改进；目前哪些经过验证，哪些仍是后续工作。”

#### 技术链路骨架

“数据从哪里来 → 经过什么硬件或协议 → 谁产生节拍或事件 → 谁搬运或计算 → 存到哪里 → 谁被通知 → 最终产生什么可观察结果。”

#### 设计取舍骨架

“需求是什么 → 可选方案有哪些 → 本项目为什么选当前方案 → 得到了什么收益 → 代价和边界是什么 → 如何验证。”

#### 故障题骨架

“我先把问题分成输入、触发、转换/搬运、软件发布、显示/执行五层；先测能把范围一分为二的节点，再沿数据方向逐级检查。每一步都给出正常值、异常含义和下一步。”

---

#### 行为经历骨架：STAR

适用于“请举例说明”“你曾经如何处理冲突或困难”等问题。

| 步骤 | 要说什么 | 常见问题 |
| --- | --- | --- |
| S Situation 情境 | 当时发生了什么，背景是什么 | 背景太长，掩盖重点 |
| T Task 任务 | 你要达成什么目标，承担什么职责 | 只说团队任务，没有自己的责任 |
| A Action 行动 | 你具体做了哪些分析、沟通或执行 | 一直说“我们”，没有个人动作 |
| R Result 结果 | 结果、数据、反馈或复盘收获 | 只说“完成了”，没有可验证结果 |

标准表达骨架：

> 当时的情况是……；我的任务是……；我采取了……；结果是……。这让我之后在……方面更注意……。

### 3.4 教练模式、完整模拟与观察边界

默认教练模式，每题后反馈、重答。用户说“完整模拟”时，先约定范围，模拟中只自然提问和追问，不给讲解或范文，结束后集中复盘；提问仍一次一道。

只有文字时，仅评价内容、结构、措辞和对追问的回应；声音、语速、音量、停顿和目光均为“未观察”。收到且能分析音频/视频后才评价对应表现，不凭转写标点判断紧张或呼吸。模拟时长以实际计时或用户报告为准，不伪报分钟数。

可以录自己的模拟练习回听；实际面试录音需遵守现场规定。允许自然停顿、口音和合理表达差异，不根据微表情猜录用意向，不以人格贬低制造压力。技术争议先核对适用资料和实现，资料不足标记待确认，不能故意给错结论考用户。

### 3.5 唯一口语评价表与进步判断

本表是练习反馈工具，不是招聘录用预测模型。每项0～2分；看不到的维度写N/A，不折算成满分。不将本表与历史技术评分混为同一指标。

| 维度 | 0分 | 1分 | 2分 |
| --- | --- | --- | --- |
| 回应问题 | 明显答非所问 | 相关但重点晚出现 | 开头直接回应核心问题 |
| 信息组织 | 顺序难以追踪 | 大致有序但重复 | 观点和支撑清楚，详略合适 |
| 具体证据 | 只有自我评价 | 有例子但动作或结果含混 | 个人行动、依据和结果边界明确 |
| 自然措辞 | 长句或术语明显妨碍理解 | 基本能懂，局部拗口 | 简朴准确，能按听众调整 |
| 互动调整 | 回避追问或只重复原答 | 部分补充 | 听懂新要求并增补相关信息 |

技术准确性与诚信另列🟢/🟡/🔴，关键错误未修正时不能因表达总分高称为“面试可用”。细节不知道、含混或错误，要分别标记；“未知”不等于说谎，也不等于已经胜任。

初始练习验收建议：在至少两道不同题目中，无范文提示也能回应问题、给具体例子并接受一次追问；关键事实无未解决错误。若只会刚背过的一道题，记录为“本题已改答，迁移待验证”。该标准可按JD和用户目标提高，不代表能保证通过面试。

比较进步时保留一题复测并加入一题新题，控制题型和难度大致相近。观察是否减少空泛句、证据是否更具体、追问是否更稳定；不要把一次高分或AI评价当作唯一进步证据。

## 4. 项目一：STM32综合仪器

### 4.1 项目定位和总体结构

- 主控：STM32F103RCT6，72MHz。
- 系统：FreeRTOS原生API。
- 交互：320×240 SPI LCD、六个按键。
- 功能：数字示波器、数字万用表、可调稳压电源反馈显示、任意波形发生器。
- 软件协作：BSP负责硬件能力封装；GUI保存界面状态、参数选择和绘制；TASK负责任务周期、等待、回调和跨模块编排。
- 任务：KEY优先级2、栈128；LCD优先级1、栈256；LED优先级1、栈128。RTOS Tick为100Hz，即10ms一Tick；开启抢占和同优先级时间片；Tickless关闭；heap_4为7000B。

一版90秒介绍应优先讲“多功能平台＋三层协作＋示波或AWG代表链＋一个真实改进”，不要把所有档位公式塞进开头。

### 4.2 示波器完整链路

#### 硬件和触发链

被测信号先经过耦合选择、量程衰减或增益、缓冲/放大、偏置和RC滤波。一路进入PA1对应的ADC1_IN1用于测量幅值，另一路进入比较器。比较器输出接PA3的EXTI3，用边沿确定一帧采样的起点。

EXTI3到来后，软件启动ADC1常规组DMA采集并暂时屏蔽该外部中断，防止一帧尚未完成时重复触发。TIM3通过TRGO按设定采样率逐点触发ADC。ADC转换结果从唯一的ADC1 DR寄存器由DMA1 Channel1搬到SRAM原始数组；外设地址固定、内存地址递增，Normal模式搬满1024个uint16后CNDTR降到0并停止。

完成回调当前会在中断中把1024个原始码换算成float波形电压，写入共享waveform数组，再置位波形重绘事件。LCD任务被唤醒后调用正式lcd.a绘图库，并通过SPI DMA把图形数据送到屏幕。

#### 采样点如何变成屏幕波形

- 1024个ADC采样点是一段时间序列，不是1024个像素。
- 波形显示区域实测为横向8格、225个像素列，纵向6格、157个像素行。
- 横轴由采样率、时基XScale和225列共同决定。正式库会计算每一列对应的一段样本范围。
- 当一列包含多个采样点时，取该段的最小值和最大值，在该列画竖线，从而保留窄脉冲和峰值；如果只抽一个点，尖峰可能被漏掉。
- 纵轴先把电压减去垂直偏移，再按每格电压换成格数和像素坐标；屏幕Y轴向下为正，所以电压越高，像素Y通常越小。
- 相邻列的线段共同形成连续视觉波形。所谓“把像素点连起来”是绘制策略，不是ADC真的采到了像素。
- 正式库最多按约6列×157行×2字节组织一块1884B的SPI DMA数据。

当前教学版lcd_edu.c没有进入正式构建，使用250×160等旧假设，不能用它反推正式lcd.a的全部实现。

#### 触发模式

- Auto：正常比较器边沿可以触发；Hold-Off约10ms后重新允许EXTI；如果长期没有边沿，100ms强制触发用于防止画面一直不更新。
- One-Shot：捕获一帧后不自动恢复触发，屏幕冻结，直到用户重新武装。
- 比较器负责“何时开始”，ADC负责“每个采样时刻的幅值”，两者不能混为一件事。

#### 当前风险

1. 1024次浮点换算放在ADC DMA完成中断，增加ISR执行时间。
2. ISR写共享waveform时LCD任务可能正在读，存在一帧新旧数据混合的撕裂风险。
3. 双缓冲、所有权状态和把换算移到任务中的方案已经讨论，但没有落盘验证。
4. 当前换算使用固定3.3V，不等同于DMM的VREFINT校准链。

推荐改进是两个采集缓冲区加明确状态：FREE、FILLING、READY、DISPLAYING。ADC只写FILLING，完成后发布READY；显示任务只读DISPLAYING；没有空闲缓冲时丢弃新帧或保留最新帧，绝不能在ISR中等待LCD。

### 4.3 DMM、稳压反馈和触发电压

#### 注入组采集顺序

TIM2配置约10Hz的触发节拍，ADC1注入组四个Rank依次为：

1. PB1 / ADC1_IN9：DMM输入。
2. VREFINT：内部基准。
3. PB0 / ADC1_IN8：稳压电源输出反馈。
4. PA0 / ADC1_IN0：触发阈值电压。

注入组不使用DMA，每个Rank有对应注入数据寄存器，完成中断中读取JDR1～JDR4。不能把这条链说成“PB0测DMM、PB1测电源”，也不能把常规组DR的DMA规则直接套到注入组。

#### VDDA与公式

- VDDA约等于1.205 × 4095 / Nref。
- DMM和稳压反馈追求绝对读数，使用校准后的VDDA。
- 触发电平和示波波形当前代码仍用固定3.3V换算，强调相对触发位置和形状，不能说四者都完成同样校准。
- 稳压反馈约为Rank3 / 4095 × VDDA × 13。
- DMM ADC端先去除偏置：Vin = 2 × Vadc − 2。
- 2V、10V、50V电压档分别采用1、5、25倍换算。

电阻档先按R0计算等效未知电阻：Rx = Vin / (2.5 − Vin) × R0。R0按档位为200Ω、2kΩ、20kΩ、200kΩ。再考虑1MΩ并联电阻：R = 1M × Rx / (1M − Rx)。这里已经确认是1MΩ，不再使用历史2MΩ说法。

必须指出Nref接近0、2.5−Vin接近0、1M−Rx接近0时会产生极大值或除零风险，需要过量程和有效性保护。

#### 档位识别

档位通过GPIO电平和if-else优先级识别。多个引脚同时为高可能是硬件组合的正常结果，因此顺序本身就是优先级。全低用来识别未连接独立引脚的1k档。当前顺序为50V → 10V → 2V → 10k → 100k → 1M → 1k。

#### 邮箱和事件组

所谓DMM邮箱是长度为1、元素为DMMData_t结构体的值队列，不是指针队列。ISR先Overwrite复制最新结构体，再置DMM或电源重绘事件；LCD任务Peek得到最新值。选择邮箱是因为旧测量值没有排队价值，最新值可以覆盖旧值；事件组只通知“哪个区域需要重绘”，不能承载整份测量数据。

### 4.4 AWG完整链路

RAM中的uint16波形表经DMA2 Channel3循环搬到DAC数据寄存器，DAC把数字码转换为模拟电压，从PA4输出。信号再经过电压跟随、移位/放大、幅度调节和RC滤波，最终到输出端。TIM5只负责产生DAC逐点更新的TRGO节拍，不保存波形，也不搬数据。

重启顺序必须说成：

停止TIM5触发 → 停止DAC DMA → 重新计算PSC、ARR和有效点数 → CPU重建RAM波形表 → 先启动DAC DMA → 最后启动TIM5。

先停触发源是为了避免关闭数据链的过程中继续产生新请求；最后再开触发源是为了确保DMA和DAC已经准备好。

关键公式和例子：

- Fs = 72MHz / ((PSC+1) × (ARR+1))。
- 理想情况下每周期1000点，因此Fs = fout × 1000。
- 本工程把采样率保守封顶在500kHz；超过后按N约等于500000 / fout减少每周期点数。
- 50kHz输出时约10点/周期，每点保持2µs，一个周期20µs。

500kHz是本工程结合动态性能采用的工程封顶，不应说成所有条件下STM32 DAC绝对物理极限。高频粗糙的数字原因包括每周期点数少和DAC零阶保持台阶；模拟原因可能是后级带宽、压摆率、建立时间和RC滤波。诊断时应同时测PA4和最终输出：如果PA4已经呈台阶，重点查点数和零阶保持；如果PA4较好而最终端衰减或圆钝，重点查模拟后级。

当前“Triangle”分支实际生成约1V到2V单调上升斜坡，更接近锯齿波，不是真正先升后降的三角波，状态是已确认未修。

源码还有一个新的口述注意点：当前TIM5主触发配置是TIM_TRGO_OC1，不能无证据说成UPDATE；安全表达是“TIM5通过TRGO逐点触发DAC”。

### 4.5 LCD SPI DMA链和白屏故障

发送链为：LCD绘制函数 → NSS/CS拉低 → RS/DC选择命令或数据 → HAL_SPI_Transmit_DMA启动 → DMA1 Channel3搬运 → DMA中断进入HAL处理 → HAL_SPI_TxCpltCallback → GiveFromISR二值信号量 → LCD任务恢复 → NSS拉高。

当前代码没有检查HAL_SPI_Transmit_DMA返回值，却无限等待完成信号量。如果启动返回BUSY或ERROR，完成回调可能永远不来，LCD任务永久阻塞且NSS保持低。

白屏排查必须分层：

1. 供电、背光和复位。背光亮只证明背光支路，不证明屏控制器初始化。
2. 检查NSS、DC、SCK、MOSI的引脚复用和静态状态。
3. 断点确认绘制和发送函数确实执行，记录HAL返回值。
4. 看DMA CNDTR是否递减、IRQ和完成回调是否到达、二值信号量是否给出。
5. 用逻辑分析仪按足够高采样率检查SPI模式、时钟、命令和数据。
6. 软件链正常后再查屏幕初始化序列和硬件屏体。

### 4.6 综合仪器当前验证状态

- 已由用户上板确认：Auto/One-Shot；AWG低频ARR与频率更新时序；频率切换立即生效；高频波形粗糙现象。
- 已确认未修：三角波实际为单调斜坡；共享波形数组存在撕裂设计风险。
- 仅代码修改、没有独立完整验证：形状或频率改变时避免无条件重复Restart。
- 尚未量化：DMM逐档精度和温漂、过量程边界、AWG模拟后级准确增益和截止频率、数字点数与模拟带宽各自贡献。
- 当前源码工作树有多处修改，不能把历史构建结果当成当前完整构建通过。
- 高频还有潜在中断负载：DAC DMA为循环中断式，半传输和全传输回调可能非常频繁；是否构成粗糙根因尚未量化。

## 5. 项目二：FreeRTOS智慧农场

### 5.1 定位、架构和任务

- 主控：STM32F103C8T6，72MHz。
- 系统：CMSIS-RTOS2封装的FreeRTOS；RTOS Tick为1000Hz，HAL另使用TIM3作为1ms时基。
- 目标：采集空气温湿度、土壤温度、土壤湿度、光照和雨滴板湿润度；与可编辑阈值比较；控制水泵和风扇；用OLED和BLE反馈。
- 软件结构应说“BSP驱动、应用任务/业务、共享状态”，不要把四个任务说成四层。

任务如下：

| 任务 | 优先级 | 职责与主要阻塞点 |
|---|---|---|
| Input | High | 10ms轮询按键和TIM1编码器；三按键低有效并二次确认 |
| Sensor | Normal | 采集、更新farmState、阈值判断、控制和告警；末尾osDelay(1000) |
| Screen | BelowNormal5 | RAM绘制、获取I²C互斥锁、整帧发送、osDelay(10) |
| BLE | Low | 队列为空时永久阻塞；取消息后UART DMA发送并轮询状态 |

Sensor的实际周期是“本轮采集和处理时间＋1000ms”，不是严格1Hz。若需要固定相位应采用绝对期限设计。

### 5.2 传感器链路

#### AHT20和OLED共享I²C1

AHT20与CH1116 OLED通过PB6/PB7共享400kHz硬件I²C1，使用互斥锁保护真实总线事务。互斥锁有所有者和优先级继承，适合任务间保护共享总线；不能在ISR中阻塞获取。

当前AHT20实现把发送命令AC 33 00、HAL_Delay(75)和接收6字节都放在持锁区。HAL_Delay是CPU忙等，不会把Sensor任务切成Blocked；Sensor仍在运行，Screen只有运行到Acquire失败后才进入Blocked。当前又没有检查I²C收发返回值，全零数据可能被解析成0%RH和−50℃。

正确改进方案是：获取锁并发送命令 → 释放锁 → osDelay约75ms → 再获取锁并接收数据 → 检查返回值、Busy位和量程 → 成功才发布新值 → 失败保留last_good并更新valid、timestamp和error。该方案仍未实现，不能说成已修复。

#### 三条ADC链

- 雨滴：PB1 → ADC1_IN9 → Rank1 → 循环DMA数组下标0。
- NTC：PA4 → ADC1_IN4 → Rank2 → 循环DMA数组下标1。
- 土壤湿度：PA0 → ADC2_IN0 → 连续转换 → HAL_ADC_GetValue读取最近一次结果。

ADC1是软件启动、连续扫描、DMA Circular；12MHz ADC时钟和239.5采样周期决定转换速度，不是外部定时触发频率。每通道约21µs，两通道一轮约42µs。

雨滴和土壤目前均先把ADC夹到4000，再用100−adc/40映射成0～100，只是相对湿润度显示，没有经过真实干湿标定，不能称为专业降雨量或土壤含水率。

NTC采用10k、B3950模型，理想比率公式为R = ADC / (4095−ADC) × 10k。若分压电阻和ADC参考同源，VDDA同时出现在分子分母中会抵消，因此结果主要依赖ADC比值、参考电阻和NTC模型，而不是绝对VDDA。ADC为0或4095附近必须做边界保护。当前工作树增加了阻值范围判断并越界返回0，但尚未编译、烧录和实测，而且0既可能表示故障也可能被误解为真实0℃。

#### OLED刷新

OLED为128×64，OLED_GRAM为8×128，共1024可见字节，不是双缓冲。RAM中排版无需持有I²C锁，只有真正ShowFrame传输需要锁。400kHz I²C下，加地址和ACK后整帧理论至少约25ms，再加10ms相对延时，最高约28.6fps；10ms延时不等于实际100fps。

### 5.3 共享数据、IPC与所有权

Sensor逐字段写farmState，Screen读取；Input修改farmSafeRange，Sensor和Screen读取。当前没有快照或版本机制，因此Screen可能读到跨两轮的组合。面试中可以提出“短临界区复制快照、双缓冲结构体或序列号一致性检查”，但不能说已经实现。

BLEQueue深度16，元素是char指针。正确所有权链为：

Sensor分配正文 → Sensor持有 → Put成功后逻辑所有权转交BLETask → BLETask Get成功后持有 → UART DMA期间BLETask必须保证缓冲区有效 → 发送完成或明确放弃后free → 内存回到heap_4。

Put失败时消息没有进入队列，仍归Sensor，必须立即释放。当前QueueBleMessageOrFree已经处理该路径，并由用户确认完成编译、烧录和上板验证。

事件、数据和资源保护要分开：

- 互斥锁：保护I²C所有权。
- 队列：保留每一条必须处理的报警消息及顺序。
- 二值信号量或任务通知：适合一次完成事件，不保存多条正文。
- 共享结构体：保存最新系统状态，但需要一致性策略。

### 5.4 控制与告警

- 水泵：PA12高有效。土壤湿度低于min时开启，达到min+5%时关闭，关闭阈值不超过max。5%滞回避免临界值噪声导致反复启停。代码、编译、烧录和用户上板验证均已完成。
- 风扇：空气温度高于上限时开启；TIM2_CH1，10kHz、85% PWM。
- 蜂鸣器：TIM4_CH4配置2kHz、20%；软件定时器设计每500ms翻转，对应完整响停周期1s。但当前Beep_on和Beep_off主体被注释，不能说本地蜂鸣告警当前已经启用。
- 告警消息：正常进入异常只发warning，异常恢复只发recovered，持续异常不每秒重复。边沿策略和用户上板验证已经完成。

### 5.5 UART DMA当前缺陷

USART3为PB10/PB11、9600 8N1、TX DMA1 Channel2。9600 8N1发送120字节约需要120×10/9600 = 0.125s。

当前BLETask没有检查HAL_UART_Transmit_DMA返回值。若上一条还在发送，本条调用返回HAL_BUSY，本条实际没有启动；代码却等待UART状态最终回到READY并释放本条缓冲区，因此主要结果是本条消息丢失。若状态永久BUSY，BLETask会持有当前指针并长期阻塞，后续队列累积；这不是严格意义上“指针已经丢失的必然泄漏”，但会导致内存长期占用甚至堆耗尽。

正确设计需要：检查HAL_OK/BUSY/ERROR；HAL_OK后等待真正Tx完成回调；BUSY采用有限等待或重入队策略；ERROR记录并恢复；所有退出路径只能释放一次；必要时用任务通知代替轮询。

### 5.6 智慧农场故障树

#### AHT显示0%和−50℃

记录发送返回、接收返回、原始6字节、Busy位 → 如果失败或全零仍被解析，软件有效性链已经定位 → 修复为成功且Busy清除才发布，否则保留上次有效值并标故障。

#### 手机没有收到告警

异常状态是否发生边沿 → malloc是否成功 → Put返回和队列深度 → BLE是否Get → HAL返回OK/BUSY/ERROR → Tx完成回调 → PB10波形 → 蓝牙模块和手机。持续异常第二秒不再发是当前正常策略，不能直接判断为丢包。

#### 水泵不转

把传感器置于明确干湿条件 → 测PA0模拟电压和ADC2原码 → 检查映射、farmState、阈值和滞回状态 → 检查PA12 → MOS/驱动、外部供电、共地、泵两端电压 → 负载、管路和真实出水。PA12能拉高只证明MCU控制端，不证明后级闭环。

#### OLED不亮

任务是否到达ShowFrame、互斥锁状态 → SCL/SDA是否有事务 → 地址是否ACK → 初始化序列、显存和屏体。供电和静态电平可用万用表，协议时序应使用逻辑分析仪。

#### 长时间运行后malloc失败

看当前和历史最小剩余堆、malloc失败计数、队列深度、Put/Get/free计数、BLE是否永久BUSY。Put失败泄漏已经关闭，但队列中最多16条动态正文仍会真实占用堆。

### 5.7 当前验证状态和禁区

- 已编译、烧录、用户上板：Put失败立即释放；warning/recovered边沿；水泵5%滞回。
- 未实现：AHT分段I²C事务、状态有效性、farmState一致性快照、UART DMA完整返回和完成语义处理、经验百分比实物标定。
- 仅工作树代码、未验证：NTC阻值范围判断。
- 当前禁用：蜂鸣器启动/停止主体。
- 不能说：HAL_Delay使Sensor进入Blocked；READY证明本条发完；GPIO高证明泵出水；free是“释放DMA”。

## 6. 项目三：低功耗LoRa传感器终端

### 6.1 项目定位、当前版本和贡献

- 主控：STM32F103C8T6，HSE 8MHz经PLL到72MHz。
- 架构：HAL裸机超级循环，不使用FreeRTOS。
- 目标：周期采集温湿度、光照和雨滴板相对湿润度，执行固定阈值判断，经本地状态输出或LoRa应用协议上报，然后进入RTC Stop低功耗；OLED只在现场按键查看时开启。
- RTC使用32.768kHz LSE形成1Hz计数。
- 用户可表述为独立完成需求、接口选择、Cube配置、驱动移植集成、应用逻辑、LoRa节点协议和调试；不要把所有底层库说成逐行原创。

当前源码基准已经更新为提交3d751c6。旧资料中“按键开屏、OLED供电/总线隔离、雨滴门控和双期限尚未实施”已经过时：这些功能现在已经写入源码，并存在默认与LoRaDebug两套成功链接产物；但没有新的烧录、实物门控、按键、RF和功耗验证证据。因此准确状态是“代码及构建完成，硬件待验证”。

### 6.2 传感采集

#### AHT20

AHT20与OLED共享I²C1的PB6/PB7，400kHz。当前实现检查I²C返回、Busy和量程；读取失败保留上一次有效值并用valid状态区分，不直接把错误数据发布。命令到读取之间需要约75ms测量时间。

#### BH1750

BH1750使用PA11/PA10 GPIO模拟I²C。当前仍为连续高分辨率0x10模式：首次测量等待约180ms，以后读取最近完成值；换算约为raw×10/12 lx。连续模式不是“每次读都重新启动ADC”，光电二极管、积分ADC和数字换算都在BH1750模块内部完成，MCU通过I²C读取数字结果。计划中的单次模式尚未修改。

#### 雨滴板

雨滴AO接PB1 / ADC1_IN9；ADC时钟12MHz、239.5周期、软件触发，每次上电稳定后做8次平均。干4095、湿0仍是占位标定值，只能得到相对湿润度，不是降雨量。

当前新增PB14作为雨滴高边电源开关的EN控制。PB14不能直接给传感器供电，而是控制外部开关。流程为上电 → 等20ms稳定 → ADC采样 → 断电。是否确实满足20ms、关断漏电和读数稳定性仍需实物测量。

### 6.3 按需OLED、总线隔离和双期限

- PC13为低有效上拉按键，下降沿EXTI；ISR只置事件，主循环执行约20ms消抖和状态切换。
- PB12控制OLED高边电源EN。
- PB13控制OLED专用I²C支路隔离EN，避免OLED断电时SCL/SDA通过保护二极管反向灌电。
- 开屏：打开电源 → 等10ms → 接通I²C支路 → 等1ms → 重新初始化控制器。
- 关屏：发送0xAE显示关闭 → 等1ms → 先断I²C支路 → 再断电。
- OLED默认关闭；按键打开后维持30s，只显示内存中最近一次缓存的数据，不主动强制进行新采样。

调度使用sample_deadline和display_deadline两个独立期限，系统睡到更早的一个，因此按键显示不会简单推迟采样。但下一次采样期限仍在一轮工作结束后按“当前RTC＋间隔”设置，所以周期包含本轮采集和通信时间，不宜称为严格10s或30s固定相位。

默认BLE构建采样间隔为5s。LoRa构建中传感正常约30s，传感失败或越界约10s；纯通信失败当前不改变休眠间隔。

### 6.4 RTC Stop原理和时序

完整主链为：唤醒 → 恢复系统时钟和SysTick → 按到期事件采集或更新显示 → 完成通信及必要外设收尾 → 计算采样、显示两个期限中的较早值 → 设置未来RTC Alarm → 清标志并进入Stop → RTC继续由LSE计时 → Alarm事件经EXTI17和NVIC唤醒 → 重新恢复HSE/PLL到72MHz和SysTick。

必须理解：

- Stop模式下CPU和大部分高速时钟停止，但备份域和RTC保持工作。
- 唤醒后不能假设系统自动回到72MHz；需要重新配置HSE、PLL和总线时钟，并恢复HAL Tick或SysTick。
- Alarm必须设置在未来，进入Stop前要正确清RTC、EXTI和NVIC相关标志，否则可能立即唤醒或永远不醒。
- 低功耗周期包括唤醒后的工作时间，因此“每隔30秒测一次”是否严格取决于期限是从上次目标时刻推进，还是从本轮结束重新加30秒。

### 6.5 LoRa软件协议和传输链

物理路径为：STM32 USART3 → 节点LoRa串口模块 → 空中RF → 网关LoRa模块 → USB转串口 → PC网关程序。ACK沿反方向返回。项目使用透明串口LoRa模块，自定义的是应用层帧和可靠性逻辑，不是LoRaWAN，也不是自行实现LoRa调制解调。

当前M0、M1、AUX使用PA8、PA9、PA1。USART3为PB10/PB11，9600 8N1，TX使用DMA。规划过的其他引脚没有进入当前实现。

上行帧18字节：

| 字段 | 字节数 | 作用 |
|---|---:|---|
| Magic | 2 | 帧头和重新同步 |
| Version | 1 | 协议版本 |
| Type | 1 | 消息类型 |
| NodeID | 2 | 节点身份 |
| Sequence | 2 | 序号、去重和ACK匹配 |
| Flags | 1 | 有效性或告警状态 |
| Temperature | 2 | 定点温度 |
| Humidity | 2 | 定点湿度 |
| Light | 2 | 光照 |
| Rain | 1 | 相对湿润度 |
| CRC16 | 2 | 完整性校验 |

多字节字段采用大端；CRC16-CCITT多项式0x1021、初值0xFFFF，覆盖前16字节。ACK为11字节，至少要匹配NodeID和Sequence，不能只因为收到11字节就认为成功。

本地发送可靠性的四层含义：

1. HAL_UART_Transmit_DMA返回HAL_OK：DMA发送被接受。
2. UART Tx完成回调：本地字节已经从UART发出。
3. AUX或模块状态：串口LoRa模块结束内部忙状态。
4. 收到并验证匹配ACK：网关确实收到了对应业务帧并回应。

当前整帧最多重试1次，即一共最多发送2轮；HAL_BUSY最多3次只是本地DMA启动尝试，不是3次无线重发。主要超时包括UART约500ms、AUX/模式切换约100ms、ACK约300ms。

PC网关已经实现串口流式拼帧、Magic重新同步、CRC校验、动态ACK、重复序号识别和CSV记录。重复帧应再次ACK，避免节点因ACK丢失继续重发，但不能重复执行同一业务。

### 6.7 低功耗节点故障树

#### 不进入Stop

在主循环各阶段记录最后成功点 → 查OLED I²C是否无限等待 → UART Tx完成是否到达 → AUX是否释放 → ACK等待是否超时退出 → RTC Alarm是否设为未来 → 是否执行到睡眠入口。

#### 进入Stop但不唤醒

RTC是否计数 → Alarm值是否在未来 → ALRAF是否置位 → EXTI17和NVIC是否使能/清标志正确 → 唤醒后是否恢复HSE/PLL和SysTick。

#### 收不到ACK

本地UART Tx完成 → AUX和模块模式 → 两端空中参数是否一致 → PC是否读到原始字节 → Magic、长度和CRC → PC是否发送ACK → ACK的NodeID与Sequence是否匹配。

#### OLED按键打开仍不亮

PC13中断事件 → 主循环消抖 → PB12电源 → PB13总线隔离 → 10ms/1ms稳定时序 → 重新初始化 → I²C ACK和数据。

#### 雨滴数据异常

PB14门控是否真正驱动外部高边开关 → 模块供电和20ms稳定 → PB1原始ADC → 8次平均 → 干湿实测标定 → 关断后的漏电和下次首样稳定性。

### 7.3 五路灰度主链

五个数字输入为PB24、PB20、PA27、PB19、PB18，依次归一化为0或1，再拼成bit4到bit0。拼接后的5位状态表示黑线相对车体的位置，而不是厘米距离。

已知映射：

| 状态 | 普通误差或动作 |
|---|---|
| 00100 | 0，居中 |
| 01100 | +2.3 |
| 00110 | −2.3 |
| 01000 | +7 |
| 00010 | −7 |
| 10000 | +20 |
| 00001 | −20 |
| 11000、11100 | 左转标志 |
| 00111、00011 | 右转标志 |

普通循迹链为：GPIO原始位 → 5bit状态 → Track_err误差 → 团队position_pid → 校正量 → left = base − out、right = base + out → 电机差速。正负方向是否对应左/右修正，最终必须用公式和上板运动共同确认，不能仅凭符号猜。

PID主要负责黑线附近的小幅连续误差修正。遇到明确的大转弯图样时，状态机切换到团队转弯流程，由MPU6050相对Yaw等条件判断约±70°转角，再回到普通循迹。不是“达到70°以后再用PID慢慢调”这么单一，而是先分类状态，再决定运行哪套控制逻辑。

### 7.4 1ms控制节拍

TIMA1频率约为80MHz ÷ 8 ÷ (255+1) = 39062.5Hz。LOAD为38表示计数39拍，因此周期为39 / 39062.5 ≈ 0.9984ms。

1ms ISR直接运行datafun；每10次还执行AHRS或测速相关逻辑，因此实际约10ms，不是源码注释写的100ms。OLED和按键位于主循环。面试中要说明1ms只是名义触发周期，真正实时性还取决于ISR最坏执行时间；可以用GPIO在ISR入口拉高、出口拉低，再用示波器测脉宽和抖动。

### 7.5 当前源码问题

## 8. 跨项目共通知识

### 8.1 RTOS和裸机

- 综合仪器：FreeRTOS原生API，以事件组、值邮箱和二值信号量组织显示链。
- 智慧农场：CMSIS-RTOS2包装FreeRTOS，以任务、互斥锁、消息队列和软件定时器组织业务。
- 低功耗节点：HAL裸机超级循环，使用RTC期限和中断事件，不存在RTOS任务调度。
- 电赛小车：TI DriverLib裸机，以高频定时中断加主循环构成控制结构。

CMSIS-RTOS2不是另一套调度器；在该工程里它调用下层FreeRTOS。HAL_Delay是忙等，osDelay或vTaskDelay会让当前任务进入Blocked并把CPU交给其他Ready任务。

vTaskDelay适合“从现在起延时”，周期会累积执行时间；vTaskDelayUntil以计划基准推进，适合固定节拍。若已经错过本周期，函数不会神奇补回执行时间，而会按API和当前Tick决定立即返回或推进到后续期限。

### 8.2 Tick、主频和时间片

- CPU 72MHz表示内核每秒时钟数量，不等于RTOS每秒调度次数。
- 综合仪器Tick 100Hz，即1 Tick = 10ms；智慧农场Tick 1000Hz，即1 Tick = 1ms。
- 时间片只在同优先级Ready任务之间轮转；高优先级Ready任务可立即抢占低优先级任务。
- 任务调用Delay或等待IPC进入Blocked后，不需要等自己的时间片耗尽。
- 如果没有其他Ready任务，运行Idle任务，而不是让已经Blocked的任务继续执行。

从ISR唤醒任务时，pxHigherPriorityTaskWoken表示“这次ISR操作是否让一个比被中断任务更高优先级的任务变为Ready”。它不是“中断是否成功”的标志。为pdTRUE时，应在ISR退出处请求上下文切换。

### 8.3 优先级反转和互斥锁

经典链：低优先级L持锁 → 高优先级H申请并阻塞 → 中优先级M抢占L → L无法释放 → H被M间接延迟。互斥锁的优先级继承会临时提升L，使其尽快完成临界区并释放锁；释放后恢复原优先级。它缓解有界反转，不意味着系统中永远不可能出现延迟，也不能替代短临界区。

二值信号量没有所有者，适合ISR到任务的完成通知；互斥锁有所有者和优先级继承，适合任务间资源保护，不应在ISR中阻塞获取。

### 8.4 DMA共同模型

DMA只按配置搬运，不理解业务、不计算物理量：

- 综合仪器ADC：ADC1 DR → DMA1 Ch1 → SRAM原始帧。
- 综合仪器DAC：SRAM波形表 → DMA2 Ch3 → DAC数据寄存器。
- 综合仪器LCD：SRAM图形块 → DMA1 Ch3 → SPI数据寄存器。
- 智慧农场ADC：ADC1 DR → 循环DMA两元素数组。
- 智慧农场和节点UART：SRAM消息 → DMA → USART发送寄存器。

外设只有一个固定数据寄存器时外设地址不递增；数组存储多个结果时内存地址递增。多通道ADC常规组仍可从同一个DR依次读，因为ADC按Rank把结果依次放到DR；注入组则有JDR1～JDR4。

### 8.5 定时器三种角色

1. PWM：比较计数值和CCR，直接形成占空比波形，驱动风扇、蜂鸣器或电机。
2. TRGO：定时器内部事件输出给ADC或DAC，决定转换节拍，本身不是模拟波形数据。
3. 编码器模式：两个正交输入接CH1/CH2，由相位关系决定计数方向和位移。

FreeRTOS软件定时器不是硬件定时器。到期回调在统一Timer Service任务中串行执行，因此回调必须短、不可阻塞；耗时业务应通知普通任务处理。

### 8.6 栈、堆和所有权

- FreeRTOS任务栈深度常以StackType_t字为单位；32位MCU上一字通常4字节。256字约1024字节，不是256字节。
- uxTaskGetStackHighWaterMark返回历史最小剩余栈字数，不是当前瞬时使用量。
- 栈溢出Hook应做最小、确定的保命动作，例如记录任务名、置安全状态、点故障灯并等待看门狗；不宜printf、动态分配或阻塞。
- 当前剩余堆表示此刻空闲，历史最小剩余堆表示运行以来最危险水位。
- 动态消息必须定义所有权转移点，并保证成功、失败、超时、重试、放弃每条路径恰好释放一次。

### 8.7 相对测量和绝对测量

如果传感电阻分压和ADC参考都由同一VDDA供电，ADC码本身代表比例，代入电阻公式后VDDA可抵消。例如NTC分压。若要恢复外部真实电压，或者信号经过独立偏置/比例网络，则需要知道ADC参考的绝对值，例如综合仪器DMM通过VREFINT反推VDDA。

雨滴板和电阻式土壤模块只能对本板局部导电性和表面水量给出相对响应，受安装位置、污染、盐分、温度、腐蚀和批次影响；没有标定时不能称为真实降雨量或体积含水率。

## 9. 通用故障诊断方法和工具教学

### 9.1 每一种工具能证明什么

| 工具 | 适合观察 | 不能单独证明 |
|---|---|---|
| 调试器 | 控制流、变量、寄存器、返回值、任务状态、断点 | 真实引脚波形质量、模拟带宽、对端物理接收 |
| 万用表 | 供电、直流电平、平均值、通断 | 高速SPI/I²C/UART时序、窄脉冲和抖动 |
| 示波器 | 模拟幅度、波形、上升时间、PWM、触发脉冲、ISR GPIO脉宽 | 复杂数字协议字段语义，除非结合解码 |
| 逻辑分析仪 | SPI/I²C/UART数字时序、地址、ACK、字节、片选 | 模拟完整性、过冲、真实电压精度、驱动能力 |
| 标准源/电阻箱 | DMM线性、档位、误差和温漂 | 软件时序、任务阻塞原因 |
| 电流表/功耗分析仪 | 活动、Stop、平均和峰值电流 | 功能是否正确，除非与状态日志联合 |
| GPIO打点 | ISR/任务区间和抖动 | 区间内部具体哪条语句耗时 |

AI讲一种验证方法时，必须把“工具目的、具体接法或操作、正常现象、异常结论、方法局限”讲完整。例如“看CNDTR”不能只说看它变化，还要说它从1024递减说明DMA接受到请求并搬运；不变化只能说明DMA没有搬运，仍需区分ADC没请求、映射错、通道没开或DMA没使能。

### 9.2 通用五层故障树

1. 输入层：供电、接线、原始模拟量或GPIO。
2. 触发层：定时器、EXTI、比较器、软件事件。
3. 转换和搬运层：ADC/DAC/SPI/UART寄存器、DMA计数和中断。
4. 软件发布层：回调、状态、邮箱、队列、事件组、所有权。
5. 输出层：屏幕、执行器、无线对端或上位机。

优先选能把链路一分为二的测点。例如AWG同时测PA4和最终输出；水泵先看PA12再看泵两端电压；LoRa先区分本地UART完成和匹配ACK。

### 9.3 故障回答常见失分点

- 只说“检查ADC、DMA、定时器”，不说检查哪个寄存器、引脚或返回值。
- 用调试器声称已经证明物理总线波形正常。
- 一开始就怀疑最复杂的原因，没有先检查供电、触发和原始数据。
- 修复后没有回归相邻功能、边界输入和长时间运行。
- 把暂时阻塞、消息丢失、内存泄漏、数据陈旧混成同一种故障。

## 11. 训练题目路由

正式题库共122道主问题，分为综合仪器、智慧农场、低功耗节点、电赛小车、跨项目、故障、FreeRTOS和行为题。AI不应每次从头顺序提问，应按用户当前目标抽取。

### 11.1 第一轮：四个项目30秒介绍

重点验收：项目定位、平台、核心功能、个人贡献、一个边界。任何一个介绍超过90秒或开始堆引脚，应要求压缩。

### 11.2 第二轮：四条代表主链

1. 综合仪器：比较器触发到1024点显示。
2. 智慧农场：传感采集到控制和边沿告警。
3. 低功耗节点：唤醒、采集、LoRa、ACK、Stop。
4. 小车：五路GPIO、状态分类、普通PID或特殊转弯。

### 11.3 第三轮：四个真实问题

1. 综合仪器：共享波形数组撕裂或SPI DMA死等。
2. 智慧农场：AHT持锁忙等、HAL_BUSY丢消息。
3. 低功耗节点：本地发送完成与端到端ACK、低功耗不进Stop。
4. 小车：转弯case未初始化error、00000/11111语义。

### 11.4 第四轮：跨项目追问

- 为什么DMM用VREFINT而NTC可以不使用？
- 三个项目中的DMA方向分别是什么？
- 硬件定时器PWM、TRGO、编码器模式和软件定时器有何区别？
- 事件组、值邮箱、消息队列、二值信号量和互斥锁怎样选？
- RTOS项目和裸机低功耗项目怎样保证周期与实时性？
- 如何证明UART消息真正送达？

### 11.5 第五轮：压力面试

连续追问“证据是什么”：

- 你说修复了，编译了吗？烧录了吗？怎样复现？
- 用什么仪器测？测点在哪里？正常值是多少？
- 这个功能是你写的还是团队接口？
- 如果返回HAL_OK但没有波形，你下一步看哪里？
- 你的改进带来什么代价？边界条件是什么？

## 12. 当前优先复测清单

AI应优先从这些仍容易混淆、又有面试价值的点出题：

1. 综合仪器1024点到225列的映射，尤其min/max保峰值。
2. TIM5 TRGO、DMA、DAC、RAM四者的数据方向和独立职责。
3. 综合仪器TIM5当前是TRGO_OC1，避免机械背成UPDATE。
4. 智慧农场HAL_Delay期间任务状态，以及AHT正确分段方案仍未实现。
5. UART HAL_OK、BUSY、READY、Tx回调和对端收到的四层语义。
6. 动态消息在Put失败、Get成功、DMA进行中和超时放弃时的所有权。
7. 低功耗节点新门控功能已经进入代码和链接产物，但尚未上板。
8. RTC Alarm唤醒链和唤醒后恢复72MHz、SysTick的原因。
9. 小车普通微调PID和特殊转弯状态机的先后关系。
10. 00000、11111和转弯图样为什么不能直接返回普通误差0。
11. 故障题中每一步的工具、测点、正常值、异常结论和局限。
12. 个人贡献、团队接口、参考代码、移植驱动的诚信表述。

已经较稳定的基础概念可以交叉抽查，不必连续重复：FreeRTOS四态、互斥锁优先级继承、ADC DR到DMA数组、UART 8N1按10位估时、水泵滞回、告警边沿。

## 13. AI反馈示例

用户若说：“定时器驱动DAC，DAC再让DMA把波形输出。”

应反馈：

- 🟢 知道定时器决定输出节拍，也知道DAC和DMA参与链路。
- 🔴 数据方向错误。DMA从RAM波形表搬到DAC数据寄存器；DAC接收数字码并转换为模拟电压，DAC不命令DMA去搬数据。
- 标准表达：“TIM5通过TRGO产生逐点转换节拍；每次触发时，DMA2 Channel3把RAM波形表的下一个数字码送到DAC数据寄存器，DAC完成数模转换并从PA4输出。”
- 变式追问：“如果TIM5 CNT在动，但DMA CNDTR不变，能证明什么，不能证明什么？”

用户若说：“HAL_Delay 75ms后Sensor进入阻塞，所以Screen能运行。”

应反馈：

- 🟢 知道75ms会影响其他任务。
- 🔴 HAL_Delay在当前实现中是忙等，Sensor保持Running并占用CPU；它不是osDelay，不会主动让出调度器。
- 标准表达：“当前AHT20在持有I²C互斥锁时调用HAL_Delay，Sensor任务持续占用CPU；正确方案是把发送和接收拆成两次短事务，中间释放锁并用osDelay进入Blocked。”

用户若说：“LoRa已经发送成功，因为UART DMA返回OK。”

应反馈：

- 🟡 只能证明本地DMA请求被接受。
- 标准表达：“HAL_OK只说明DMA启动请求被接受；Tx完成回调才说明本地UART发完，AUX释放说明模块结束忙状态，收到NodeID和Sequence匹配且CRC正确的ACK才是网关端到端确认。”

## 15. 最终训练原则

1. 先说结论，再说链路，再说设计理由，最后说问题和证据状态。
2. 每个模块都能画出数据方向、触发方向和通知方向，三者不要混淆。
3. 参数必须带单位，定时器必须检查PSC和ARR的加一。
4. 面试中的“我做了”必须能对应到个人职责和当前证据。
5. 故障排查不是猜原因，而是用测点不断缩小范围。
6. 未完成、未实测应准确说明；诚实不自动抵消岗位能力缺口，仍需补齐验证和相关知识。
7. 标准答案用于校正，不要求逐字背诵；最终目标是用户能用自己的语言稳定复述，并经得住连续追问。

### 16.2 国内求职场景与证据边界

本次目标是帮助正在求职的学生练好中文面试表达，默认从现有 STM32、MCU、RTOS 和项目调试经历入手。嵌入式岗位存在 MCU 固件、嵌入式 Linux、驱动/BSP、应用等差异；收到目标职位描述后再调整重点，不能因为岗位都叫“嵌入式”就要求相同知识。这里的默认方向是针对已有学习材料的训练选择，并非全国岗位占比结论。

国内企业的专业考察与综合沟通都值得准备。例如华为官方 FAQ 列有专业面试和主管面试；海康威视的校招页面建议学习行为面试法。乐鑫官方职业介绍涉及固件架构、驱动、RTOS、协议栈和跨团队协作。这些材料支持在技术表达之外练习经历说明和协作沟通，但不能推导所有企业使用相同流程、轮次或题目。[中1][中2][中3]

本指南把依据分成三种，训练师引用时必须保留区别：

- **企业一手说明**：可以说明该企业页面列出的流程或工作内容，不能当作整个行业的统计。
- **高校就业指导和实践报道**：可以支持方法建议或说明模拟训练确实被使用；活动感言不等于严格实验，不据此声称录用率提升。
- **本指南设计**：下面的压缩练习、角色切换、追问梯度、时间安排和评价表，是根据上述建议与用户目标制定的可试行方案，不是官方考试标准或经过验证的量表。

优先练习能观察到变化的行为：第一句是否回应问题、例子是否具体、是否讲清个人行动、追问后能否调整、换题后能否继续使用方法。暂不宣称“练多少天必然面试成功”。没有实测数据时，用测试条件、观察结果、代码位置或责任边界提供证据，不编造改善百分比。

| 录像与评语结合 | 四川农业大学实践报道介绍录像复盘和评委建议[中8] | 条件允许时观察自己的模拟表现，再与文字内容一起检查 | 专业与面试类型不同，仅借用反馈形式 |
| 清晰、简朴、认真倾听 | 珠海城市职业技术学院就业指导建议结构化回答、案例支撑与倾听[中9] | 先答所问，适时确认，不滔滔不绝 | 无须机械模仿某种语气或微表情 |

不把网页上的“高通过率”“表情占多少分”等营销数字纳入评分；没有研究出处的精确比例不采纳。不根据微表情猜测面试官是否喜欢候选人。服装、目光和音量以清楚、舒适、符合场合为准，允许个体差异。

### 16.4 八种可操作练习

本章是训练方案设计。每次选一到两种即可；推荐时间是练习预算，可按个人节奏调整。

#### 一句话先回答

**适用**：讲了很久却没有回答核心问题。AI问“你在这个项目中主要负责什么”，用户先用一句话回答，再补充两件具体工作。首句不放学校、全部元器件和项目历史。

**观察**：听完第一句，旁人能否复述你的主要职责。若不能，AI指出缺少的是职责、动作还是对象，让用户重说；不替用户编一整段经历。

#### 同一内容说长短两版

**适用**：冗长、舍不得删细节。先自然说90秒，再压缩成30秒；保留目标、个人动作和结果或边界，详细参数留给追问。随后换一种提问方式再答，防止只是背压缩稿。

**观察**：短版是否仍回答问题，是否删掉重复背景而非关键事实。没有音频或计时记录时，只判断信息取舍，不能声称实际超时。

#### 五个关键词脱稿

**适用**：看稿会说，离稿就断。只记“目标、职责、难点、行动、结果”五个提示词，先看词说，再移开提示说。AI之后打乱追问顺序，例如先问结果，再问为什么这样做。

**观察**：句子可以不同，但事实和因果一致。若只是措辞不同，不要求复刻范文。

#### 听题后澄清

**适用**：被模糊问题带偏。AI问“你这个系统性能怎么样”，用户先确认“您主要关注响应时间、功耗，还是稳定性？”再按确定维度作答。

**观察**：能识别真正需要澄清的条件。清楚的问题直接答，不每次机械复述题目。

#### 面向不同听众解释

**适用**：只会堆术语。向技术同事讲实现、条件和取舍；向HR讲用途、职责和成果；向非技术同学讲作用和一个类比。三个版本必须事实一致。

**观察**：听众能否说清“你做的东西有什么用”。类比只能帮助理解，不能替代真实机制或引入错误因果。

#### 连续追问但不攻击

**适用**：首答顺畅，被追问就慌。先问“你做了什么”，再从回答中选一项问“为什么”，最后问“怎样验证或有什么限制”。熟练后再加入方案替换或时间约束。

**观察**：能否针对新问题增加信息，承认未知并给出合理下一步。模拟严肃质疑，不辱骂、不贬低人格、不逼迫编造。

#### 录音中的一句修订

**适用**：口头禅、长句、指代混乱。回听30～60秒自己的模拟录音，选一句最难懂的原话。先识别“它”“这个”“然后”分别指什么，再改成两个短句，重新录一次。

**观察**：是否更容易理解，而非追求口头禅归零。正常停顿可以保留。AI只有实际收到可分析的音频时才评价声音；转写内容可能漏词，技术名词疑似错转时先确认。

#### 间隔换题复测

**适用**：刚改完会答，过后又乱。下次训练先用不同项目或日常情境复测同一种表达能力。例如昨天练项目汇报，今天练向同学说明活动延期。

**观察**：在没有范文提示时仍能先说结论并补证据。本指南建议下一次和之后隔几次训练复测，可随表现调整，不设固定的科学最优间隔。

### 16.5 八组面试表达示例与追问

以下均为本指南编写的教学示例，不是企业原题、真实录用答案或用户已发生的经历。方括号需替换成真实信息。涉及用户项目的现状，训练师另读最新记忆、正式题库和必要源码后确认；本章不重新认定项目已完成什么。

#### 示例一 自我介绍

**问题**：请简单介绍自己，以及为什么应聘嵌入式岗位。

**待改表达**：“我会C、STM32、串口、I2C、SPI，也做过很多项目，学习能力比较强。”

**问题所在**：列出了名词，却没有给对方留下一个可核实的能力印象。

**参考骨架**：“我是[学校专业]的应届生，希望从事[MCU固件等具体方向]。我在[项目]中负责[实际职责]，其中一个主要工作是[动作]，解决或定位了[具体问题]，证据是[实际记录或结果]。这段经历让我更关注[与岗位相关的能力]。我希望在贵司[JD中真实职责]上继续积累。”

**追问**：“你刚提到的工作，哪一部分最能体现独立思考？”讲评只检查岗位方向、个人行动和证据；不要求一次介绍四个项目。

#### 示例二 解释一个技术选择

**问题**：这个系统为什么采用RTOS？

**待改表达**：“RTOS比较高级，可以多任务同时运行，所以更快。”

**情境示例**：“这里有采集、交互和通信等不同节奏的工作。我希望它们的等待和响应更容易组织，所以考虑用任务和同步机制分开管理。不过RTOS也增加了栈空间和并发处理成本。是否更合适，要看响应要求和资源预算；功能简单时，裸机状态机也可能满足需求。”

这是一段设计理由表达示范，具体工程是否如此必须另核对。不要把示范自动变成“我的项目已证明更快”。

**追问**：“你说的响应要求具体是什么？如果不用RTOS，怎样组织？”重点练习需求、选择、代价和验证，而不是只背优点。

#### 示例三 故障排查

**问题**：串口通信时对端偶尔收不到数据，你会怎么办？

**待改表达**：“我会检查代码、DMA、中断、波特率，反正逐个排查。”

**情境示例**：“我先确认是对端没有收到字节，还是收到了但解析失败，并记录出现故障时的条件。随后比较发送端和接收端的观测，选择一个能缩小范围的测点。如果发送端没有预期输出，就回查发送请求和完成过程；如果线路有数据但对端不接受，就进一步检查双方配置和协议字段。拿到证据后再决定修改哪一层。”

**追问**：“第一步你准备用什么工具、看哪里？这个观察能排除什么？”具体寄存器、接口和正常值必须根据题设补充，不能用泛泛的流程获得技术满分。

#### 示例四 行为题与失败经历

**问题**：讲一次你处理困难或失误的经历。

**虚构教学情境**：“一次课程联调中，页面显示异常，我一开始直接改显示逻辑，没有先确认输入数据。我的任务是定位并恢复显示。我后来对比输入和显示前的数据，发现错误在前一环，随后修正并按原步骤回归。那次经历让我意识到，排查前应该先固定复现条件，再判断错误从哪一步出现。”

这体现STAR和反思，但不证明用户经历过此事。用户没有对应经历时，AI应通过询问真实课程、小组作业或日常事件提取素材，不借用虚构经历。

**追问**：“你自己做的关键动作是什么？如果再发生，你第一步会改成什么？”没有量化数据，也可以讲复现步骤和观察结果。

#### 示例五 与硬件同学存在分歧

**问题**：联调故障时，对方认为是软件问题，你认为是硬件问题，如何沟通？

**情境示例**：“我会先把共同目标确定为恢复功能，把观察事实和猜测分开。我把现象、配置和复现步骤给对方，再约定一个双方都能接受的测点和测试条件。根据结果一起缩小范围，必要时各自验证一段链路，再同步结果。”

**追问**：“如果双方仍有不同判断，你下一句话怎么说？”可以答“我们先用同一组输入比较这个测点的结果，再决定下一步”，避免把协作说成争论输赢。

#### 示例六 不会回答或没有测过

**问题**：你的节点实际续航多久？

**如果没有实测**：“目前我没有完整的续航实测，不能给确定天数。估算前需要知道电池可用容量和各状态耗电，特别是活动、休眠及唤醒的占比。我会先测整机各状态电流，再结合使用周期估算，并用实际运行验证。”

**追问**：“现在已有哪项证据，缺哪项？”未知可以诚实说明，但如果缺的是岗位核心能力，仍应记录为待补项；诚实不自动抵消能力缺口。

#### 示例七 求职动机和反向提问

**问题**：为什么选择我们公司？

**参考骨架**：“我关注到贵司[官网可核实的产品或业务]，这个岗位涉及[JD职责]。我已有[真实相关经历]，希望进一步学习[具体能力]。想了解新人通常先从哪个模块开始参与？”

可练习的反问：“新人前三个月主要交付什么？”“软件与硬件、测试团队通常如何协作？”“这个岗位更偏MCU固件还是Linux开发？”AI可以模拟回答，但要明确是虚拟公司设定，不能冒充目标公司内幕。

#### 示例八 面对被打断

**问题**：“这些背景我知道了，你直接说自己的贡献。”

**参考应对**：“好的，我主要负责两件事：[职责一]和[职责二]。其中最关键的一步是[个人动作]，对应结果是[证据]。”

重说时删去背景，从对方指定的层级继续，不从自我介绍开头重启。训练师观察的是调整能力，不以被打断本身判失败。

### 16.6 日常口才向面试迁移

以下为原创练习题，不是已核实的面试高频题库。一次选一题，先生活情境，再换成工程情境，检验同一能力能否迁移。

| 生活场景 | 工程场景 | 本轮只观察 |
| --- | --- | --- |
| 推荐一种通勤方式并解释原因 | 比较两种实现方案并做选择 | 有结论、依据与代价 |
| 向朋友解释今天做了什么 | 向面试官汇报一项项目工作 | 有具体动作，不只有活动列表 |
| 向室友说明公共物品故障 | 向硬件同事描述异常 | 区分现象、猜测和求助请求 |
| 解释小组活动延期及处理办法 | 说明任务风险与交付安排 | 先说影响，再说行动和所需协助 |
| 向非专业朋友解释一种技术 | 向HR说明项目价值 | 术语少而准确，能让对方理解 |
| 讨论一次意见不一致 | 讲一次接口或分工冲突 | 先理解对方，再用共同标准推进 |

可直接出题：“用一分钟说明今天最重要的一件事。”“推荐一种工具，但也说出它不适合的情况。”“同学临时改变方案，你怎样确认原因并表达不同意见？”

技术迁移题：“用三句话解释你负责的模块。”“你如何知道故障真的修好了？”“如果时间只剩一半，先保留什么功能，为什么？”“请用没有接触过单片机的人也能听懂的话介绍项目。”

## 18. 四项目技术重点与能力全景

### 18.1 技术价值如何判断

一项常见技术，只要能说明约束、选择理由、模块协作、异常路径和验证方法，就有能力展示价值。事件组、按键或数组本身很普通，围绕它们形成的按需刷新、输入状态机、数据所有权和实时性设计却值得展开。

按三种用途准备：已有实现作为项目技术事实；已修复并有证据的问题作为经历案例；未实施的分析作为追问和改进方案。理解第三方实现可以证明阅读和分析能力，不能直接证明原创开发能力。

#### 屏幕事件组：必须完整讲出的设计

九个区域为电源标签、DMM标签、发生器面板、运行模式面板、缩放面板、刻度标签、光标面板、波形面板、光标标签。它们是刷新请求，不是定时器，也不是九份数据。

典型路径：

- 测量更新：DMM计算→Overwrite结构体→请求DMM/电源标签重绘→LCD读取邮箱并画对应区域。
- 调整XScale：更改时基并设置采样率→请求缩放面板、刻度、波形、光标标签重绘。
- 调整光标：修改光标百分比→请求光标面板、波形和光标标签重绘。
- 波形采集结束：换算数组→请求波形重绘→LCD组合当前时基、刻度、触发阈值和光标参数调用绘图库。

xEventGroupWaitBits的pdTRUE/pdFALSE/portMAX_DELAY分别表示满足等待后清除所等待的已置位位、任意位满足即可返回、无事件时阻塞等待。返回的位集合应由多个if逐一处理。改成else-if会在本次多个位都已被清除的情况下只画一个区域，其他请求可能丢失，不只是“慢一点”。

同一个位在消费前多次置位会合并，适合“最终状态需要刷新”，不适合逐条不可丢的报警正文。若任务已经取走请求，绘制期间新置位的请求可以留到下一轮；事件合并不意味着所有时刻只画一次。多个区域顺序绘制也不是原子提交整幅屏幕，尚不能保证它们来自同一版参数快照。

官方和本地内核一致：xEventGroupSetBitsFromISR经xTimerPendFunctionCallFromISR将操作交给定时器服务任务。完整链应包含“ISR→定时器命令队列→服务任务置位→LCD就绪→调度执行”。其pxHigherPriorityTaskWoken通常对应被唤醒的服务任务，不能直接当成LCD唤醒结果。命令队列满时可返回pdFAIL，目前业务未检查。相比之下，SPI完成回调的GiveFromISR直接操作信号量。这是前期FromISR练习需要补上的具体API差异。

事件组不保护波形缓冲区，也不携带缓冲编号；xEventGroupSync是任务间屏障，不能放在ISR里等待显示任务。若进一步实现双缓冲，应明确FREE/FILLING/READY/DISPLAYING和丢帧策略，再选通知工具。

| 有限等待和重试 | BUSY最多3次启动尝试，整帧最多重试1次；UART/AUX/ACK分别有超时，超时发送需终止再返回 | 故障收敛、防永远耗电、栈上帧缓冲生命周期；当前函数仍有忙等/阻塞，并非全异步状态机 |
| 序号、ACK与重复消息 | 重发同一序号，网关识别重复仍回复ACK，并标记duplicate供业务处理 | 丢ACK场景、幂等意识；仅有NodeID/Sequence不自动解决重启/回绕/多节点接入 |
| PC流式网关 | 接收分段/连续多帧，找帧头，CRC失败后重新同步，动态ACK和CSV | 字节流处理、跨端调试、日志和可观测性；节点ACK接收仍是固定长度阻塞方式 |
| 测试与工程边界 | 7项主机测试含正确帧、CRC损坏、拆帧、粘帧、垃圾前缀、重复与CSV | 构造边界和回归测试；不等于C固件测试、双模块RF或功耗验证 |

平均电流应按完整周期的各阶段电荷求和再除以周期，包含唤醒、采样、显示、发射、ACK等待、重试和睡眠，以及板上稳压器/LED/模块。降低MCU睡眠电流未必带来同等整机收益。通信超时上限既是可靠性参数，也是最坏能耗参数；无线空中速率与UART波特率不是同一个数。

现有代码还有应据实说明的边界：最终SleepRadio返回值未处理，OLED I2C有无限等待风险，固定ACK读取缺重同步；默认BLE变体的部分返回值只被忽略。框架已有有限超时，不能进一步推断整个系统已经不存在卡死路径。

### 18.6 把前期疑问转化为能力证据

| 曾经讨论的问题 | 应建立的完整理解 | 对应能力 |
|---|---|---|
| 邮箱是否只传指针、事件组有何用 | 仪器是结构体值邮箱，农场是指针队列；数据、通知、资源锁、完成同步各有职责 | 正确选择IPC和数据语义 |
| 多个位同时置位、if还是else-if | 一次取回全部满足位后逐项处理；重复位合并；新的请求留下一轮 | 事件驱动UI与并发思维 |
| 1024点为何不是1024像素 | 采集深度/采样率/时间窗口/像素列各自独立；min/max保留峰值但不增加采样信息 | 采集与图形处理 |
| DR和CNDTR代表什么 | 数据寄存器与剩余传输数量；固定外设地址、递增内存地址；单项完整不等于整帧一致 | DMA配置与调试 |
| 事件组同步能否解决撕裂 | 通知不等于所有权；缓冲区状态必须禁止同时读写；ISR不能等待LCD | 并发协议与实时性 |
| 注入组为何不怕影响波形 | 必须分析ADC硬件抢占/重启和时间间隙，不能用“肉眼看不出”证明没有误差 | 测量时序和证据意识 |
| 100Hz与72MHz、Delay与DelayUntil | CPU时钟、Tick、外设触发、任务周期、刷新率不同；高优先级就绪不必等时间片 | 时间与调度推理 |
| task-woken究竟唤醒谁 | 看具体API实际解除谁的阻塞；事件组ISR委托服务任务与信号量不同 | 内核机制阅读 |
| 互斥锁和优先级继承 | 资源所有者、等待状态、继承触发和释放；不是避免全部优先级反转/死锁 | 资源竞争分析 |
| 指针丢了是否等于内存释放 | 变量寿命、分配对象寿命、逻辑所有权、DMA使用期分别判断 | C内存安全 |
| HAL_OK/READY/完成回调/ACK | 每个只能证明对应一层；失败要检查、收敛并保持缓冲有效 | 驱动到业务的可靠性 |
| 阈值附近抖动与报警洪泛 | 控制滞回、报警状态边沿、去抖和定期提醒解决不同问题 | 状态与控制设计 |
| 500k到底限制哪里 | ADC采样和DAC更新分别核对；信号频率、样本数、模拟带宽不同 | 性能预算与定位 |
| 关MCU为何还耗电 | 外设待机、无线、OLED、反向供电、稳压器和指示灯均参与 | 整机低功耗设计 |
| 全黑全白怎样交PID | 先解释图样含义和状态，再决定误差是否有效及控制策略 | 异常场景建模 |

### 18.7 本轮核对补充的风险与证据边界

1. 仪器cursor_panel.c的deltaY打印单位目前为s，实际电压差应为V；属于源码确认的单位错误，未修改。
2. 固定10ms Hold-Off不是DMA完成握手。在慢时基，例如ARR=56249、PSC=0时，采样率约1280Sa/s，1024点约0.8s；重新开放外部触发和100ms强制触发可能早于本帧完成。属于需要专项验证的重入风险，尚未复现实测。
3. 仪器main在创建/运行LCD任务前启动DMM等采集，事件组却在LCD任务内创建。需核验早期中断与高优先级KEY任务是否会在句柄初始化前访问；这是启动顺序风险，不是已确认必现崩溃。
4. 仪器LCD Reset里pdMS_TO_TICKS(1)在100Hz Tick配置下可能为0，不能把代码注释“延时1ms”当实测脉宽。
5. DMM短采样时间与VREFINT长采样是当前代码事实，是否满足具体模拟源建立时间需图纸/器件参数和测试；VREFINT名义值估VDDA不等于完整溯源校准。
6. 农场报警发送失败后仍更新边沿状态，可能丢失本次warning且不再自动重试；Put失败释放解决了内存泄漏，不保证报警最终送达。
7. 节点main注释“Stop期间SysTick仍计时会立即唤醒”不严谨：真正Stop时其高速时钟已经停，暂停Tick用于入睡/恢复过程避免不需要的节拍中断；唤醒恢复时钟后再恢复时间基准。
8. 本轮为源码阅读与技术归纳，没有重编译固件、运行硬件、RF或功耗测量。未修改任何唯一源码、原题库或飞书；新增分析不能当作旧实测结论。
