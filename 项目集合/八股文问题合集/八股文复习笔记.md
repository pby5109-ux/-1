## 一、C 语言与内存

### .data 段和 .bss 段分别叫什么？

**常见问法**：bss data 段；已初始化／零初始化数据放哪里？

**简答**：`.data` 是已初始化数据段，通常存放非零初值的全局和 static 变量；`.bss` 是未初始化／零初始化数据段，通常存放未显式初始化或初值为 0 的全局和 static 变量。典型 MCU 工程中，两者运行时都占 RAM，启动代码复制 `.data` 初值、清零 `.bss`。

**补充理解**：`.bss` 通常不在固件镜像中逐字节存储零，但仍占 RAM；实际归段由编译器与链接脚本决定，普通自动局部变量通常用栈或寄存器。

### 全局变量在哪里初始化？

**常见问法**：全局变量在哪初始化；为什么进入 main 时变量已经有初值？

**简答**：普通 C 全局变量通常由启动代码／C 运行时在 `main()` 前初始化：把 `.data` 的初值从 Flash 复制到 RAM，把 `.bss` 清零。具体代码可能在 `Reset_Handler` 或它调用的运行库中。

**补充理解**：C++ 还可能需要全局对象构造；特殊不初始化段和自定义启动流程另按工程规则处理。

### 内存映射外设寄存器是什么意思？为什么用 volatile？

**常见问法**：volatile 的作用与典型场景；内存映射寄存器是什么意思？

**简答**：volatile 表示对象可能被当前代码之外的因素改变，要求编译器保留实现规定的可观察访问，不能随意把它当成稳定数据优化。典型场景是内存映射外设寄存器，以及 MCU 中由中断修改、任务读取的简单标志。

**补充理解**：芯片将外设寄存器放进 CPU 地址空间，访问规定地址就是操作 GPIO、UART 等硬件，宽度和副作用须按手册。中断共享标志仍需保证访问原子性及正确同步；volatile 不保证原子性、互斥或内存顺序，也不能替代 CPU 屏障／Cache 维护。

### 结构体内存对齐是什么，为什么需要？

**常见问法**：结构体内存对其；为什么要结构体对齐；如何设置对齐？

**简答**：内存对齐让对象起始地址满足类型要求，适应 CPU 访问限制并提高效率。编译器会在结构体成员之间和末尾填充，使成员地址及结构体总大小满足对齐要求。默认按 ABI 布局，可调整成员顺序减少填充；`#pragma pack` 可限制对齐，C11 `_Alignas`／C++ `alignas` 可要求更严格对齐。

**补充理解**：假设 char 大小／对齐为 1、int 为 4，`char a; int b; char c;` 的偏移为 0、4、8，总大小为 12，尾部补齐保证数组下一元素也对齐；改为 `int b; char a; char c;` 通常为 8。`pack(1)` 可使前者为 6，但可能产生非对齐访问，影响速度或触发异常。用 `sizeof` 和 `_Alignof`／`alignof`核对；通信协议还须明确字段宽度和字节序。

### 大端和小端是什么，如何转换？

**常见问法**：大小段；大小段怎么转换（按大端／小端理解）；字节序是什么？

**简答**：大端是低地址放高有效字节，小端是低地址放低有效字节。`0x12345678` 从低地址到高地址，大端为 `12 34 56 78`，小端为 `78 56 34 12`。协议转换可按规定顺序通过移位与掩码逐字节序列化；必要时用字节交换或主机／网络字节序接口。

**补充理解**：转换字节序不是改变 CPU 本身的端序，也与栈向上／向下增长无关。单字节无需交换；32 位反转不能用于所有宽度。建议固定宽度类型，避免仅靠结构体指针强转解析。

### 内存分配有哪些方式？

**常见问法**：内存分配有哪些；堆和栈有什么区别？

**简答**：常见方式是静态存储、栈上自动分配和堆上动态分配。全局／static 对象通常长期存在；栈上局部对象通常随作用域结束失效，分配快但空间有限；堆对象按需申请、显式释放，生命周期灵活，但有管理开销、失败与碎片风险。内存池是预留内存上的分配管理策略。

**补充理解**：任务栈保存调用现场、局部变量与上下文；动态创建 FreeRTOS 任务可先从堆申请栈区域，再在其上运行。栈的增长方向由架构与实现决定。malloc/free、pvPortMalloc/vPortFree 等接口必须匹配，不返回失效局部变量的地址。

### 什么是内存池，适合什么场景？

**常见问法**：了解内存池吗；为什么通信缓冲区用内存池？

**简答**：内存池是提前准备一块内存并自行管理分配，嵌入式常用固定块池：按固定大小切块，申请时取空闲块，释放时归还。适合频繁分配、大小相近的消息或 DMA 缓冲区，分配时间更容易预测，也能减少外部碎片。

**补充理解**：例如准备 10 个 64 字节块，20 字节消息也占一个块，存在内部浪费；并非所有内存池都是固定块。多任务访问要同步，块大小、数量、对齐及 DMA 可访问性需规划。固定池机制见[Arm 文档](https://arm-software.github.io/CMSIS_6/main/RTOS2/group__CMSIS__RTOS__PoolMgmt.html)。

### 内存池、堆分配和栈分配有什么区别，哪个开销大？

**常见问法**：内存池和在堆栈中进行动态内存分配有什么区别；哪个开销大？

**简答**：典型栈分配只需调整栈指针，开销很小，但生命周期短且栈容量有限；固定块池可用空闲链表快速取还，通常开销低且可预测，但块大小固定；通用堆支持不同尺寸和生命周期，需要查找、分割／合并等管理，通常管理开销更大且可能碎片化。

**补充理解**：不能脱离分配器实现、同步和清零要求给绝对排名。内存池的底层区域也可以来自静态数组或一次堆申请；存储来源与分配策略是两个概念。

### 内存碎片有哪些，如何减少？

**常见问法**：RTOS 内存碎片化如何缓解；剩余堆够为什么申请失败？

**简答**：内部碎片是块内未用空间；外部碎片是空闲块不连续，总空闲量够却没有足够大的连续块。固定数量的对象优先静态分配；固定尺寸数据用内存池；复用缓冲区，尽量在初始化阶段完成长期分配，减少交错的变长申请／释放。

**补充理解**：20 字节数据占 64 字节池块会浪费 44 字节；两处不相邻的 40 字节空闲不能满足 60 字节连续请求。支持相邻空闲块合并的 heap_4／heap_5 可减轻外部碎片，但不保证消除；监测历史最小剩余堆与最大空闲块（实现支持时），检查失败返回。池可能内部浪费，调大堆也不能根治碎片。见 [FreeRTOS 内存管理](https://www.freertos.org/Documentation/02-Kernel/02-Kernel-features/09-Memory-management/01-Memory-management)。

### 字符串字面量能修改吗？

**常见问法**：`char *p = "abc"; p[1] = 'd';` 对吗？

**简答**：不对。在 C 中，p 指向字符串字面量，修改其内容是未定义行为；它常放在只读区域，可能触发异常。只读使用写成 `const char *p = "abc";`；要修改则用 `char a[] = "abc"; a[1] = 'd';`。

**补充理解**：C++ 中直接用 char* 接收字符串字面量也不符合现行语言规则。见 [C11 草案 §6.4.5](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)。

### 数组和指针的 sizeof 有什么区别？

**常见问法**：指针和数组有什么区别；int a[10]、int *p=a 的 sizeof？

**简答**：数组是同类型元素组成的连续对象；指针变量保存地址，所指类型决定解引用和指针运算。数组名在多数表达式中转为首元素指针，但数组本身不是可改指向的指针变量。sizeof(a)=10*sizeof(int)，sizeof(p) 是指针自身大小；常见 32 位 MCU ABI 下分别为 40 和 4。

**补充理解**：sizeof 真数组不会让它退化；作为函数参数声明的数组会调整为指针，函数内 sizeof 该参数得到指针大小。不能仅凭“32 位”认定所有类型大小；指针加一与 &a+1 的区别见本分区对应题。

### a+1 和 p+1 相同吗，指针加一是什么意思？

**常见问法**：`int a[10]; int *p = a;` 后，a+1 与 p+1；数组名与普通指针区别？

**简答**：在 p 仍等于 a 时，a+1 和 p+1 都指向 a[1]。指针加 1 是前进一个所指类型的元素，int* 前进 sizeof(int) 字节，不是固定前进 1 字节。

**补充理解**：数组名在多数表达式中转换为首元素指针，但数组不是可重新赋值的指针变量；p 可以改指向，不能写 a=p。`&a+1` 跨过整个数组；运算必须在有效数组范围或其尾后位置内，尾后指针不能解引用。

### 如何声明返回 int*、参数为两个 int 的函数指针？

**常见问法**：声明一个函数指针，返回值是 int*，参数是两个 int？

**简答**：写作 `int *(*fp)(int, int);`。`(*fp)` 表示 fp 是指针，后面的 `(int, int)` 表示指向的函数参数，最前面的 int* 表示返回类型。

**补充理解**：可用 `typedef int *(*FuncPtr)(int, int);` 简化声明。调用前必须指向类型匹配的有效函数；返回指针所指对象的生命周期也必须有效。

### strcpy 的源和目标相同，有问题吗？

**常见问法**：`char a[]="abcd"; char *b=a; strcpy(a,b);` 是否安全？

**简答**：有问题。b 与 a 指向同一存储区，源和目标重叠，调用 strcpy 是未定义行为；这题并不是目标容量不足，因为数组 a 有 5 字节，包含结尾的 \0。

**补充理解**：字符串复制还需检查目标容量是否包含结尾 \0。重叠搬移用 memmove 并给出正确字节数；完全相同的地址通常无需复制。见 [C11 草案 §7.24.2](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)。

### 指针可以直接赋值为整数或固定地址吗？

**常见问法**：`int a[10]; int *p=a; p=10;`；`int *p=0xB...;` 可以吗？

**简答**：将非零整数直接赋给指针不满足标准 C 的赋值约束，需要编译器诊断；即使显式转换为指针，也不代表能安全解引用。`p=10` 改的是地址，不是数组元素；要写首元素应写 `*p=10`。

**补充理解**：MCU 固定地址访问应按芯片头文件或手册，使用实现支持的整数到指针转换，确保地址映射、对齐、宽度和权限正确；外设寄存器通常带 volatile。数组的存储位置不能像普通指针那样重新赋值。0／NULL 的空指针情形与非零整数不同。

### sizeof 和 strlen 有什么区别，什么时候计算？

**常见问法**：sizeof／strlen 的含义、是否包括 \0、编译期还是运行期？

**简答**：sizeof 是运算符，返回类型或对象占用的字节数；strlen 是库函数，计算字符串到首个 \0 前的字符数，不包括 \0。固定大小类型的 sizeof 通常是编译期常量，不求值其表达式操作数；strlen 按字符串内容计算，通常在运行时扫描，编译器也可优化常量结果。

**补充理解**：`char a[]="abc";` 时 sizeof(a)=4、strlen(a)=3。对 char* 做 sizeof 得到指针大小，strlen 仍看其所指字符串；须保证指针有效且范围内有终止符。C 中可变长数组相关 sizeof 可能在运行时求值，不能说 sizeof 永远在编译期完成。

### memcpy 和 memmove 有什么区别？

**常见问法**：内存复制重叠怎么办；哪一个允许重叠？

**简答**：两者都按指定字节数复制，不依赖字符串结束符。memcpy 要求源、目标不重叠，重叠时行为未定义；memmove 允许重叠，效果如同先复制到临时区域再写目标，实现可通过选择复制方向完成。

**补充理解**：例如数组内部移动一段数据应使用 memmove；二者都不替你检查容量。不能仅用“memcpy 更快”概括所有实现。见 [C11 草案 §7.24.2](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)。

### malloc 和 calloc 有什么区别？

**常见问法**：动态内存申请是否清零；与 FreeRTOS 内存接口有什么关系？

**简答**：malloc(size) 申请 size 字节，不初始化内容；calloc(n,size) 为 n 个元素申请空间，并将分配区所有位清零。两者成功返回指针，失败返回 NULL，使用后配套 free；申请失败检查和所有权管理都不能省略。

**补充理解**：计算数组分配尺寸须防止乘法溢出，并避免依赖零大小申请的特殊结果。FreeRTOS 的 pvPortMalloc／vPortFree 是另一组配对接口，不能默认申请后清零或与标准库 free 混用。见 [C11 草案 §7.22.3](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)。

### 内存泄漏、野指针和悬空指针是什么？

**常见问法**：内存泄漏与无效指针怎么区分？

**简答**：内存泄漏是动态内存已申请却未正确释放，或丢失最后一个管理它的指针；野指针常指未初始化或指向无效／未知位置的指针；悬空指针指向生命周期已经结束的对象。术语“野指针”使用范围可能包含悬空指针，重点是无效访问。

**补充理解**：例：malloc 后直接覆盖指针会泄漏；未初始化 int* 就解引用是野指针；free 后继续访问，或函数返回局部变量地址，是悬空指针。明确所有权、初始化指针并匹配释放；释放后将一个指针置 NULL 不会修复其他别名。

### static 关键字的作用是什么？

**简答**：函数内的 static 局部变量具有静态存储期，整个程序运行期间存在，多次调用保留值，但名字的作用域仍是所在代码块；文件作用域的 static 变量和函数具有内部链接，只能由本翻译单元直接通过该名字访问。未显式初始化的 static 对象默认零初始化。

**补充理解**：static 不表示常量，也不保证多任务访问安全。C 中静态存储期对象的初始化发生在程序启动阶段，不应套用 C++ 局部静态对象“首次经过时初始化”的规则。

### inline 的作用是什么？

**简答**：inline 是函数说明符，建议编译器将函数体展开到调用处，以减少调用开销，适合短小且频繁调用的函数；是否展开由编译器决定，普通函数也可能被展开。过多展开可能增加代码体积。

**补充理解**：它仍是函数，有类型检查；与宏不同，参数按函数调用语义求值。C 头文件中的小工具函数常写 static inline；普通 inline 的外部定义规则要结合 C 标准和工具链，不能照搬 C++。见 [GCC inline 说明](https://gcc.gnu.org/onlinedocs/gcc/Inline.html)。

### 结构体和联合体有什么区别？

**简答**：struct 各成员有各自的存储位置，可同时保存不同字段，大小包含成员和对齐填充；union 各成员共用同一块存储空间，大小足以容纳最大成员并满足对齐，适合一个对象在不同状态保存不同类型的数据。

**补充理解**：union 写入一个成员可能覆盖其他成员的表示，不能认为各成员值同时有效；推荐配合类型标签使用。不宜靠读另一个成员完成可移植的协议解析，应考虑字节序、布局和类型表示。

### 链表和数组有什么区别？

**简答**：数组元素连续存放，按下标访问为 O(1)，缓存局部性好，但中间插入／删除通常要移动元素；链表通过指针连接节点，不要求连续内存，查找通常为 O(n)，有额外指针开销。已找到节点且具备必要链接时，链表插入／删除可为 O(1)。

**补充理解**：单链表删除一般还需前驱节点，寻找前驱可能为 O(n)。嵌入式可用静态节点池管理链表，链表不一定需要 malloc。

### 如何删除链表中的一个节点？

**简答**：单链表先找到待删节点及前驱，让前驱的 next 指向待删节点的 next；若删头节点则更新头指针。双链表还需更新后继的 prev，并按实现维护尾指针／哨兵。最后按节点来源释放或归还节点池。

**补充理解**：先保存后继再释放，释放后不能继续访问；空表、找不到、头尾节点都需处理。只有动态申请且由本模块拥有的节点才配套 free，静态节点不能 free；多任务操作应保护整段链表修改过程。

## 二、MCU 启动、中断与低功耗

### MCU 从上电到 main() 的启动过程（Cortex-M）

**常见问法**：系统上电到 main 函数的过程；main 前做了什么？

**简答**：上电复位后先确定启动源，CPU 从启动向量表读取初始 MSP 和复位入口，进入 `Reset_Handler`；启动代码完成必要系统初始化和 C/C++ 运行环境初始化，包括复制 `.data`、清零 `.bss` 及必要构造／库初始化，最后调用 `main()`。

**补充理解**：不一定先运行 Bootloader；若启动引导程序，则按其流程交接应用。`SystemInit` 与数据初始化顺序随工具链变化，完整应用时钟配置也可能在 main 中完成。口诀：选启动源 → 取栈和入口 → 系统与变量初始化 → main。

### 为什么用中断？查询与中断的区别（面试）

- 轮询：CPU 主动检查外设状态；中断：事件满足条件后提出中断请求，CPU 响应并进入 ISR，处理后恢复被打断的流程。
- 中断适合串口接收等异步事件，减少持续查询，让 CPU 处理其他工作或休眠。
- 忙等轮询占 CPU；周期轮询不一定忙等，但响应取决于检查间隔，可能因缓冲区溢出或短暂事件而丢失数据/事件。
- 中断有保存/恢复上下文的开销，并带来优先级和共享数据并发问题；高频事件可结合 DMA 或轮询，不能一概认为中断更好。
- ISR 尽量短：按硬件要求读取/保存数据、处理标志、通知任务；复杂解析放任务或主循环。中断延迟受屏蔽和高优先级中断影响。

### MCU 休眠功耗如何判断是否合理，异常怎么排查？

**常见问法**：休眠电流如何判断；为什么比手册高？

**简答**：先区分 MCU 芯片电流与整板电流，核对实际休眠模式、供电、温度、RAM／RTC／外设保留状态，与数据手册同条件比较。测电流波形确认真正进入睡眠，区分稳定底电流、周期唤醒脉冲与平均电流。

**补充理解**：按模块断电或最小固件逐项排查：调试器、指示灯、稳压器静态电流、外设未睡眠、GPIO 悬空／电平冲突、引脚反向供电、时钟未关闭、Tick 或其他中断频繁唤醒。普通万用表可能漏看尖峰或产生负担电压；FreeRTOS 可评估 Tickless Idle，但仍须验证硬件确实进入预期模式。GPIO 设置结合 [ST AN4899](https://www.st.com/resource/en/application_note/an4899-stm32-microcontroller-gpio-hardware-settings-and-lowpower-consumption-stmicroelectronics.pdf)。

### 系统低功耗设计可以从哪些角度入手？

**常见问法**：嵌入式低功耗怎么做；只降低主频够吗？

**简答**：从硬件选型、运行时序、外设控制和测量验证共同入手：选低静态电流器件／电源；按需开关传感器和无线模组；事件驱动、批量处理，缩短活跃时间并选择合适休眠模式；按实际负载配置时钟，必要时用 DMA 和 Tickless Idle，处理 GPIO 与唤醒源。

**补充理解**：按完整工作周期计算平均功耗及唤醒／通信开销，同时保证响应时间和数据不丢失。降频可能使处理时间更长，不能只看瞬时电流；确认关闭外设后无引脚反向供电。休眠模式、保留资源、恢复时钟和唤醒时延都按芯片手册，最终测整板电流波形与能量。

## 三、进程、线程与通信

### 进程与线程是什么，有什么区别？

**常见问法**：进程线程区别；进程和线程一般用在哪些地方？

**简答**：进程通常是资源分配与隔离单位，拥有独立虚拟地址空间；线程是进程内的执行与调度单位。同进程线程共享代码、全局数据和堆，各自有栈、寄存器上下文及线程局部存储。线程通信方便、切换通常更轻量，但共享数据需同步，错误可能破坏整个进程。

**补充理解**：具备进程隔离的操作系统可用独立进程运行程序或服务；同一程序内的界面、通信、计算可用线程分工。常见 MCU FreeRTOS 任务更接近线程，通常共享地址空间，各有栈；MPU 可增加保护，不等同于完整进程模型。单核轮流调度，多核可并行。

### 各项区别的简单示例

| 项目 | 示例 |
|---|---|
| 一个进程多个线程 | 一个播放器进程中，界面线程响应按钮，解码线程处理音视频 |
| 地址空间 | 两个进程即使变量地址相同，也通常对应不同内存；同进程线程可访问同一个全局变量 |
| 共享资源 | 采集线程写共享缓冲区，显示线程读取；需保证数据一致 |
| 独立栈和上下文 | 两个线程各自调用函数并保存自己的局部变量，切换后各从原执行位置继续 |
| 通信 | 进程间可用管道传数据；线程间可用共享缓冲区配合信号量 |
| 创建和切换 | 常规同进程线程切换主要恢复执行上下文；进程切换通常还涉及地址空间切换 |
| 故障影响 | 一个线程越界可能破坏本进程其他线程数据；独立进程的内存隔离通常可保护另一进程 |
| FreeRTOS 对应 | 串口任务与显示任务各有栈，但可共享同一个全局数组 |

### 进程间通信有哪些？

**常见问法**：进程间通信哪些；IPC 常见方式及适用场景？

**简答**：常见有管道／命名管道、消息队列、共享内存、信号量、信号和 Socket。管道传字节流，消息队列传消息，共享内存共享大块数据；信号量主要做同步，信号主要通知事件；Socket 可用于本机或网络通信。

**补充理解**：这是通用进程模型下的通信方式，不代表普通 FreeRTOS 任务有独立进程空间；MCU 任务间常用队列、通知、信号量和共享缓冲区。共享内存仍需同步和生命周期管理。

### 共享内存通信是什么用法？（MCU/FreeRTOS）

**常见问法**：共享内存怎么通信；多任务访问共享资源如何避免数据竞争？

**简答**：多个任务、中断或 DMA 通过同一块 RAM 交换数据，全局缓冲区也属于共享内存。任务间可用互斥锁保护完整读改写过程；极短操作可用适用的临界区或原子操作；通过队列、单一资源管理任务或明确所有权，减少同时修改同一对象。

**补充理解**：例：UART DMA 写缓冲区，完成后通知解析任务；数据在缓冲区，通知表示就绪。双缓冲／环形缓冲区要保证读期间不覆盖，指针队列只传地址，生命周期由使用者管理。锁顺序一致，持锁时间短，原子操作不自动保护整个结构体；ISR 不能用任务互斥锁，volatile 不能替代同步。带 Cache 平台还需 DMA 一致性处理。

### 零拷贝为什么叫零拷贝，MCU 中怎么理解？

**常见问法**：零拷贝是什么；原先怎么拷贝；DMA 或指针队列算什么？

**简答**：核心是减少或避免传输路径中多余的 CPU 数据复制。普通流程可能是接收缓冲区→中间缓冲区→处理缓冲区，多次 memcpy；优化后让生产者、消费者直接复用同一缓冲区，只传指针和长度。

**补充理解**：MCU 示例：UART DMA 直接接收到池块，完成后通过指针队列交给解析任务。DMA 仍在搬运数据，硬件读写不会凭空消失；指针队列仍复制指针。关键是管理所有权、生命周期，避免覆盖，并按平台处理缓存一致性。

### 用 UDP 实现可靠通信，需要哪些机制？

**简答**：应用层增加报文序号、ACK、超时重传和有限重试；接收端去重，按需求处理乱序；明确报文长度、完整性校验与会话标识，防止旧报文混入。通过窗口／限速、退避与拥塞控制避免重传加剧网络堵塞，超限应上报失败。

**补充理解**：ACK 丢失会导致重复发送，因此业务处理也需去重或保证幂等。可靠是协议目标，不代表断网时仍保证交付；分片、缓存容量和超时要有边界。见 [RFC 8085 UDP 使用指南](https://www.rfc-editor.org/rfc/rfc8085)。

### 组播和广播有什么区别？

**简答**：广播把报文发给广播域内所有主机；组播把报文发给加入指定组的接收者，适合一对多发送。IPv4 支持广播和组播；IPv6 使用组播，不提供广播。

**补充理解**：广播一般不跨路由器传播，组播跨网段需要网络设备支持。以太网交换机未启用组播监听时可能泛洪组播帧，但接收范围的协议语义仍不同。

### 怎样判断发出去的是广播报文？

**简答**：抓包看目标地址，分清 IP 层与以太网层。IPv4 的 255.255.255.255 是受限广播；子网广播地址要按子网掩码计算，例如 192.168.1.0/24 的广播地址为 192.168.1.255。以太网广播目标 MAC 是 FF:FF:FF:FF:FF:FF。

**补充理解**：不能只看最后一段是 255 就认定 IP 广播。ARP 请求常以广播 MAC 发送，但它不是 IPv4 数据报；确认自己发送的报文应同时检查协议、目标地址和负载。

## 四、FreeRTOS

<a id="tasks"></a>

### 一、任务与任务通知

#### 创建任务时 pvParameters 可以传什么？

- pvParameters 是 void*，用于将一个参数指针传给任务入口；任务内转换回正确类型后使用。
- 可以传配置结构体、设备上下文、缓冲区描述等的地址；多个参数封装成一个结构体；不需要参数时传 NULL。
- 内核保存并传递指针值，不自动复制其指向的结构体或缓冲区。
- 数据须在任务使用期间有效；推荐生命周期足够长的全局/static 对象，或明确管理的动态内存。不要传随后返回函数内普通局部变量的地址。
- 多任务共享该对象时仍需考虑并发保护；void* 不能消除生命周期或数据竞争问题。
- 不要混淆 xTaskCreate 的 pvParameters（输入给任务）与 pxCreatedTask（输出任务句柄）。

#### 任务通知只能在任务之间传一个信号吗？

- 不只能任务间：任务或 ISR 都能通知指定任务，ISR 必须用 FromISR 接口。
- 可用于唤醒、计数、设置事件位，或传递一个 32 位值；语义由发送动作和接收方式决定。
- 常见搭配：xTaskNotifyGive / vTaskNotifyGiveFromISR → ulTaskNotifyTake；xTaskNotify / xTaskNotifyFromISR → xTaskNotifyWait。
- 每个通知槽属于一个接收任务；可有多个发送者，但一次通知不广播给多个任务。
- 通知存放在 TCB 中，无需单独创建对象；不是消息队列，不能默认缓存多条独立数据，覆盖/计数行为需按模式选择。
#### FreeRTOS 是什么，面试怎么简要介绍？

**常见问法**：了解 FreeRTOS 吗；相比裸机有什么作用？

**简答**：FreeRTOS 是面向 MCU 等嵌入式平台的实时内核，提供按优先级调度的任务、队列、信号量／互斥锁、事件组、任务通知和软件定时器。它便于把采集、通信、显示等功能分成任务，通过同步机制协作。

**补充理解**：实时性关注能否满足期限，不是单纯“运行更快”；仍需合理设计优先级、阻塞时间、中断和资源使用。按真实项目说明任务分工、通信方式和一次问题定位，不把读过文档写成用过。见 [FreeRTOS 官方介绍](https://freertos.org/Why-FreeRTOS/What-is-FreeRTOS)。

#### 任务上下文切换如何发生？

**常见问法**：什么是上下文；FreeRTOS 任务怎样切换？

**简答**：任务阻塞、主动让出，或更高优先级任务就绪等事件，可使调度器选择下一任务；同优先级任务还可能按配置时间片轮转。切换时保存当前任务的寄存器与栈指针等执行现场，再恢复下一任务，让其从之前位置继续。

**补充理解**：常见 Cortex-M FreeRTOS 移植借助 PendSV 完成切换，异常硬件压栈和移植代码共同保存／恢复现场；不是每个 Tick 都必然切到别的任务，也不会复制整个任务栈。切换耗时随架构、FPU、配置变化。见 [FreeRTOS 上下文切换说明](https://library.freertos.org/Why-FreeRTOS/FAQs/Memory-usage-boot-times-context)。

#### RTOS 任务优先级设计遵循哪些原则？

**常见问法**：任务优先级怎么定；20 个任务如何排序；为什么数据采集任务优先级较高？

**简答**：以截止期、允许响应延迟、最坏执行时间和任务依赖为依据，及时性要求高的采样／控制等通常较高，显示／日志等后台工作通常较低；同时评估 CPU 负载和共享资源阻塞，验证最坏响应是否满足期限。高优先级任务应短、可等待事件，给其他任务和 Idle 留出时间。

**补充理解**：周期短优先是特定假设下的调度方法，不是所有工程通则；不能把任务全设为最高优先级。FreeRTOS 任务优先级一般数值越大越高，不能与常见 Cortex-M 中断优先级的数值规则混淆。用运行时间、延迟和压力测试验证，不只凭经验。

**本轮补充**：先列出 20 个任务的触发方式、周期／截止期、最坏执行时间、允许抖动和资源依赖，再按紧迫程度分层；相近要求可共用优先级，不必设 20 个不同等级。采集任务较高是为及时取走数据、控制采样间隔、避免硬件缓冲溢出；若定时器／DMA 已保证采样并有足够缓冲，后续处理不一定高于有更严期限的控制任务。关键看期限和最坏延迟，不能仅按任务名称排序。

#### 任务饥饿是什么，怎样避免？

**常见问法**：为什么低优先级任务不运行；taskYIELD 能解决吗？

**简答**：任务长期得不到 CPU 或所需资源，导致工作无法推进，称为任务饥饿。单核固定优先级系统中，高优先级任务持续就绪、忙等轮询、过高负载，以及过长 ISR／临界区等都可能使其他任务难以运行。优先让任务阻塞等待队列／通知或按合理周期运行，限制处理量并调整优先级和资源策略。

**补充理解**：普通事件等待不等于饥饿。高优先级任务一直就绪时，taskYIELD 不保证让低优先级任务运行；轮转时间片也不自动照顾低优先级任务。监测各任务运行时间与 Idle 是否能运行，结合事件是否送达区分饥饿、死锁和等待。见 [FreeRTOS taskYIELD 说明](https://www.freertos.org/media/2018/FreeRTOS_Reference_Manual_V10.0.0.pdf)。

#### 如何结束一个任务（线程）？

**常见问法**：结束线程有哪些方式；怎么终止（按 MCU／FreeRTOS 任务解释）？

**简答**：优先协作退出：通过通知／队列发送停止请求，任务在安全位置停止业务，结束或交接 DMA 等异步操作，释放自己持有的资源与锁，然后调用 vTaskDelete(NULL) 自删除。也可用 vTaskDelete(handle) 删除其他任务，但必须先确认其已安全停止。

**补充理解**：开启 INCLUDE_vTaskDelete；任务入口不能直接 return。删除不会自动释放任务业务代码申请的内存或持有的互斥锁。动态创建任务自删除后，栈和 TCB 的回收由 Idle 完成，要保证 Idle 能运行；静态创建任务的用户缓冲区不能交给内核 free，复用须确认清理完成。暂停／阻塞不等于终止。见 [FreeRTOS 任务生命周期](https://github.com/FreeRTOS/FreeRTOS-Kernel-Book/blob/main/ch04.md)。

#### RTOS 任务频繁响应超时，如何排查？

**简答**：先明确从哪一事件到哪一动作的期限，用时间戳或 GPIO 测量“事件产生→ISR→任务就绪→任务运行→处理完成”。检查中断屏蔽和长 ISR、高优先级任务持续运行、CPU 负载、锁等待／优先级反转、队列积压、I/O 阻塞，以及超时单位和事件丢失。

**补充理解**：区分调度等待、资源阻塞、业务执行和外设等待，再针对原因缩短 ISR／临界区、拆分耗时处理、用 DMA／缓冲、调整任务周期／优先级或容量。用最坏负载复测；不能只调高优先级或放宽超时来掩盖问题。

### 二、队列

#### FreeRTOS 队列是值拷贝吗？

- 是。发送时把单项数据复制进队列，接收时再复制到接收缓冲区；大小由创建时的 uxItemSize 决定。
- 发送成功后修改原变量，不影响队列中的副本；失败则没有成功入队，需检查返回值。
- 若单项为指针，只复制指针值，不复制指向的数据；传 &ptr，接收也传 &ptr。
- 指针指向的数据必须保持有效，并约定谁修改、谁释放，避免悬空指针或并发修改。

#### xQueueReceive 是读取队列头部吗？

- 是。成功时将队列头部的一项数据复制到接收缓冲区，并从队列中移除该项。
- 这里的头部是下一项待取数据，不是 Queue_t 控制头。
- 常规 xQueueSend / xQueueSendToBack 从尾部入队，配合 Receive 形成先进先出。
- xQueueSendToFront 从头部插入，新插入的数据将优先被接收。
- xQueuePeek 只复制头部数据，不移除；空队列按等待时间阻塞，超时返回失败。

#### 从队尾发送的数据，需要移动到队头才能读取吗？

- 不需要。队头/队尾表示逻辑读写位置，数据不会逐格移动。
- 空队列发送 A 后，A 就是队头也是队尾，可以立即接收。
- 已有 A、B 时发送 C，接收顺序是 A→B→C；靠读写位置更新，不靠搬移所有数据。
- 底层使用环形缓冲区，读写位置走到末尾后回绕；队列中有数据即可接收，无须填满。
<a id="semaphores"></a>

### 三、信号量与互斥锁

#### 计数信号量的存取函数是什么？

- 释放/增加计数：`xSemaphoreGive(handle)`，成功后计数加 1；达到最大计数时失败。
- 获取/减少计数：`xSemaphoreTake(handle, waitTicks)`，成功后计数减 1；为 0 时按指定时间等待，0 表示不等待。
- 中断使用 `xSemaphoreGiveFromISR()` / `xSemaphoreTakeFromISR()`，不能阻塞，按需请求 ISR 退出时切换任务。
- 创建：`xSemaphoreCreateCounting(maxCount, initialCount)`；查询当前计数：`uxSemaphoreGetCount(handle)`。
- 存取的是计数/资源令牌，不传递具体数据；检查返回值 `pdTRUE`/`pdFALSE`。

#### 互斥锁的获取和释放函数是什么？

- 普通互斥锁：创建 xSemaphoreCreateMutex()，获取 xSemaphoreTake(mutex, waitTicks)，释放 xSemaphoreGive(mutex)。
- 递归互斥锁：创建 xSemaphoreCreateRecursiveMutex()，获取 xSemaphoreTakeRecursive()，释放 xSemaphoreGiveRecursive()，成功获取几次需释放几次。
- 不要混用普通和递归接口；锁必须由持有任务释放，不能在 ISR 中获取或释放互斥锁。
- 名称为 Semaphore（信号量），公开获取接口不是 xSemaphoreTakeMutex。

#### 事件组省内存，为什么还用二值信号量？

- 事件组表示条件/状态，可等待任意一个或全部条件；置位可能唤醒多个满足条件的等待任务。
- 二值信号量表示一个可消费的令牌；一次 Give 最多唤醒一个等待任务，Take 成功消耗令牌。
- 事件组即使等待时自动清位，也不能当作只允许一个等待者消费的信号量。
- ISR 中 GiveFromISR 可直接完成释放；SetBitsFromISR 要通过定时器命令队列交给服务任务处理，有排队和调度延迟。
- 单事件交接可用二值信号量；多条件组合/广播状态用事件组；固定接收任务可考虑任务通知。
- 两者都不能可靠累计每次重复事件；需计次数用计数信号量，需传数据用队列。选型看语义、时延和用途，不只看对象内存。
#### 互斥锁和自旋锁有什么区别，适用场景是什么？

**常见问法**：互斥锁与自旋锁；等锁时是否占 CPU？

**简答**：互斥锁获取失败时可阻塞任务，让 CPU 运行其他就绪任务，适合任务间保护共享资源；自旋锁持续检查锁是否可用，等待期间占 CPU，通常用于多核下很短的临界区，获取与释放需要正确的原子操作和内存顺序。

**补充理解**：普通单核 MCU FreeRTOS 项目优先使用任务互斥锁或短临界区，不要手写 while(flag) 当自旋锁。若高优先级任务一直自旋，低优先级持锁者可能无法运行并释放锁；标准任务互斥锁具有优先级继承机制。

#### 互斥锁什么时候让出 CPU？

**常见问法**：互斥锁什么时候阻塞；xSemaphoreTake 一定切换任务吗？

**简答**：`xSemaphoreTake(mutex, waitTicks)` 在锁不可用且允许等待时，可让当前任务进入阻塞态，调度其他就绪任务。锁可用则成功返回；等待时间为 0 时立即返回失败，不因这次取锁进入等待。

**补充理解**：解锁后若使更高优先级任务就绪，抢占式调度下可能切换；是否立即切换还取决于调度配置。拿着锁的任务也可能被抢占，互斥锁不会关中断。见 [FreeRTOS 互斥锁说明](https://freertos.org/Real-time-embedded-RTOS-mutexes.html)。

#### 中断里能使用互斥锁吗，延后到任务处理呢？

**常见问法**：ISR 里面能用互斥锁吗；中断后续处理怎么做？

**简答**：FreeRTOS 的互斥锁不能在 ISR 中获取或释放，包括“不等待”的取锁；它有任务所有权与优先级继承语义，ISR 也不能阻塞等待。中断中用适用的 FromISR 队列、任务通知或信号量通知任务。

**补充理解**：复杂处理延后到普通任务执行后，任务上下文可以按需用互斥锁。若任务与 ISR 共同访问数据，使用合适的短临界区／原子操作或缓冲区交接；不是给 ISR 套上任务互斥锁。FromISR 调用还须符合移植规定的中断优先级。见 [FreeRTOS 中断延后处理示例](https://freertos.org/Embedded-RTOS-Binary-Semaphores.html)。

#### 什么是优先级反转，有什么危害和解决方法？

**常见问法**：高优先级任务为什么被低优先级任务拖住；继承能完全解决吗？

**简答**：高优先级任务等待低优先级任务占有的资源，若中优先级任务又抢占持锁者，就会间接拖延高优先级任务。危害是响应时间变长、错过截止期。可用支持优先级继承的互斥锁、系统支持的优先级天花板协议，并缩短持锁时间、避免锁内长阻塞和不必要共享。

**补充理解**：例：L 持锁，H 等锁，M 抢占 L，使 H 等更久；继承把 L 暂时提升，让它尽快完成并释放。继承不会跳过持锁代码，也不解决所有嵌套锁、死锁或长时间 I/O 问题。FreeRTOS 互斥锁有简化继承，普通二值信号量没有；不能把资源互斥锁随意换成信号量。见 [FreeRTOS 互斥锁说明](https://freertos.org/Real-time-embedded-RTOS-mutexes.html)。

<a id="events"></a>

### 四、事件组

#### xEventGroupGetBits 获取一位还是多位？

- 正确名称：xEventGroupGetBits(group)，返回整个事件组当前位值，类型 EventBits_t。
- 单位判断：bits & BIT0；多位任意成立：(bits & mask) != 0；多位全部成立：(bits & mask) == mask。
- 只读取，不等待、不清位；返回的是查询时的快照，之后可能被其他任务改变。
- 中断读取使用 xEventGroupGetBitsFromISR()；不要操作内核保留位。

#### 等所有任务到达同步点的事件组函数是什么？

- `xEventGroupSync(group, myBit, allBits, waitTicks)`：原子地设置自己的到达位，并等待所有指定到达位成立，形成同步屏障。
- 每个参与任务用一个独立位；allBits 为所有参与位的按位或。条件满足后本轮同步位自动清除。
- 例：A 设置 BIT0，B 设置 BIT1，两者都等 BIT0|BIT1；先到者阻塞，后到者满足条件，双方继续按调度运行。
- 满足条件不代表同时执行；单核仍按优先级调度。超时可能提前返回，必须检查返回位，超时后的位状态需自行设计。
- 与 WaitBits 区别：WaitBits 只等待，Sync 将自己的置位和等待作为一个原子同步操作；不能从 ISR 调用。

#### 事件组需要软件定时器任务吗？

- 普通任务调用 SetBits、ClearBits、WaitBits 等，直接处理，不需要定时器服务任务转发。
- xEventGroupSetBitsFromISR / xEventGroupClearBitsFromISR 将操作送入定时器命令队列，由定时器服务任务执行。
- 原因：设置事件位可能唤醒多个任务，处理时间不固定，避免在 ISR 内做这部分工作。
- 使用上述延后处理接口通常需 configUSE_TIMERS=1、INCLUDE_xTimerPendFunctionCall=1；具体核对工程内核版本。
- 不必创建用户软件定时器；借用的是共用服务任务与命令队列。队列满可能发送失败，成功只表示请求入队。
<a id="timers"></a>

### 五、软件定时器

#### 为什么软件定时器要设置队列长度？

- `configTIMER_QUEUE_LENGTH` 设置共享定时器命令队列的容量，单位为命令条数。
- 启动、停止、重置、修改周期等请求先入队，由定时器服务任务处理。
- 容量限制的是待处理命令数，不是定时器数量，也不是到期事件数量。
- 队列满时，任务侧接口可按指定时间等待；不等待或超时则发送失败。ISR 接口不能阻塞。
- 根据命令突发积压量设置；增大容量会增加 RAM 占用。

#### 软件定时器动态创建与静态创建有什么区别？

- 动态：`xTimerCreate()` 从堆分配定时器对象；静态：`xTimerCreateStatic()` 使用用户提供的 `StaticTimer_t` 缓冲区。
- 两者创建后都需要启动；删除命令处理后，动态对象按堆实现释放，静态缓冲区由用户管理。
- 所有定时器共用服务任务及命令队列，不是每个定时器各有任务栈。
- 缓冲区必须在定时器使用期间有效；通用创建规则见[内存分配](#allocation)。
<a id="critical"></a>

### 六、中断与临界区

#### CRITICAL 是什么意思？

- 表示临界区：保护共享数据操作，避免并发干扰。
- 常见宏：`taskENTER_CRITICAL()` / `taskEXIT_CRITICAL()`，必须成对，允许按移植规则嵌套。
- 常见单核 Cortex-M 移植通过屏蔽一定范围的中断保护操作，不保证屏蔽所有中断。
- 临界区尽量短，不执行延时或可能阻塞的操作；ISR 使用对应的中断版接口。
- 单独的 `CRITICAL()` 可能是项目封装，需查看定义。
#### 中断与任务之间怎样交互数据？

**常见问法**：ISR 到任务有哪些通信方式，各有什么注意事项？

**简答**：小数据可用 FromISR 队列值拷贝，事件可用 FromISR 任务通知或信号量；大量数据常用共享环形／双缓冲区或 DMA，ISR 通知任务处理，必要时用指针队列交接缓冲区。队列保留消息，通知轻量但不是多条数据队列，单个标志也不能可靠累计事件。

**补充理解**：ISR 不能阻塞，只用适用的中断版 API，检查队列满等返回值并符合中断优先级要求；唤醒更高优先级任务时按移植规则请求切换。共享缓冲区要控制边界、生命周期、读写位置和所有权，有 Cache 时处理一致性；短共享操作用合适原子／临界区，不能在 ISR 获取任务互斥锁。事件组 FromISR 的延后处理限制见事件组分区。

<a id="allocation"></a>

### 七、内存分配与内核对象

#### 为什么很多对象都有静态和动态创建？

- 动态创建：FreeRTOS 从堆申请对象内存；创建方便，可能因分配失败而失败。
- 静态创建：用户提供对象所需内存；对象本身不再从堆申请，内存占用更容易规划。
- 创建后的功能基本相同，区别是内存来源和管理方式，不是运行方式。
- 不同对象需要不同存储：任务＝控制块＋栈，队列＝控制块＋数据区，信号量＝控制块。
- 固定数量、长期使用可选静态；按需创建、销毁可选动态。二者可按配置混用。
- 静态接口仍在运行时调用；提供的缓冲区必须在对象使用期间有效，不能使用函数返回后失效的普通局部数组。

#### 常见内核对象的底层组成和 RAM 占用

实际大小随版本、架构、配置变化；以下是对象内存，不含堆分配头和对齐开销。

| 对象 | 底层组成 | 内存估算 |
|---|---|---|
| 任务 | TCB 控制块＋独立栈 | sizeof(StaticTask_t)＋栈深度×sizeof(StackType_t) |
| 队列 | Queue_t 控制块＋数据缓冲区 | sizeof(StaticQueue_t)＋长度×单项字节数 |
| 二值信号量 | 长度 1、单项大小 0 的队列机制 | sizeof(StaticSemaphore_t) |
| 计数信号量 | 单项大小 0 的队列机制，队列计数表示资源数量 | sizeof(StaticSemaphore_t)，不随最大计数线性增加 |
| 互斥锁/递归互斥锁 | 队列机制＋持有者、递归计数等控制信息 | sizeof(StaticSemaphore_t)，无需数据区 |
| 事件组 | 事件位＋等待任务链表 | sizeof(StaticEventGroup_t) |
| 软件定时器 | 周期、回调、ID、链表项等控制信息 | sizeof(StaticTimer_t)；另外共用服务任务和命令队列 |
| 任务通知 | TCB 内的通知值和状态 | 无独立对象分配；每槽字段为 4 字节值＋1 字节状态，结构对齐另计 |
| 流/消息缓冲区 | 控制块＋环形缓冲区 | 控制块＋缓冲区（含实现所需预留）；消息缓冲区每条消息还存长度头 |

- 队列、信号量、互斥锁复用队列机制；其余对象有自己的结构。
- 单核常规配置下控制块常为几十至百余字节量级，任务栈/数据缓冲区通常更占内存；不要背固定字节数。
- 标准 FreeRTOS 的任务栈深度单位是 StackType_t 元素数，常见 STM32 为 4 字节；厂商移植可能不同。
- 本工程可用 sizeof 对应 Static 类型查看控制块大小；动态创建前后比较 xPortGetFreeHeapSize() 可观察实际堆消耗，需排除其他分配干扰和首次共享设施初始化。

#### 队列控制头占多少字节？

- 控制头即 `Queue_t`，大小随内核版本、架构和配置变化，不应背固定数字。
- 本工程查看 `sizeof(StaticQueue_t)`，得到控制块大小，不包含数据区。
- 总对象大小约为控制块＋队列长度×单项大小；动态分配另有分配头和对齐开销。
- 之前的 80 字节只是计算示例，不是已核实的教材或工程数值。

### 八、堆栈监测与异常钩子

#### 堆与任务栈分别看什么？

- 堆是动态分配池；任务栈保存局部变量、调用信息和上下文。
- 动态任务的栈可以从堆中分配，但“任务栈用满”和“堆分配失败”是不同问题。

#### 监测接口和异常钩子怎么用？

| 功能 | 接口 | 用途／易错点 |
|---|---|---|
| 当前剩余堆 | `xPortGetFreeHeapSize()` | 初始化或分配后查看；单位字节，不代表最大连续空闲块 |
| 历史最小剩余堆 | `xPortGetMinimumEverFreeHeapSize()` | 压力测试后评估堆余量；支持情况取决于堆实现 |
| 历史最小剩余任务栈 | `uxTaskGetStackHighWaterMark(handle)` | 复杂路径跑过后调整栈配置；NULL 表示当前任务 |
| 堆分配失败钩子 | `vApplicationMallocFailedHook(void)` | 用户实现、系统触发；不检测堆写越界 |
| 栈溢出钩子 | `vApplicationStackOverflowHook(TaskHandle_t xTask, char *pcTaskName)` | 用户实现、系统检测后触发；不能保证捕获所有溢出 |

常用配置：

```c
#define INCLUDE_uxTaskGetStackHighWaterMark 1
#define configUSE_MALLOC_FAILED_HOOK       1
#define configCHECK_FOR_STACK_OVERFLOW    2
```

通常放在诊断任务、调试命令或故障处理模块，不必每轮业务处理都查询。

#### 最小剩余栈在多任务中如何测量，会变化吗？

- 正常多任务运行中调用接口；每个任务有自己的栈，切换不会清空历史痕迹。
- 创建时填充栈，查询时扫描未被改写的填充值，估算历史使用深度。
- 返回历史最小余量，不是当前余量；例如曾剩 100、后来剩 800，查询仍约为 100。
- 同一任务生命周期内通常只会变小或不变；接收结果的普通变量不会自动刷新，要重新调用并赋值。
- 标准内核单位为 `StackType_t` 元素数，字节数＝返回值×`sizeof(StackType_t)`；常见 STM32 为 4 字节，厂商移植可能不同。

例：连续查询为 `100 → 100 → 60 → 60`，表示后来栈使用更深了。应覆盖复杂和异常路径并留余量，未被实际写入的栈空间可能使估算偏乐观。

#### 任务栈除了动态监测，还有什么分析方法？

**常见问法**：任务堆栈除了动态监测还有什么方法实现（按栈占用分析理解）？

**简答**：可用编译器栈使用报告、调用图与最深调用链估算，加上局部变量、寄存器保存、异常／中断和库函数开销，为任务栈预算留余量；GCC 可用 `-fstack-usage` 和 `-Wstack-usage=N`。链接 Map 可看内存布局及栈预留，MPU／栈保护可辅助发现越界。

**补充理解**：单个函数报告不是整条调用链峰值；递归、函数指针、可变长数组、汇编和库函数可能导致静态估算不完整。Map 不能单独证明实际最坏栈深度；应与压力测试、高水位和溢出检查配合。见[GCC 说明](https://gcc.gnu.org/onlinedocs/gcc-13.1.0/gcc/Warning-Options.html)。

#### 怎么避免任务栈溢出？

**常见问法**：怎么避免栈溢出问题；什么情况下会栈溢出；RTOS 中怎么排查？

**简答**：按最深调用链和复杂路径预算栈并留余量；避免无界递归、超大局部数组和不受控调用深度，关注 printf 等库函数开销。开启溢出检查／钩子，运行高水位与异常路径测试，检查数组越界；支持时可用 MPU 或栈保护。

**补充理解**：大型缓冲区可移到生命周期明确的静态区域或池／堆，但要处理共享和分配失败；同时检查任务栈与中断栈。检测不是防止所有破坏，也不能自动修复溢出。

**排查步骤**：确认任务创建时栈深度的单位，运行最复杂、异常和高负载路径，记录 uxTaskGetStackHighWaterMark 的历史最小余量；结合溢出钩子、栈边界填充值和调试器检查。若有故障，抓取 PC／LR／SP、调用链与现场，用硬件观察点／MPU 寻找最早的越界写；区分实际栈用尽和其他代码写坏栈。高水位正常也不能排除未覆盖路径或未写入的栈空间。Cortex-M 常见移植还要分别检查任务使用的 PSP 栈和 ISR 使用的 MSP 栈，不能只看任务栈。

<a id="pwm-clock"></a>

## 五、定时器、PWM 与时钟

### PWM 波的原理是什么？

**常见问法**：PWM 周期、频率与占空比；定时器参数怎样决定波形？

**简答**：PWM 通过改变高电平持续时间调节占空比。周期 T 是一轮波形时间，频率 f=1/T；高有效时占空比 D=高电平时间/T。常见向上计数、PWM 模式 1 下，f=f_TIM/((PSC+1)*(ARR+1))，D 约为 CCR/(ARR+1)。

**补充理解**：例如周期 1 ms、频率 1 kHz，高电平 0.25 ms 就是 25%。中心对齐、极性等改变时须核对公式；f_TIM 是实际定时器时钟。理想平均电平为 D*V高+(1-D)*V低，但 GPIO 仍是脉冲，需要负载或滤波。见 [ST 定时器资料](https://www.st.com/content/ccc/resource/training/technical/product_training/group1/66/65/13/8d/79/18/49/c9/stm32c0-wdg-timers-general-purpose-timer/files/stm32c0-wdg-timers-general-purpose-timer.pdf/jcr%3Acontent/translations/en.stm32c0-wdg-timers-general-purpose-timer.pdf)。

### 除了定时器 PWM 模式，还有什么实现方式？

**常见问法**：硬件 PWM 与软件 PWM 区别；还有哪些办法产生 PWM？

**简答**：硬件 PWM 由定时器计数和比较自动输出，通常时序稳定、CPU 占用低；软件 PWM 用延时或中断控制 GPIO，灵活但受调度／中断延迟影响，CPU 占用和抖动通常更大。还可用输出比较、支持条件下的定时器触发 DMA，或专用 PWM 芯片。

**补充理解**：按频率、精度、通道数选型；软件方式适合要求较低的低速输出。DMA 方案需芯片支持触发和目标寄存器；CPU 休眠时硬件 PWM 是否继续运行也取决于定时器时钟与电源域。RTOS 延时的限制见下一题。

### 能否通过 RTOS 延时函数产生 PWM？

**常见问法**：通过 rtos 延时函数；vTaskDelay 翻转 GPIO 能做 PWM 吗？

**简答**：可以让任务依次输出高电平、延时、输出低电平、延时，产生低速且精度要求不高的软件 PWM。精度受 Tick 分辨率、任务调度及中断影响，延时到期只是任务就绪，不保证立即执行；不宜用于高频或精密 PWM，应优先硬件定时器。

**补充理解**：`vTaskDelay` 的相对延时还会叠加执行耗时；绝对周期延时可减少周期漂移，但不能消除调度抖动。毫秒换算为 Tick 时还可能取整为 0。见[FreeRTOS 延时说明](https://freertos.org/a00127.html)。

### 为什么选择这个时钟频率？

**常见问法**：为什么选择这个时钟频率；为什么不总是用最高频率？

**简答**：依据处理量和实时期限、外设时序与精度、功耗、芯片限制共同选择。先确认计算／通信能及时完成，再核对定时器、串口、ADC 和总线分频是否满足要求，最后在够用的前提下兼顾功耗和余量。

**补充理解**：应区分 CPU 时钟、外设时钟、定时器时钟与 RTOS Tick；核对 PLL、供电条件和 Flash 等待周期。面试可说：为满足【具体负载及期限】选【实际频率】，分频满足【外设需求】，并用【测量证据】验证；题目未提供工程与频率，不能编造具体理由。

## 六、故障排查

### 系统跑飞常见原因的简单示例

| 原因 | 示例 |
|---|---|
| 数组越界 | buf[8] 只允许索引 0～7，却写 buf[8]，可能覆盖邻近变量、栈或控制块 |
| 栈溢出/递归过深 | 函数递归没有终止条件，调用现场不断占栈，最终超出栈空间 |
| 大型局部数组 | 任务栈约 1KB，却使用并写入局部数组 uint8_t buf[2048] |
| 空指针 | p=NULL 后执行 *p=1，访问无效目标；是否故障取决于地址映射 |
| 悬空指针 | 把函数局部变量地址保存给任务，函数返回后任务再用该地址 |
| 函数指针错误 | 未初始化回调指针就调用，可能跳转到错误地址 |
| 中断向量损坏 | RAM 向量表中 UART 中断入口被覆盖，中断时跳到错误地址 |
| 返回地址损坏 | 越界写覆盖栈中的返回地址，函数返回时跳到错误位置 |
| 非法地址 | 通过错误指针访问未映射或不允许访问的地址，可能触发总线/内存故障 |
| 非对齐访问 | 以要求对齐的指令或开启非对齐陷阱的配置访问 buf+1 上的 32 位数据，可能异常 |
| ISR 调错 API | 中断里使用带阻塞等待的 xQueueSend，应该使用 FromISR 版本 |
| ISR 优先级不合法 | 常见 Cortex-M3/M4 移植中，若库级 API 优先级边界为 5，优先级 2 的 ISR 不得调用 FreeRTOS API，5～更大的合法值才可；数值越小优先级越高 |
| 竞态 | 两个任务同时做 count++，交错执行造成更新丢失；不一定跑飞，但可破坏后续逻辑 |
| DMA 越界 | 接收缓冲区为 64 字节，却设置 DMA 写入 128 字节，覆盖其他数据 |
| 缓存一致性 | 带 D-cache 的 MCU 上 DMA 已更新 RAM，CPU 却读到旧缓存，误判数据 |
| 时钟问题 | PLL 配置或 Flash 等待周期不匹配，可能造成执行异常 |
| 电源问题 | 电机启动导致 MCU 供电跌落，触发欠压复位 |
| 看门狗 | 长时间阻塞或高优先级任务霸占 CPU，喂狗流程没执行，触发复位 |

这些原因可能表现为数据错误、HardFault、死锁或复位，并非都真的跳到错误地址。ISR 优先级/非对齐/缓存行为需结合具体芯片和移植配置。

### 排查时先区分哪些现象？

**常见问法**：偶发死机、HardFault 的通用排查；先抓哪些信息？

**简答**：先区分异常、死锁、任务饥饿、看门狗／欠压复位等现象。保留固件版本、复位原因、最后事件与任务状态；HardFault 抓取异常压栈的 PC、LR、栈指针和故障寄存器，用对应 ELF／Map、反汇编定位，再检查越界、悬空指针、栈、ISR API、DMA 与供电时钟。

**补充理解**：Cortex-M3／M4／M7 可看 CFSR／HFSR，BFAR／MMFAR 要确认有效位；M0 等寄存器不同。异常栈中的 PC 与当前处理器在故障处理函数中的 PC 要区分，非精确总线故障还可能需追溯较早访问。故障记录尽量简短，不依赖可能已损坏的堆、锁或阻塞打印；检查数组边界、栈余量，必要时用硬件观察点、MPU 和压力测试找首次破坏。寄存器说明见 [Arm Cortex-M7 手册](https://documentation-service.arm.com/static/61efd6602dd99944d051417b)。

### 定位和复现疑难 bug 常用哪些手段？

**常见问法**：偶发问题怎样提高复现率；调试一般怎么做？

**简答**：先记录触发条件、固件版本、输入、时序与环境，建立最小可复现流程；用有时间戳的事件记录、断言、故障快照、调试器断点／观察点定位，用逻辑分析仪、示波器和电流测量关联外部现象，再逐步缩小模块与变量。

**补充理解**：可重放通信流量，测试高负载、超时、队列满、分配失败、断电／重启等边界；固定随机种子便于复现。每次改一个关键条件，用证据验证假设，修复后跑原复现场景和相关压力测试。日志和断点会改变时序，竞态问题优先轻量追踪，不把暂时不再出现当成已修复；个人经历据实描述。

## 七、外设接口与调试

### 什么是上拉电阻，I²C 为什么需要？

**常见问法**：上拉电阻是什么；SDA 和 SCL 为何要上拉？

**简答**：上拉电阻把信号线连接到正电源，使无人驱动时保持高电平。常规双向 I²C 的 SDA／SCL 用开漏方式，只主动拉低，释放后由上拉电阻拉高，可实现多设备共享总线。

**补充理解**：阻值要兼顾总线电容、上升时间和拉低电流；过大可能上升太慢，过小增加电流并影响低电平。内部弱上拉不一定满足 I²C 时序，需按芯片与总线规格选择。见 [NXP I²C 规范](https://cache.nxp.com/docs/en/user-guide/UM10204.pdf)。

### I²C 的 ACK／NACK 波形是什么，读失败一定有 NACK 吗？

**常见问法**：读取失败后总线行为；ACK 和 NACK 什么波形？

**简答**：每传完 8 位，第 9 个 SCL 时钟是应答位：SCL 高电平期间，SDA 为低是 ACK，为高是 NACK。发送方先释放 SDA，由接收方应答。地址阶段无设备响应、设备暂未准备好等可表现为 NACK；卡线、超时等失败不一定有完整 NACK 时序。

**补充理解**：主机读数据时由主机应答，读最后一字节发送 NACK 再 STOP 是正常结束，不能当成读失败。出现 NACK 后可 STOP 或重复 START，具体按控制器与驱动处理。见 [NXP I²C 规范 §3.1.6](https://cache.nxp.com/docs/en/user-guide/UM10204.pdf)。

### 面试问熟悉哪些外设接口，怎么回答？

**常见问法**：对哪些外设比较熟悉；I²C、串口等怎么介绍？

**简答**：选实际使用过的接口，从“连接设备、收发方式、任务分工、遇到的问题及验证方法”回答。例如 UART 可讲帧格式、波特率、中断／DMA、缓冲区；I²C 可讲地址、寄存器访问、ACK 和上拉；SPI 可讲时钟模式、片选与传输。

**补充理解**：按真实项目选择，不编造用过的接口或调试经历。MIPI 是一组接口规范，常用于高速摄像头／显示等，未用过时说明了解范围，不硬套成 UART／I²C。

### 如何用示波器或逻辑分析仪排查 I²C／AS5600 跳变？

**常见问法**：I²C 设备无响应如何调试；会用逻辑分析仪、示波器吗；AS5600 跳变？

**简答**：逻辑分析仪看数字时序与协议解码，示波器看电压幅度、上升时间和毛刺。I²C 无响应先定位是无 SCL、地址阶段 NACK，还是 SDA／SCL 卡低，再查供电、共地、上拉、引脚复用、7／8 位地址约定、启动等待和速率；波形与驱动错误码对应，不仅看软件返回失败。

**补充理解**：AS5600 的 12 位原始角度在 4095→0 回绕通常正常；短路程差值按 4096 周期处理须保证采样间位移小于半圈。异常再查成对字节读取／拼接、通信状态与磁场。SPI 看片选和采样边沿，UART 看位时间与帧格式；测量工具使用经历据实回答。见 [AS5600 手册](https://look.ams-osram.com/m/7059eac7531a86fd/original/AS5600-DS000365.pdf)。

### I²C 有哪些信号，SCL／SDA 的时序规则是什么？

**常见问法**：I²C 两根线作用；START、STOP、数据何时改变？

**简答**：SCL 是时钟线，SDA 是双向数据线，空闲时通常都为高。SCL 高时 SDA 由高到低表示 START，由低到高表示 STOP；普通数据在 SCL 低时改变，高时保持稳定，由接收方采样。每字节 8 位，之后是第 9 位 ACK／NACK。

**补充理解**：重复 START 可在不先 STOP 的情况下开始新阶段。控制器产生时钟，目标设备可能拉低 SCL 延长等待；速率、建立／保持时间和上升时间要满足器件要求。见 [NXP I²C 规范](https://cache.nxp.com/docs/en/user-guide/UM10204.pdf)。

### I²C 地址有几位，R/W 位和写流程是什么？

**常见问法**：I²C 是 7 位还是 8 位地址；写寄存器流程？

**简答**：常用 7 位设备地址，也支持 10 位地址。7 位寻址的首字节由“7 位地址＋1 位 R/W”组成：0 表示主机写，1 表示主机读；R/W 不属于设备地址。寄存器型设备的典型写流程是 START→设备地址＋W→ACK→寄存器地址→ACK→数据→ACK→STOP。

**补充理解**：区分手册的 7 位地址与含 R/W 的地址字节，并核对 API 是否要求左移。例如 7 位地址 0x36，对应写地址字节 0x6C、读地址字节 0x6D；寄存器地址宽度、数据长度和写后等待由设备手册决定。见 [NXP I²C 规范](https://cache.nxp.com/docs/en/user-guide/UM10204.pdf)。

### SPI 有几种模式，Mode 1 怎样采样？

**常见问法**：CPOL／CPHA 含义；Mode 1 的采样边沿？

**简答**：SPI 的 CPOL 与 CPHA 组合成 4 种模式。CPOL 决定时钟空闲电平；CPHA=0 在第一个边沿采样，CPHA=1 在第二个边沿采样。Mode 1 是 CPOL=0、CPHA=1：SCK 空闲为低，上升沿更新／推出数据，下降沿采样。

**补充理解**：Mode 0：0/0、上升沿采样；Mode 2：1/0、下降沿采样；Mode 3：1/1、上升沿采样。两端还须匹配位序、数据宽度、频率与片选时序；不同厂商寄存器命名要按手册换算。见 [Microchip SPI 模式表](https://onlinedocs.microchip.com/oxy/GUID-A299F4E7-F38C-4DF5-96C0-A87B9F519156-en-US-4/GUID-8A5B8750-B99E-4176-834E-E44E98F4A098.html)。

### UART 数据帧由什么组成，起始位是什么电平？

**常见问法**：UART 帧结构；8N1 是什么？

**简答**：常见非反相 UART 帧由起始位、数据位、可选校验位、停止位组成。空闲高，起始位低，停止位高；8N1 表示 8 位数据、无校验、1 位停止位，共 10 个位时间，数据通常低位先发。

**补充理解**：两端须匹配波特率、数据位、校验和停止位。这里说的是 MCU 逻辑端；反相配置或 RS-232 物理电压不能直接按 GPIO 高低解释。见 [Microchip UART 帧格式](https://onlinedocs.microchip.com/oxy/GUID-C431CD9B-65A0-4015-871C-58A444612066-en-US-3/GUID-F84E04E8-3235-4E21-89A9-D1911E9B91DD.html)。

### 只有 TX／RX，MCU 与休眠模组怎样唤醒和接收？

**常见问法**：没有独立唤醒引脚，串口能否唤醒双方？

**简答**：MCU 唤醒模组：先查模组是否支持 UART 唤醒，支持时按规定发唤醒序列、等待就绪再传数据；不支持时，仅靠 TX／RX 不能保证唤醒，要增加控制线或约定周期接收。模组唤醒 MCU：可用芯片支持的低功耗 UART 唤醒，或在支持条件下用 RX 边沿触发外部中断。

**补充理解**：RX 边沿唤醒后恢复时钟和 UART，首字节可能丢失，协议需前导、等待、确认／重发。Stop 等模式下 UART、DMA 和相关时钟是否运行须逐项确认，不能默认深睡仍完整收帧。MCU 侧条件见 [ST AN4991](https://www.st.com/resource/en/application_note/DM00355687-.pdf)。

### DMA 缓冲区与存储扇区／页对齐问题怎么排查？

**常见问法**：DMA 内存访问失败或数据错误；地址、长度、扇区／页边界不满足怎么办？

**简答**：分别核对三类要求：DMA 是否能访问该 RAM、地址与传输宽度是否匹配；带 Cache 平台的缓存行及一致性；SD／Flash 等存储驱动的块大小、偏移和页边界。检查源／目标地址、长度与计数单位、错误标志，并用已知模式逐层核对数据。

**补充理解**：优先使用 DMA 可访问且满足对齐的长期缓冲区；无法直接传输时可用对齐中转缓冲区，拆分块或按存储语义读改写。按平台规则做发送 clean、接收 invalidate 等缓存维护，避免范围牵连相邻数据；只加 volatile 不能解决。扇区／页对齐不等于 Cache 行对齐，数值按实际设备确认。见 [Arm Cache 接口要求](https://arm-software.github.io/CMSIS_6/main/Core/group__Dcache__functions__m7.html)。

### 面试问了解无线协议，怎么回答？

**常见问法**：常见无线方案；LoRa 和 LoRaWAN 是一回事吗？

**简答**：先说真实使用过的方案，再讲连接方式、报文、可靠性与功耗取舍。常见有 Wi-Fi、BLE、Zigbee；LoRa 是物理层调制技术，LoRaWAN 是其上的网络协议与体系，串口 LoRa 模块点对点传输不代表使用 LoRaWAN。

**补充理解**：准备说明模块配置、地址／信道、数据帧、超时重试、校验和睡眠唤醒；距离、速率、功耗必须结合条件，不背固定数值，也不编造用过的协议。见 [LoRa Alliance 说明](https://lora-alliance.org/lorawan-for-developers/)。

### USB 有哪几种传输方式？

**常见问法**：熟悉 USB 吗；控制、批量、中断、等时传输区别？

**简答**：USB 有 4 类传输：控制传输用于枚举、配置和控制请求；批量传输用于大块可靠数据，时延无保证；中断传输由主机按约定间隔访问，适合小量、低延迟事件数据；等时传输面向音视频等实时流，按周期分配带宽，出错通常不重传。

**补充理解**：USB“中断传输”不是设备随意主动打断主机。MCU 项目可结合实际 CDC、HID、MSC 等设备类说明，设备类与传输类型不是一个概念。见 [ST USB 概览](https://wiki.st.com/stm32mcu/wiki/USB_overview)。

### 常见 USB 描述符有哪些？

**常见问法**：USB 描述符作用；枚举时主机怎么认识设备？

**简答**：常见有设备、配置、接口、端点和字符串描述符。设备描述符给出 VID／PID 等基本信息；配置描述符描述一个配置及其接口／端点集合；接口描述符描述功能或设备类；端点描述符说明方向、传输类型、最大包长等；字符串描述符提供名称等文本。

**补充理解**：还可能有 HID、IAD、BOS 等类或能力相关描述符。主机在枚举中通过 EP0 控制请求读取描述符；描述符内容要与固件真实接口、端点和类请求处理一致。见 [ST USB 设备库手册](https://www.st.com/resource/en/user_manual/um1734-stm32cube-usb-device-library-stmicroelectronics.pdf)。

### UART、I²C 开发需关注哪些通信风险？

**常见问法**：串口／I²C 常见问题与预防措施？

**简答**：共同关注电平、共地、配置、时序、并发访问、超时和错误恢复。UART 重点是波特率／帧格式、收不及时导致溢出、DMA 缓冲区覆盖，以及应用报文分包、长度和校验；I²C 重点是地址约定、上拉／上升时间、NACK、忙状态／卡线和设备写后等待。

**补充理解**：一次串口接收不一定等于一完整应用帧，UART 也不自带应用报文边界。接口事务由一个任务管理或加适用互斥保护；异常处理避免无限等待／重试，按故障类型清状态、重置外设或依器件流程恢复总线，注意不要破坏同总线其他事务。用波形与错误计数验证，DMA 与唤醒细节见本分区其他条目。

## 八、系统设计与固件可靠性

### Flash 频繁擦写有什么问题，怎样延长寿命？

**常见问法**：Flash 擦写寿命与磨损均衡；参数怎样可靠保存？

**简答**：Flash 擦写次数有限，频繁更新同一页会加快磨损；擦写有页／块粒度、耗时和供电条件，断电或低压可能使数据不完整，部分芯片还会影响代码／中断运行。可减少无变化写入、合并批量写、日志式追加、多页轮换／磨损均衡，或为高频数据选择适合的存储器。

**补充理解**：关键参数用序号、CRC、有效提交标志和冗余记录，写新记录验证成功再淘汰旧记录，以便掉电恢复；这些保证一致性，不能代替磨损均衡。寿命与保持时间按具体器件条件评估，RAM 暂存降低写频率时也须权衡掉电丢失。见 [ST EEPROM 仿真说明](https://www.st.com/resource/en/application_note/dm00311483.pdf)。

### 固件升级怎样避免失败后系统无法启动？

**常见问法**：升级失败、断电、坏固件怎么恢复；A／B 和回滚？

**简答**：保留受保护的 Bootloader 与恢复入口，将新镜像先写到备用槽／暂存区，检查完整性、型号和版本兼容，必要时验证签名。采用 A／B 或可恢复搬移机制，升级状态与切换标志支持掉电恢复；新固件试运行自检后确认，失败或未确认则回滚到旧版。

**补充理解**：不能认为双分区自然防掉电：元数据、搬移进度和参数迁移也要设计恢复。空间不足时可外部暂存或保留可重新下载的恢复程序；CRC 检测传输损坏，不等于来源认证。测试断电、包损坏、启动崩溃与确认超时等场景，避免同时破坏正常镜像与恢复路径。参考 [MCUboot 升级与回滚设计](https://docs.mcuboot.com/design.html)。

### 嵌入式软件架构设计重点考虑什么？

**常见问法**：架构怎么分层；多任务系统如何划分模块？

**简答**：先明确功能、实时期限、资源、功耗和可靠性要求，再划分驱动、协议／服务、业务等职责。重点确定模块接口和数据所有权、任务／ISR 分工、通信与同步、错误恢复、内存预算、参数／升级边界，以及可测试、可调试和可维护性。

**补充理解**：任务按时序和阻塞需求划分，不必一个模块建一个任务；共享设备尽量统一管理。通过状态机和明确接口减少隐式全局依赖，避免过度分层与不必要拷贝。用实际延迟、栈／堆、故障注入和接口测试检验设计，不只画框图。

### 如何介绍项目中有挑战的问题？

**常见问法**：挑一个印象深刻的问题；项目／实习难点怎么讲？

**简答**：选择真实参与的问题，按“项目背景与个人职责→现象和影响→定位证据与根因→方案及取舍→验证结果”回答。突出自己完成的分析和行动，明确团队贡献以及已实现、已编译、已实测的边界。

**补充理解**：口述框架：“我负责【模块】，在【条件】出现【现象】；通过【日志／波形／调试证据】定位到【根因】，采用【修改】并用【复现场景】验证。”括号必须填真实事实；没有实测数字就不编造改善幅度。

### 项目问题的定位过程怎么讲，是直接查手册吗？

**简答**：先确认现象与复现条件，沿数据路径缩小范围；结合日志、返回码、寄存器、波形或故障现场提出假设，再查手册核对具体时序／限制，用最小实验验证假设，修复后复测原场景与相关边界。

**补充理解**：手册用于解释和核对证据，不能代替定位过程。面试应说清每一步观察到了什么、排除了什么，以及为什么采取下一步；没做过的排查步骤不能当作个人经历。

### 平时用哪些 AI 工具，面试怎么回答？

**简答**：只说实际用过的工具和用途，例如用当前 AI 助手解释知识、梳理资料或辅助分析代码；再说明自己如何核对和验证。其他工具仅在确实用过时补充，不罗列未使用的产品。

**补充理解**：表达框架：“我使用【真实工具】辅助【实际工作】，核心判断由自己完成，代码会阅读、编译并按场景验证。”不把学习整理说成已经上线使用或获得实际效果。

### 如何判断 AI 输出可靠，防止 AI 幻觉？

**简答**：将关键结论与官方手册、API 文档和当前源码交叉核对，确认芯片、版本与配置适用；检查代码逻辑、边界、生命周期及并发风险，再编译、做针对性测试，硬件时序和功耗等需实测。要求能追溯的证据，并检查引用是否真的支持结论。

**补充理解**：能编译不代表行为正确，另一个 AI 的认可也不能代替证据。无法验证时保留不确定性，避免把猜测写成工程事实。

## 九、控制算法

### PI 与 PID 怎样选型，微分环节有什么弊端？

**常见问法**：何时用 PI 或 PID；D 项为何可能使控制变差？

**简答**：PI 用比例调节响应、积分改善稳态精度，结构较简单；当动态响应和阻尼不足，且测量质量与采样条件允许时，可评估增加微分的 PID。微分反映变化趋势，可改善阻尼，但会放大噪声和量化误差，导致输出抖动；对误差微分还可能因设定值突变产生冲击。

**补充理解**：按被控对象、噪声、采样周期与执行器限制选择，不是 PID 必然优于 PI。常用带滤波的微分、对测量值微分减小设定值冲击，并检查滤波引入的滞后；PI／PID 都需输出限幅、抗积分饱和和稳定采样，D 项不能替代积分消除稳态误差。见 [NI PID 原理](https://www.ni.com/en/shop/labview/pid-theory-explained.html)与[微分冲击处理](https://www.ni.com/docs/en-US/bundle/labview/page/implementing-the-pid-algorithm-with-the-pid-vis.html)。
