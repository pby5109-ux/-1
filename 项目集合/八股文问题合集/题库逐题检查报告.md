## 需要修正或限定的条目

### 1. C049：volatile 的位置不合法，SET／CLR 也不等于原子 TOGGLE

位置：[C 专题第 49 题](D:/APP/project_practice/codex-project/项目集合/八股文问题合集/C语言面试问答精简版.md:572)，错误示例在第 576 行。

原文的 `volatile REG ^= mask` 不是合法的 C 更新语句。volatile 应写在对象／指针所指类型的声明或类型名中，随后执行 `REG ^= mask`；后者仍然是读改写，不因此具有原子性。本机 Arm GCC 已复现原写法语法错误，修正语法后可编译。

此外，原文“优先使用硬件原子置位／清位机制”用于“翻转”题时条件不够。原子 SET／CLR 能直接完成置位／清零，但“先读旧值，再决定 SET 还是 CLR”不自动组成原子翻转。若 A、B 均读到 0 后各自执行一次 SET，最后仍为 1；真正执行两次 TOGGLE 应回到 0。

建议将简答与补充改为：

> 先确认寄存器语义、位号和访问宽度；若芯片提供有原子保证的 TOGGLE／XOR 寄存器，可按手册使用。否则应保护整个读改写过程，或由单一任务管理该位；任务与 ISR、多核、DMA 等并发来源分别按平台同步，不能只靠 volatile。只有 SET／CLR 寄存器时，不可未经论证就把“读取后选择写哪一个”当作原子翻转。
>
> 对象可声明为 volatile 类型，但 `REG ^= mask` 本身不保证原子性；写 1 清零、读有副作用等特殊寄存器仍按手册处理。

依据：[C11 草案 §6.7、§6.7.3](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)。[ST GPIO 官方源码](https://github.com/STMicroelectronics/stm32f4xx-hal-driver/blob/master/Src/stm32f4xx_hal_gpio.c)中 WritePin 直接写 BSRR，而 TogglePin 先读 ODR 再计算并写 BSRR；从该实现可推断，后一整段不能仅因写 BSRR 是原子操作就宣称为并发安全的 TOGGLE。

### 2. C132 附表：堆排序“最好 O(n log n)”缺少条件

位置：[C 专题排序比较表](D:/APP/project_practice/codex-project/项目集合/八股文问题合集/C语言面试问答精简版.md:1457)；附在第 132 题之后。

该格作为宽松上界并非数学上的假命题，但放在“最好时间”一列会让人误认为任何输入和常见实现都需要 n log n 量级工作。允许重复键，且下沉在父节点不小于孩子时立即停止的常见实现，在所有键相等时可以线性完成；关键字互异时最好情况的比较次数为 n log n 量级。

建议把该格写成“允许重复键时可 O(n)；关键字互异时 O(n log n)”，并在表下注明对应常见的遇序已满足就停止下沉实现；平均、最坏 O(n log n) 和迭代额外空间 O(1) 不变。不要把这一限定误解成所有堆实现的性能都完全一样。

依据：[Princeton Algorithms 优先队列页 Web Exercise 1](https://algs4.cs.princeton.edu/24pq/)及其[复杂度表脚注](https://algs4.cs.princeton.edu/cheatsheet/)明确区分重复键与互异键。另以相等键的下沉模型验证，n=16、32、64、128 时比较次数为 42、90、186、378，符合线性增长；这只是所述模型验证，不冒充原资料 C 实现的运行结果。

## 建议补充的边界与措辞

### 3. G072：ISR 临界区应保存并恢复原屏蔽状态

位置：[通用笔记 CRITICAL 条目](D:/APP/project_practice/codex-project/项目集合/八股文问题合集/八股文复习笔记.md:611)，第 616 行仅写“使用对应的中断版接口”。方向正确，但建议补上用法：

```c
UBaseType_t saved = taskENTER_CRITICAL_FROM_ISR();
/* 仅执行适用、短且不会阻塞的操作。 */
taskEXIT_CRITICAL_FROM_ISR(saved);
```

返回值要交给匹配的 EXIT，不能丢弃或无条件开中断。具体接口和适用中断优先级仍按移植规定。依据：[FreeRTOS 官方 API](https://www.freertos.org/Documentation/02-Kernel/04-API-references/04-RTOS-kernel-control/02-taskENTER_CRITICAL_FROM_ISR_taskEXIT_CRITICAL_FROM_ISR)。这是补充，不把现有“使用对应接口”判成相反的错误结论。

### 4. C126：限制快排栈深时，明确较大一侧改迭代

位置：[C 专题第 126 题](D:/APP/project_practice/codex-project/项目集合/八股文问题合集/C语言面试问答精简版.md:1391)。

“受控地递归较小侧可限制栈深”方向正确，建议写明：较小分区递归，较大分区在循环中处理（或由实现保证消除对应尾递归），以得到 O(log n) 的辅助调用栈上界。仅交换两个递归调用的先后次序仍可能有 O(n) 栈深；这项优化也不自动把最坏时间从 O(n²) 改成 O(n log n)。

### 5. C128：n/2−1 和逆向循环的无符号边界

位置：[C 专题第 128 题](D:/APP/project_practice/codex-project/项目集合/八股文问题合集/C语言面试问答精简版.md:1409)。

算法思路正确。若用 size_t 表示 n／下标，n=0、1 时直接计算 n/2−1 会下溢，`i >= 0` 对无符号下标也不能用于终止。建议补一句“先处理 n<2，或使用安全的逆向遍历”；例如：

```c
for (size_t i = n / 2; i > 0; ) {
    --i;
    /* 对索引 i 做下沉调整，函数内部仍需检查孩子边界。 */
}
```

这不是要求改用某个特定整数类型；重点是实现时匹配索引类型与边界。

### 6. G088：数组越界示例的声明与下标分开写

位置：[通用笔记跑飞示例](D:/APP/project_practice/codex-project/项目集合/八股文问题合集/八股文复习笔记.md:781)。

原句“buf[8] 只允许索引 0～7，却写 buf[8]”在意图上能理解，但把声明长度与元素表达式混在一起。建议写成“声明 `uint8_t buf[8];` 后，有效下标是 0～7；访问 `buf[8]` 越界”。这是措辞改善，不改变其越界风险结论。
