## 1. 先给结论

- 如果产品是“手机附近直接查看数据的便携传感器”，选蓝牙LE。
- 如果产品是“分布在农田、大棚或园区，每10～60秒上报少量数据的传感网节点”，选LoRa。
- 结合当前项目的数据特征、“传感网节点”定位和求职展示价值，**推荐把LoRa作为主通信链**。

这不是因为“LoRa比蓝牙高级”，而是因为两者解决的系统问题不同。

## 2. LoRa和LoRaWAN不是一回事

| 名称 | 层次 | 负责什么 |
|---|---|---|
| LoRa | 无线物理层/调制技术 | 把数据通过低速、长距离的无线链路发出去 |
| LoRa点对点 | 自定义应用方案 | 两个或多个LoRa模块直接发自定义数据帧 |
| LoRaWAN | LoRa上方的MAC/网络协议 | 规定终端、网关、网络服务器、入网、安全、上下行窗口等 |

如果只购买两个LoRa模块，一个接传感器节点，一个接笔记本/另一块MCU，实现的通常是**LoRa点对点或自定义星型网络**，不能在面试中直接称为LoRaWAN。

LoRaWAN还需要LoRaWAN网关、网络服务器和入网参数。它的工程价值更高，但不适合在缺少网关和时间的情况下为了名称强行加入。

## 3. 针对当前项目的对比

| 维度 | DX-BT24蓝牙LE | LoRa | 对本项目的影响 |
|---|---|---|---|
| 主要优势 | 手机原生支持、连接简单 | 远距离、低速少数据、穿透/链路预算更好 | 传感节点小包上报更符合LoRa |
| 频段 | 2.4GHz | 常用Sub-GHz，须选择当地法规允许的频段 | 不能随意购买任意频段模块 |
| 手机直连 | 可以 | 普通手机不能直接收LoRa | 换LoRa后必须增加接收端/网关 |
| 数据量 | 适合更高数据率和交互 | 适合低速、短包、低频次上报 | 温湿度等只需十几字节，LoRa足够 |
| 节点休眠 | 低功耗广播时仍定期发广播 | 可在两次上报间完全Sleep | LoRa很适合“唤醒→发一包→休眠” |
| 发射瞬时电流 | 通常较低 | 高发射功率时可达几十mA | 供电和去耦必须按峰值电流设计 |
| 平均功耗 | 取决于广播/连接参数 | 取决于上报周期、发射功率、SF、带宽和重发 | 不能简单说LoRa一定比BLE省电 |
| 下行实时性 | 建立连接后较好 | LoRaWAN Class A通常只在上行后开短接收窗口 | 低功耗与“服务器随时下发”不能同时达到最优 |
| 系统成本 | 一个节点+手机即可 | 至少一个发送节点+一个接收端 | 替换不是单模块成本 |
| 面试差异化 | 与智慧农场BLE经验有重复 | 可讲节点ID、帧、CRC、ACK、重试、链路和网关 | LoRa对当前项目集的增量更大 |

## 4. 为什么“LoRa一定更省电”是错的

平均电流仍然由状态占空比决定：

```text
Iavg = (Isensor × tsensor
      + Itx × ttx
      + Irx × trx
      + Isleep × tsleep) / Tperiod
```

LoRa的优势是发完短包后可以长时间深度休眠，不是发射时电流小。设置过高发射功率、过大Spreading Factor、过多重发或过密的上报周期，都会拉长空中时间并增加平均功耗。

Semtech给出的SX126x系列参考值包括约4.6mA接收电流和约25mA@+14dBm发射电流；这些是芯片/参考条件数据，不是本项目整板实测值。

## 5. 推荐的系统形态

### 第一版：LoRa点对点，先建立完整证据链

```text
传感器节点
STM32F103 + AHT20 + BH1750 + 雨滴 + OLED + LoRa
        ↓ 周期性无线帧
接收/汇聚节点
LoRa + 另一块MCU或USB串口
        ↓
笔记本串口工具/简单上位机
```

这一版不冒充LoRaWAN，但可以完整教学和展示：

- 少量环境数据的二进制打包；
- 节点ID、序号、数据有效位、报警位和CRC；
- 发送成功/超时、ACK、有限重试和丢包统计；
- 无线发送完成中断、LoRa Sleep和STM32 Stop的顺序；
- 多节点的基础星型汇聚。

### 第二版：再决定是否上LoRaWAN

只有当已经具备LoRaWAN网关或可用网络服务器时，再学习OTAA/ABP、DevEUI/JoinEUI/AppKey、Class A接收窗口、ADR和应用载荷。

## 6. 推荐的低功耗时序

```text
RTC唤醒
→ 恢复STM32时钟
→ 唤醒传感器，开始AHT20/BH1750测量
→ 获取雨滴ADC并校验各数据
→ 打包：NodeID + Seq + Flags + T + H + Light + Rain + CRC
→ LoRa从Sleep进入Standby
→ 配置频率/带宽/SF/编码率/发射功率
→ 写FIFO并启动TX
→ 等待TxDone中断，有限超时
→ 可选：打开短ACK接收窗口，最多重试1次
→ LoRa进入Sleep
→ OLED熄屏，其他外设休眠
→ STM32进入RTC Stop 30s；异常时10s
```

## 7. 建议的帧格式

不要继续发送当前BLE中的长ASCII句子。LoRa应尽量使用紧凑二进制帧：

| 字段 | 建议长度 | 说明 |
|---|---:|---|
| Version | 1B | 协议版本 |
| Node ID | 2B | 节点编号 |
| Sequence | 2B | 帧序号，用于发现丢包/重包 |
| Flags | 1B | 各传感器valid位+报警位 |
| Temperature | 2B | 放大10倍后的有符号整数 |
| Humidity | 2B | 放大10倍的无符号整数 |
| Light | 2B | lux，必要时做饱和 |
| Rain | 1B | 0～100% |
| Battery | 2B | 可选，mV |
| CRC16 | 2B | 应用层完整性/快速排查 |

整帧只需约17字节，比ASCII文本更节省空中时间，也更适合讲协议设计。如果底层LoRa硬件已启用CRC，应用层CRC16是否保留可以再根据故障定位需求取舍，不必机械重复。

## 8. 还需要购买或准备什么

LoRa不能只换节点这一端。最小闭环需要：

1. 两个频段和协议参数一致的LoRa模块；
2. 发送节点与接收/汇聚节点各一个主控或其中一端带USB-UART；
3. 合规频段的天线，不可在未接天线时高功率发射；
4. 足够峰值电流和就近去耦的3.3V供电；
5. 明确选择UART透传模块还是SPI射频模块。

### UART模块与SPI模块的取舍

- UART透传LoRa模块：上手快，但与当前DX-BT24透传逻辑相似，可讲的射频状态机较少。
- SX1262等SPI模块：需要掌握SPI、BUSY/DIO中断、命令、FIFO和TX/RX/Sleep状态，教学和面试价值更高，但实现量更大。

如果时间目标是尽快形成可展示项目，可先用UART模块做完整闭环；如果目标是深化嵌入式能力，可选SPI的SX1262模块。最终选型需结合时间、预算、板上空闲引脚和可用接收端决定。

## 9. 对求职展示的建议

你已经有智慧农场中的蓝牙透传、队列、UART DMA和消息内存所有权经验。传感节点如果继续使用蓝牙，主要增量只剩下RTC Stop和模块PWRM0。

换成LoRa后，新增的可讲价值包括：

- 为什么传感网选低速长距离链路；
- 空中时间与平均功耗的关系；
- 多节点帧格式、节点ID、序号、状态位和丢包检测；
- ACK、超时、有限重试和“可靠性与功耗”的取舍；
- 传感器、无线模块和MCU的联合休眠状态机；
- 点对点LoRa、自定义星型网络与LoRaWAN的边界。

因此从“四个项目不重复、秋招面试可追问、能体现系统取舍”的角度，LoRa更值得。

## 10. 当前决策建议

**建议选LoRa，但先做LoRa点对点/自定义星型网络，不立即追求LoRaWAN。**

实施前必须先回答：

1. 节点需要的实际距离和环境（室内、楼层、大棚、户外农田）是什么？
2. 是否接受手机不再直接连节点，数据先到接收/汇聚节点？
3. 已经有LoRa模块吗？如果有，需要确认型号、频段、接口（UART/SPI）和数量。
4. 是要“快速做出可展示闭环”，还是“接受更大改造量，学会SPI射频芯片状态机”？

## 11. 一分钟口试表达

> “我在通信技术选型时比较了蓝牙LE和LoRa。蓝牙的优势是手机可以直接连接，更适合近距离交互；而我的节点每10到30秒只上报十几字节的环境数据，并希望部署在较大范围，所以LoRa的低速、长距离和发完即休眠更匹配。我选择先做LoRa点对点的星型汇聚，没有在不使用网关和网络服务器时把它说成LoRaWAN。节点每次RTC唤醒后采集数据，打包节点ID、序号、有效位和传感器数据，等TxDone后让LoRa和STM32一起休眠。我还对ACK、有限重试和发射参数做取舍，因为LoRa发射峰值电流并不小，它的低功耗来自少量短包和长时间休眠，而不是发射时一定比蓝牙省电。”
