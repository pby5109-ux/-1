2. 先固定三层边界

层级本项目做什么常见误解
应用协议层18B遥测、11B ACK、Magic、NodeID、Sequence、Flags、CRC把Sequence或Flags说成信道/频率
UART/模块接口层STM32通过9600 8N1发送字节，M0/M1切模式，AUX报告模块忙闲把DMA完成说成网关已经收到
LoRa RF层模块内部LLCC68完成调制、发射、接收和解调把自定义点对点协议说成LoRaWAN

当前系统是“串口LoRa模块＋自定义点对点/星型应用协议”。LoRaWAN则包含标准MAC、网关转发和网络服务器，典型结构是星中之星；当前代码没有Join、设备会话密钥、帧计数器和网络服务器，因此不能称为LoRaWAN。

3. 模块必须先完成的一次性配置

当前STM32代码不在启动时执行AT配置，只负责M0/M1、AUX和业务收发。因此两块模块必须事先通过USB转TTL配置，并保存一致参数：

  1. 串口：9600、8N1，与USART3一致。
  2. 传输模式：透明传输，当前18B帧直接交给模块，不带定点模式的目标地址和信道前缀。
  3. LEVEL、CHANNEL、OPENKEY/KEY：两端一致，否则不能可靠互通。
  4. 硬件模式控制：设置AT+SWITCH=1并重启，使M0/M1成为模式输入。
  5. DRSSI：当前解析器按固定18B帧工作，首次联调保持关闭。开启后接收包尾会多一个RSSI字节，必须同步修改网关解析。
  6. 天线和电源：先接匹配天线再发射；模块发射电流约173～174mA，电源必须有足够瞬态能力和就近去耦。
厂商默认值包括LEVEL2、433.15MHz、22dBm、透明传输和高时效模式，但不能因为“默认”就不查询。正式测试前应把两端AT+HELP或逐项查询结果保存为配置证据。

4. 频率和信道

厂商把信道00定义为433.15MHz，之后每增加一个信道编号，中心频率增加1MHz。信道是模块RF配置，不出现在本项目18B应用帧中。两端中心频率不同通常无法通信；附近同频设备越多，碰撞和丢包风险越高。

选信道时要同时考虑当地无线电法规、模块允许范围、天线匹配和现场噪声。不能只因为模块支持433～532MHz就任意使用全部频率。当前课程不替代法规核对，也不把某个频率写成对所有部署都合法。

5. BW、SF、CR和功率如何权衡

参数增大后通常发生什么工程代价
BW带宽符号更短、速率更高、空中时间更短接收灵敏度通常降低，远距离能力变差
SF扩频因子每个符号使用更多扩频码片，处理增益和灵敏度提高符号时间按2^SF/BW增长，速率下降、占空时间和能耗上升
CR编码率冗余增加，对部分错误更有恢复能力有效载荷占比降低，空中时间增加
发射功率链路预算提高发射电流、干扰和法规压力上升；不能解决所有天线和碰撞问题

核心关系：更慢、更窄、更高SF通常换来更强接收能力，但每包占用信道更久；更快、更宽、更低SF可缩短空中时间和单包能量，却可能缩短距离。最大发射功率和最大SF并不是“最优设置”，因为长空中时间会提高碰撞概率并拖慢ACK。

dBm是对数单位。功率增加3dB约为2倍，增加10dB为10倍。22dBm约等于158mW射频输出，但不等于模块只消耗158mW；模块手册在默认参数下给出的发射电流约173mA。

这还没有加入LoRa前导码、物理头、模式切换、网关解析、收发转换和两段UART时间。因此300ms在LEVEL2下只能称为一个可能可用的初值；在LEVEL0下仅净荷时间就超过300ms，必然不够。最终超时应根据逻辑分析仪测得的ACK往返时延分布设置，例如取高分位值再留裕量，不能凭感觉确定。

7. 链路预算与距离为什么不能只看“8km”

链路预算的简化思想是：

接收余量 ≈ 发射功率 + 发射天线增益 + 接收天线增益
          - 路径损耗 - 馈线/连接/遮挡损耗 - 接收灵敏度门限

模块给出的22dBm和-134dBm可形成很大的理论预算，但8km是特定空旷、天线高度和参数下的参考值，不是产品保证。实际距离还受天线匹配、安装高度、金属遮挡、地面反射、供电跌落、同频干扰、湿度和测试环境影响。

距离不足时不要第一步就把功率开满。先核对天线、供电、信道/LEVEL一致性和现场噪声，再在法规允许范围内调整功率和速率。

8. M0/M1、AUX和当前状态机

M0M1模式当前用途
00高时效模式节点唤醒后发送和接收ACK
10空中唤醒模式当前节点代码未使用
01AT模式预配置或调试使用，当前运行时未进入
11休眠模式发送流程结束后降低模块功耗

AUX高表示模块正在发送、接收或切换模式；AUX低表示这些忙状态完成。AUX是本地模块状态，不证明远端网关收到数据。

LoraNode_Init → M0/M1=11 → 等AUX低 → initialized=true 每轮发送 → 组18B帧（本轮Sequence固定） → M0/M1=00唤醒 → 等AUX低 → 启动USART3 TX DMA → 等UART完成回调/错误/超时 → 阻塞接收11B ACK，窗口300ms → 校验Magic/Version/Type/CRC/NodeID/Sequence/status → 失败则同帧同Sequence再试一次 → Sequence加1 → M0/M1=11休眠 → 正常30s、异常10s进入MCU Stop

9. 三层完成事件必须严格区分

事件可以证明不能证明

AUX由高回到低本地模块忙状态结束不能证明远端应用校验通过
匹配的合法ACK网关应用至少接收、解析并确认了该NodeID/Sequence不能证明业务存储永久成功，除非ACK语义专门这样定义

10. ACK、重试和“至少一次”语义

当前max_retries=1表示首次发送失败后最多再发一次，总尝试次数为2次。18B帧在进入循环前已生成，因此两次使用相同Sequence。这样如果网关已经收到第一包、只是ACK丢失，第二包会被识别为重复包。

网关对重复包仍然回复ACK，否则节点会继续判定失败；但业务数据、数据库写入或报警动作只执行一次。这形成接近“至少一次送达＋业务去重”的语义，而不是天然的严格一次送达。

重试必须有限，因为每次重试都包含唤醒、发射、接收等待和ACK窗口。无限重试会把通信故障转化为电池耗尽故障，也可能加重信道拥塞。

11. Sequence的价值与当前边界

  • ACK匹配：拒绝其他节点或旧帧的ACK。
  • 重复识别：同NodeID＋Sequence再次到达时标记duplicate。
  • 丢包估计：观察序号间隙，区分首发成功、重试恢复和最终丢失。
  • 当前行为：一次调用无论最终成功失败，退出前都会把Sequence加1。

Sequence是16位，最终会回绕；节点重启又从0开始。PC只缓存最近1024个(NodeID, Sequence)，可以限制内存，但节点刚重启时仍可能与缓存中的旧键冲突。可选改进是增加Boot/Session ID、把Sequence持久化或给去重项加时间有效期；这些都尚未实现。

12. 多节点时NodeID为什么不够

多个节点在同一透明信道上传时，NodeID只能让网关知道“数据属于谁”，无法避免两个节点同时发射造成的空中碰撞。尤其所有节点同时上电并采用完全相同的30秒周期时，很容易长期同步碰撞。

策略作用代价
随机抖动每周期增加小随机偏移，打散长期同步周期不再完全固定
指数/随机退避失败后等待随机窗口再重试增加最坏时延和状态机复杂度
时隙给节点分配固定上传窗口需要时钟同步和节点管理
分信道把节点分散到不同中心频率网关需要多接收资源或切换信道
LBT发送前监听信道是否忙增加监听功耗和时延，仍不能完全解决隐藏节点

模块支持LBT和噪声阈值配置，但当前固件没有自动配置或测试。厂商建议先查询现场噪声再设置阈值；开启LBT不能直接宣称“不会碰撞”。

13. RSSI怎样使用，以及为什么不能直接开启

模块开启AT+DRSSI=1后，会在接收数据包尾部追加1字节RSSI。厂商换算示例为：

RSSI_dBm = -(0xFF - rssi_byte)
例如AB：-(255 - 171) = -84 dBm

当前PC网关按固定18B遥测帧寻找和解析；若直接开启DRSSI，接收侧将看到“18B应用帧＋1B RSSI”，现有解析器可能把RSSI当成下一段垃圾字节。正确做法是先确定模块串口输出的包边界，再由网关把最后1B作为链路元数据剥离，18B仍交给应用协议解析，并把RSSI单独写入CSV。

RSSI只反映接收功率，不等同于包质量，也不能单独预测丢包。测试时要同时保存距离、环境、天线高度、LEVEL、功率、RSSI和成功率。

14. PC网关代码的工程价值

串口任意大小chunk → 追加到buffer → 搜索A5 5A → 不足18B继续等待 → 凑18B校验Version/Type/CRC → 失败仅滑动1B重新找Magic → 成功解析NodeID/Seq/Flags/数据 → 判断duplicate → 先写11B ACK并flush → 再写CSV和终端日志

“先ACK、后日志”用于缩短往返时延，避免CSV磁盘写入或终端输出拖慢ACK。去重集合限制为1024项，避免网关长期运行导致内存无限增长。重复帧仍产生ACK，但日志标记duplicate=true。

当前网关仍有明确边界：没有串口断线自动重连；没有业务范围校验；Flags尚未展开成人类可读字段；没有RSSI尾字节支持；CRC不提供身份认证和防篡改；CSV写入失败可能使进程退出。这些是后续改进方向，不是已经实现的能力。

16. 六棵核心故障树

16.1 完全收不到上行

  1. 检查USART3 TX是否有9600 8N1波形，DMA是否完成。
  2. 检查M0/M1是否确实为00、AT+SWITCH=1是否已保存并重启。
  3. 检查AUX是否经历忙高和完成低，模块供电在发射瞬间是否跌落。
  4. 核对两端MODE、LEVEL、CHANNEL、OPENKEY/KEY。
  5. 检查天线、共地、TX/RX交叉、USB转TTL逻辑电平。
  6. 检查PC COM口、波特率、网关进程和流式解析统计。

16.2 AUX一直高

  1. 万用表/逻辑分析仪确认引脚真实电平，排除GPIO模式或引脚接错。
  2. 观察M0/M1切换前后时序，确认没有悬空。
  3. 检查模块是否持续发送/接收、是否进入异常模式或供电反复跌落。
  4. 达到100ms模式超时后记录LORA_NODE_MODE_TIMEOUT，不能无限等待。

16.3 UART完成但没有ACK

UART完成只排除了MCU本地发送未结束，后续仍可能是模块未RF发射、RF上行丢失、网关CRC拒绝、网关ACK未发、下行丢失、ACK错位或300ms过短。沿AUX、网关原始串口、网关日志、ACK TX、节点RX逐段找断点。

16.4 CRC持续失败

检查波特率/数据位、应用版本和帧长度；确认没有把ASCII十六进制文本当原始二进制；确认DRSSI没有额外追加1B；检查Magic错位、串口丢字节和C/Python大小端一致性。CRC失败时滑动1B重同步，不能直接丢掉整段18B。

16.5 距离明显不足或丢包高

依次检查天线匹配和位置、发射瞬态供电、LEVEL/信道一致性、现场同频噪声、金属遮挡和测试高度；最后再调整速率与功率。保存每次改动前后的同条件数据，不能只凭一次“能不能收到”下结论。

16.6 休眠电流明显过高

检查M0/M1是否11、AUX是否完成、AT+SWITCH=1是否生效、SleepRadio是否失败；再检查MCU是否真正进入Stop、OLED/BH1750/雨滴板和稳压器静态电流、GPIO上拉及反向供电。模块手册6µA只代表模块默认条件下的休眠电流，不等于整板休眠电流。

17. 到货后的实物测试顺序

  1. 单模块AT核对：保存两块模块的HELP、MODE、LEVEL、CHANNEL、SWITCH、DRSSI、POWE和KEY状态。
  2. 模块对传：先用两台USB转TTL和串口工具验证透明传输，不接STM32，隔离RF/模块配置问题。
  3. PC网关联调：安装pyserial，确认COM口持续收流、动态ACK和CSV。
  4. 节点闭环：接STM32，验证18B上行、11B ACK、NodeID/Sequence匹配。
  5. 时序记录：逻辑分析仪同时看STM32 TX/RX、M0、M1、AUX；标记唤醒、UART结束、AUX结束、ACK首字节和休眠时刻。
  6. 故障注入：关闭网关，确认总共尝试2次后仍进入休眠；发送坏CRC不ACK；重复Sequence仍ACK但业务只记录一次。
  7. 距离/RSSI：固定天线高度、LEVEL、功率、信道、周期和包数，分距离保存CSV。
  8. 功耗：分别测采集、UART/RF发射、等待ACK、模块休眠和MCU Stop阶段，计算周期平均电流。

丢包统计要区分：

首发成功率 = 首次就收到匹配ACK的包数 / 总业务包数
重试恢复率 = 首次失败但重试成功的包数 / 首次失败包数
最终丢包率 = 两次均失败的业务包数 / 总业务包数

19. 功耗计算与测量限制

周期平均电流不是把几个电流直接相加，而是按持续时间加权：

Iavg = (I采集×t采集 + I发射×t发射 + I等待ACK×t等待 + I休眠×t休眠) / T周期

万用表平均档可能漏掉173mA级短发射脉冲；更可靠的方法是电流分析仪，或在供电回路串小采样电阻并用示波器测压降。没有这些仪器时可以给出理论预算和测量方案，但不能宣称已经得到真实平均电流。

21. 高频追问的标准结论

  1. 为什么不用BLE？BLE适合近距离手机交互；当前场景节点分散、短包低频且网关集中，LoRa更适合远距离低速上传。代价是速率低、空中时间长，并需要自建网关和协议。
  2. 为什么不是LoRaWAN？当前是两端串口模块透明传输加自定义ACK，没有LoRaWAN的Join、网络服务器和标准MAC，系统更简单但扩展、安全和网络管理需要自己实现。
  3. 为什么有Flags？传感器失败时保留数值可能无法区分旧值和新值，valid位让网关知道每项数据是否可信；alert位快速表示本轮是否异常。
  4. 为什么要Sequence？用于ACK匹配、识别重复、同帧重试和统计丢包；NodeID只说明来源。
  5. 为什么重试同一个Sequence？这是同一个业务数据包，若只是ACK丢失，网关可识别第二次为重复而不重复入库。
  6. 为什么最多一次重试？提高偶发丢包恢复率，同时限制发射功耗、阻塞时间和信道占用，避免故障时无限耗电。
  7. AUX低是否表示网关收到？不是，只表示本地模块忙状态结束；必须收到合法匹配ACK才能证明网关应用确认。
  8. 为什么300ms不能直接相信？它取决于LEVEL、空中时间、模块切换和网关处理。LEVEL0仅29B净荷往返就约690ms，最终必须实测。
  9. 为什么不能把功率和SF都开最大？虽然可能提高链路预算，但会增加发射能耗和空中时间，提高碰撞概率并拉长ACK等待。
  10. CRC通过说明什么？只说明字节和CRC自洽；还要检查版本、类型、Flags、范围、NodeID、Sequence和时效，CRC也不提供鉴权。
  11. 多节点怎样避免碰撞？NodeID不能避免碰撞，应采用随机抖动/退避、时隙、LBT或分信道，并用统计数据选参数。
  12. 低功耗怎样形成闭环？减少活跃时间、有限重试、模块M0/M1休眠、STM32 RTC Stop，并管理OLED/BH1750等外设；最后用分状态电流与持续时间计算平均电流。
