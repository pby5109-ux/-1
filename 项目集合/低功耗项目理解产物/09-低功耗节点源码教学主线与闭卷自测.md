## 1. 项目定位：一句话到一分钟

### 结论

这是一个**电池供电、长期无人值守、每15分钟通过 LoRa 上报一次环境数据的 STM32 节点**，配套一个 PC 侧串口网关负责收帧、回 ACK、记录传感故障。它的技术含量不在"接了三个传感器"，而在于**用一个绝对时间基准把采集、显示、上报和休眠串成一条可解释的时序**，并把每个外设都放回它该有的功耗状态。

### 源码证据

- 平台与总线：`STM32F103C8T6`，HAL 裸机超级循环，无 RTOS（`Core/Src/main.c:501` 主循环）。
- 采集：AHT20 温湿度、BH1750 光照、雨滴模块 ADC（`Core/Src/main.c:546`–`556`）。
- 上报：默认构建走 USART3 文本（BLE），`LoRaDebug` 构建走 18 字节二进制帧（`Core/Src/main.c:587`–`638`）。
- 睡眠：RTC Alarm 每 900 秒唤醒，业务做完进 Stop（`Core/Src/main.c:123`、`334`–`415`）。

### 讲解

- **节点 vs 网关**：节点是电池约束方，追求平均电流；网关长期供电，可以"奢侈"地做 CRC 校验、去重和写文件。两边的设计目标不同，所以协议要在**节点侧尽量简单**（18 字节、定长、无握手协商），在**网关侧尽量稳**（流式组帧、坏帧滑动重同步）。
- **为什么低频**：温湿度和光照都是慢变量，人在手机上看的是"今天棚里多少度"，不是"每秒多少度"。把周期从 5 秒拉到 900 秒，把休眠占空比推高，是这类项目最有效的一招。
- **为什么它和智慧农场不重复**：农场是 FreeRTOS 多任务 + IPC + 蓝牙交互，考的是 RTOS；这个项目是裸机 + 精确时序 + 通信可靠性 + 功耗账，考的是"能不能把整机功耗算清楚、把无线链路讲诚实"。

### 答辩口径（30 秒）

> "我做的是一个 STM32F103 的低功耗环境传感节点：AHT20 温湿度、BH1750 光照、雨滴模块 ADC 三路采集，平时每 15 分钟由 RTC Alarm 唤醒一次，采集、判阈值、通过串口 LoRa 模块发一帧 18 字节遥测，等网关 ACK，然后让外设和模块都回到低功耗状态再进 Stop。板上有按键可以随时看屏，看屏不改变上报周期。PC 侧我写了网关程序，负责流式收帧、CRC 校验、回 ACK 和记录传感器故障。休眠电流是我这边电池侧测到的 54µA，平均电流按阶段电流和占空比积分算出来的；无线距离、RSSI、丢包率和模块休眠电流目前没有实测数据，我不把这些当成绩讲。"

### 闭卷自测

1. 用一句话说清"节点"和"网关"在功耗与可靠性上的分工差异，并各举一个源码里的具体设计。
2. 周期为什么可以做成 15 分钟？如果老板要求改成 10 秒，你会怎么回答？

**答案要点**

1. 节点受电池约束 → 协议和流程尽量简单、尽快睡：定长 18 字节帧、平时只发不接（只在等 ACK 时开短收窗）、发完立刻 `SleepRadio` 再 Stop（`BSP/Src/lora_node.c:197`–`199`）。网关长期供电 → 稳定性优先：流式缓存凑帧、CRC 不过就滑动一字节重同步、重复帧也回 ACK（`tools/lora_gateway.py:93`–`141`）。
2. 温湿度/光照是慢变量，采样频率高于变化速度没有信息增益，只会线性拉高平均电流（每多一次采集就多一段 90mA 活动时间）。要改成 10 秒，先要给出新的能量预算和理由（比如需要捕捉降雨突变），并接受续航成倍缩短，而不是只改一个数字。

## 2. 代码结构与两种构建

### 结论

工程一份源码、两个构建：`Debug` 走 BLE 文本上报，`LoRaDebug` 走 18 字节二进制帧 + ACK。协议层、节点状态机层、应用层、PC 网关层职责分离，`main.c` 只做"采集—判定—上报—显示—睡"的业务编排。

### 源码证据

- 构建开关：`CMakeLists.txt:15` 的 `option(SENSOR_COMMUNICATION_LORA ...)`，`CMakeLists.txt:74`–`76` 展开为编译宏 `SENSOR_COMMUNICATION_LORA`，`main.c` 用 `#if SENSOR_COMMUNICATION_LORA` 切分支。
- 分层：
  - `BSP/Src/lora_protocol.c`：纯字节协议（大端读写、CRC16-CCITT、遥测/ACK 编解码），不碰 GPIO、不碰 UART。
  - `BSP/Src/lora_node.c`：硬件状态机（M0/M1、AUX、DMA 发送、等 ACK、重试、序号）。
  - `Core/Src/main.c`：业务（采集、阈值、valid/flags 打包、显示、Stop）。
  - `tools/lora_gateway.py`：PC 侧流式收帧、ACK、故障日志。
- 设备驱动：`BSP/Src/aht20.c`、`BSP/Src/light.c` + `light_i2c.c`（软件 I²C）、`BSP/Src/rain.c`、`BSP/Src/oled.c`。

### 讲解

- **为什么保留两套**：BLE 版本是"现场可读"的历史版本，上位机用手机蓝牙就能看到文本；LoRa 版本是"远距离、可组网"的工程版本。双构建让改造可回退，也让面试时能讲清"我是在一个已经工作的系统上做增量，而不是重写 Demo"。
- **协议层为什么不碰硬件**：`lora_protocol.c` 只依赖 `stdint/stdbool/stddef`，所以同一份逻辑可以放到 PC 用 Python 重写做交叉验证（`tools/test_lora_gateway.py` 就是这么做的）。这是"协议要有测试向量"的最小实践。
- **旧代码保留策略**：停用的远程阈值、OLED 常显、连续光照模式都用 `#if 0` 或 `OLD:` 注释保留在原地（例如 `main.c:39`–`45`、`main.c:121`、`BSP/Src/light.c:56`–`61`）。好处是能随时对照"为什么改"；代价是读代码时要分清哪段在编。

### 闭卷自测

1. 说出四个文件的职责边界，并指出哪一个文件不含任何 GPIO/UART 调用。
2. `Debug` 和 `LoRaDebug` 的差别在哪一行代码上？为什么不用两份源码？

**答案要点**

1. `lora_protocol.c`（纯协议）/`lora_node.c`（硬件时序与状态机）/`main.c`（业务与调度）/`lora_gateway.py`（上位机）；不含硬件调用的是 `lora_protocol.c`。
2. 差别在 `CMakeLists.txt:15` 的 CMake 选项展开为 `SENSOR_COMMUNICATION_LORA` 宏，`main.c` 用条件编译切上报路径。共用一份源码才能保证采集、阈值、功耗策略这些"必须一致"的部分不会在两份副本里漂移。

## 3. 运行节拍：900 秒基准 + 按键 10 秒窗口

### 结论

系统里同时存在**两条独立期限**：采样期限（绝对 RTC 时刻，900 秒栅格）和显示期限（按键触发，10 秒窗口）。按键只影响显示，不推迟采样；两条期限谁先到就睡到谁，醒来后各按各的规则处理。

### 源码证据

- 常量：`main.c:122`–`124`（`OLED_VIEW_SECONDS 10`、`SENSOR_PERIOD_SECONDS 900`、`OLED_BUTTON_DEBOUNCE_MS 20`）。
- 绝对期限递推（不是 `now + 900`，而是在 900 秒栅格上推进，错过就跳下一格）：
  ```c
  if (first_sample) { sample_deadline = now + SENSOR_PERIOD_SECONDS; }
  else { do { sample_deadline += SENSOR_PERIOD_SECONDS; } while (RTC_TimeReached(now, sample_deadline)); }
  ```
  `main.c:525`–`533`。
- 按键：`PC13` 下降沿 EXTI，ISR 只置位（`main.c:767`–`773`）；主循环里 20ms 消抖 + 清标志 + 确认电平（`main.c:287`–`316`）。
- 关屏时按键 → 只置 `display_sample_requested`（`main.c:313`）；亮屏时按键 → 立即 `OLED_PowerOff`（`main.c:306`）。
- 采集后开屏显示、并设 10 秒期限（`main.c:642`–`647`）：
  ```c
  if (display_sample) { OLED_PowerOn(); OLED_RefreshSensorValues(); display_deadline = RTC_ReadCounter() + OLED_VIEW_SECONDS; }
  ```
- 下一次睡眠取两者较早值（`main.c:676`–`683`）：`next_deadline = min(sample_deadline, display_deadline)`。
- 按键请求与周期同时到期时合并一次采集：`sample_due || display_sample` 共用同一段采集代码（`main.c:518`–`521`），但**只有 `sample_due` 才发无线**（`main.c:587`）。
- 时间基准：RTC 用 LSE 32.768kHz，`AsynchPrediv = RTC_AUTO_1_SECOND` → 计数 1Hz（`Core/Src/rtc.c:44`–`46`、`Core/Src/main.c:738`–`740`）。
- 读计数器用"高-低-高"三读防进位撕裂（`main.c:238`–`252`），比较用有符号差值防回绕（`main.c:254`–`262`）。

### 讲解

- **为什么必须是绝对期限**：处理耗时、按键唤醒、I2C 重试都会让一轮的实际长度抖动。如果每轮都写 `deadline = now + 900`，误差会被逐轮累积，节拍越跑越偏；用 900 秒栅格递推，长期平均周期精确，代价是单次采集时刻可能有不到一轮的抖动。
- **为什么按键不能推迟采样**：如果按键会重置采样期限，那么"频繁按屏"的设备就会永远不上报——这是把交互行为耦合进业务周期的经典错误。这里两条期限完全独立，还顺手解决了"按键恰好和周期撞车"的情况：合并一次采集，不重复动作。
- **10 秒不是精确的 10.000 秒**：RTC 只有 1Hz 计数，量化误差 <1 秒，再加上关屏收尾的执行时间，所以只能说"约 10 秒"。要说精确 10.000 秒就得换更细的 RTC 时间基（比如把 `AsynchPrediv` 改小）。
- **Sleep-on-exit 的省电技巧**：按键后只是"显示"这一件事在计时，画面靠 OLED 自己保持，MCU 在这 10 秒里可以继续 Stop（`main.c:394`–`396`），不需要忙等。

### 闭卷自测

1. 画出一轮完整时序：上电首次、周期到期一次、关屏按键一次，分别发生了什么，什么时候睡、睡到哪个时刻。
2. 为什么关屏按键只让 `display_sample_requested = true`，而不直接 `OLED_PowerOn()`？如果直接开屏会出什么问题？
3. 按键"不推迟周期"这个约束，在源码里体现在哪一行？

**答案要点**

1. 上电：`first_sample = true` → 立即采集 → 上报（BLE/LoRa）→ 下次期限 = `now + 900` → Step 到 `min(采样期限, 显示期限)`。周期到期：采集 → 上报 → 900 栅格推进 → 睡到下一格。关屏按键：EXTI 置位 → 主循环消抖确认 → 置请求标志 → `continue` 回去立刻采集 → 开屏 → 显示 → 显示期限 = `now + 10` → 睡到 `min(采样期限, 显示期限)`；期间不再上报。

## 4. 采集与失败语义：valid 位 + 哨兵值

### 结论

一次采集失败，**不允许拿上一次的旧值冒充本次有效数据**。板内用"本次是否有效"的标志 + 哨兵值表示失败，OLED 显示 `ERR`，无线帧里用 `flags` 的 valid 位 + 约定哨兵表达，网关再按 valid 位归一成 `-1` 和 `sensor_errors`。业务越阈值和采集失败是两件事，不能混。

### 源码证据

- 三路采集与失败处理（`main.c:546`–`556`）：
  ```c
  aht_ok = AHT20_Measure();
  if (aht_ok != 0U) { temp = AHT20_Temperature(); humi = AHT20_Humidity(); }
  else { temp = -50.0f; humi = -1.0f; }
  light_ok = Light_ReadOnce(&light);
  rain_ok = (Rain_ReadPowered(&rain_raw, &rain_percent) == HAL_OK) ? 1U : 0U;
  if (!light_ok) { light = UINT16_MAX; }
  if (!rain_ok) { rain_percent = UINT8_MAX; }
  ```
- AHT20 自身的检查：发送/接收返回 `HAL_StatusTypeDef`、读回后判 Busy 位（`readBuffer[0] & 0x80`）最多重试 5 次、量程检查（湿度 0～100%、温度 −40～+85℃）后才更新（`BSP/Src/aht20.c:78`–`126`）。
- BH1750：单次高分辨率 `0x20` → 等 180ms → 读两字节 → `raw * 10 / 12` 换算勒克斯 → 显式 `0x00` Power Down（`BSP/Src/light.c:41`–`53`）。
- 雨滴：`PB14` 使能高边开关 → 等 20ms → ADC 软件触发 8 次取平均 → `dry/wet` 线性映射成 0～100% → 关 `PB14`（`BSP/Src/rain.c:28`–`71`）。
- 阈值（业务语义，与 valid 无关）：温度 25～35℃、湿度 45%～70%、光照 ≥1000lx、雨滴 ≤60%（`main.c:114`–`119`、`main.c:578`–`584`）。
- 帧内表达（`main.c:591`–`602`）：`flags` 的 bit0/1/2 分别是 AHT/光照/雨滴本次有效，bit7 是 ALERT（`BSP/Inc/lora_protocol.h:9`–`12`）；当前已提交源码在AHT失败时设`temp=-50.0f`，所以温度原始字段`temp*10 = -500`（旧资料写`-10`已过时），湿度失败发 `0xFFFF`，光照失败发 `0xFFFF`，雨滴失败发 `0xFF`。网关按valid位统一显示无效温湿度为`-1`，不直接显示空口占位值。
- 网关侧归一（`tools/lora_gateway.py:145`–`164`）：按 valid 位决定输出数值还是 `-1`，并生成 `sensor_errors: ["aht20", ...]`；只有 `sensor_errors` 非空才写故障 CSV（`tools/lora_gateway.py:167`–`188`）。仅业务越阈值会置ALERT并在终端JSON的flags中可见，当前网关不另写阈值告警文件或推送警报。

### 讲解

- **为什么要 valid 位而不是"用 −1 表示失败"**：真实温度 −1℃ 是合法值。网关如果把 −1 当失败，就会把正常数据误报成故障。判据必须来自"本次测量是否成功"这个独立信息，而不是从数值反推。
- **为什么失败不能沿用旧值**：沿用旧值会在屏幕上造成"设备看起来一直正常"的假象，掩盖传感器断线；工程上宁可显示 `ERR`，也不要展示无法追溯来源的数据。
- **雨滴百分比是相对湿润度**：`RAIN_ADC_DRY_CALIBRATION 4095` / `RAIN_ADC_WET_CALIBRATION 0` 只是占位标定（`BSP/Inc/rain.h:13`–`14`），必须上板实测干燥和浸湿的原始 ADC 再替换；现在的百分比不能讲成"降雨量 mm"。
- **ADC 采样参数**：`PB1 = ADC1_IN9`，软件触发、单次转换、239.5 周期采样时间，ADC 时钟 = PCLK2/6 = 12MHz（`Core/Src/adc.c:52`–`62`、`Core/Src/main.c:740`）。

2. 为什么"采集失败"和"温度超过 35℃"在帧里的表达方式不同？各用哪个字段？

**答案要点**

1. valid=1 时 −1℃ 是合法测量，网关输出 `temperature_c: -1.0`、`sensor_errors` 为空、不写故障 CSV；valid=0 时网关输出 `-1` 并把 `"aht20"` 放进 `sensor_errors`，写故障日志。OLED 侧两者显示不同：valid=1 显示 `T=-1.0 C`，valid=0 被替换成 `T=ERR`（`main.c:272`–`277`）——OLED 只做现场粗看，判据一律以帧内 valid 位为准。
2. 越阈值是"数据有效但关心"→ 保留真实数值，置 `FLAG_ALERT`（bit7）；采集失败是"数据不可信"→ 清对应 valid 位，发约定哨兵值。前者进业务告警，后者进故障日志，处理路径不同。
3. 连续高分辨率模式（`0x10`）会持续按 120ms 左右周期转换，两次采集之间仍在耗电；单次模式（`0x20`）转换一次后自动 Power Down，采集完成再显式发 `0x00` 兜底（`BSP/Src/light.c:6`–`16`、`41`–`53`）。

## 5. 整机功耗与供电门控

### 结论

MCU 进 Stop 只解决"MCU 自己"，整机功耗由"每个器件在非工作时段处于什么状态"决定。当前源码已经对 OLED 和雨滴模块做了真正的电源门控（含总线隔离），BH1750 用单次模式自关机，AHT20 靠自身待机，LED 在 Stop 前关闭。

### 源码证据

- 引脚：`PB12 = OLED 电源使能`、`PB13 = OLED 专用 I²C 支路使能`、`PB14 = 雨滴模块电源使能`（`Core/Inc/main.h:63`–`68`），复位后全部输出低（`Core/Src/gpio.c:63`）。
- OLED 上下电顺序：
  - 上电：`PB12 = 1` → 等 10ms → `PB13 = 1` → 等 1ms → `OLED_Init()`（`BSP/Src/oled.c:111`–`126`）。
  - 断电：`0xAE` 停显示驱动 → 等 1ms → `PB13 = 0` 隔离总线 → `PB12 = 0` 断电源（`BSP/Src/oled.c:128`–`139`）。
- 默认关机：`main.c:455`–`459` 的旧 `OLED_Init()` 被 `#if 0` 掉，OLED 由按键打开。
- BH1750 上电即 Power Down：`main.c:465`–`466` 调用 `Light_PowerDown()` 而不是 `Light_Init()`。
- 雨滴：`Rain_ReadPowered()` 内部"使能 → 20ms 稳定 → 采样 → 断电"（`BSP/Src/rain.c:61`–`71`）。
- Stop 前关状态灯：`Enter_Stop_Until()`将`PA7`、`PB0`写低。
- 能量账（**用户报告的电池输出侧阶段平均电流**，不是本次固件复测）：活动 0.9s/90mA、休眠 54µA、纯显示 10s/60mA；1500mAh 取 90% = 1350mAh；每天 96 次周期 + 1 次按键采集但不上报。
  | 阶段 | 每天时间 | 电流 | 日耗电 |
  |---|---:|---:|---:|
  | 采集（周期 96 次 + 按键 1 次） | 87.3s | 90mA | 2.1825 mAh |
  | 纯显示 | 10s | 60mA | 0.1667 mAh |
  | 休眠 | 86302.7s | 0.054mA | 1.2945 mAh |
  | 合计 | 86400s | 平均 151.82µA | 3.6437 mAh/天 |
  理论续航 1350 ÷ 3.6437 ≈ **370.5 天**（连续积分模型，不是跑了一年）。

### 讲解

- **门控不是"断电越多越好"**：OLED 断电是拿"上电稳定 10ms + 重新初始化 + 重画显存"换静态电流，值不值得取决于实测残流。这里之所以必须连**总线支路**一起断，是因为 OLED 与 AHT20 共享 I²C1：只切 OLED 的 VCC，AHT20 通信时的高电平仍可能经 OLED 的 I/O 保护结构倒灌，或让 OLED 板载上拉拖住总线。所以顺序是"先断信号、再断电源"，上电顺序相反（先电源、后信号）。
- **GPIO 不能直接给模块供电**：`PB12/PB13/PB14` 只驱动高边负载开关的 EN/栅极，电流路径是 `3V3 → 负载开关 → 模块 VCC`。GPIO 的驱动能力和保护都不允许它当电源用。
- **Stop 前把未用 GPIO 设成模拟输入**：浮空数字输入在阈值附近可能来回翻转，增加输入缓冲级电流。但这不是万能药——它不移除外部上拉、不隔离器件漏电、也不解决跨电源域倒灌，所以只能对**已核对的未分配引脚**做（见第 6 节）。
- **平均电流的正确写法**：`Iavg = Σ(I_state × t_state) / T`，单位是 mA，不是 mA/s 也不是 mA/h。说续航时必须同时给出假设（容量、降额、占空比、电流来源），否则就是把模型讲成实测。

### 闭卷自测

1. 为什么关 OLED 要先断信号再断电源，开的时候顺序反过来？如果只断电源不断信号会发生什么？
2. 用给出的阶段电流算一次平均电流和理论续航（可以用 900 秒周期、每天 96 次）。这个数字能不能写成"实测续航 12 个月"？
3. 雨滴模块断电采样会带来什么风险？为什么不能把断电时的 ADC 读数当成"干燥"？

**答案要点**

1. 断电的器件若仍被 SCL/SDA 的常供电高电平拉动，可能经其 I/O 保护二极管反向供电，出现"半上电"、额外漏电和初始化异常；先隔离信号就切断了这条路径。反过来，上电时若信号已经在，而 VCC 还没稳，同样可能通过信号线给未上电的器件灌电，所以要先电源后信号（`BSP/Src/oled.c:111`–`139`）。
2. `(87.3×90 + 10×60 + 86302.7×0.054) / 86400` = `3.6437mAh/86400s` → 平均 151.82µA；1350/3.6437 ≈ 370.5 天 ≈ 12.2 个月。不能写成"实测续航"：容量是标称值乘降额，阶段电流是用户侧阶段测量，且未计自放电、老化、低温、重试和失败路径，只是**连续积分模型**。
3. 断电期间 AO 无有效含义，即使 ADC 返回 `HAL_OK` 也可能读到低值而被映射成 100% 湿润（`BSP/Src/rain.c:5`–`26` 的映射会把低值判为"湿"）。所以必须"上电—稳定—采样"并按 valid 位标注有效性；代价是只能在采样窗口检测降雨，会漏掉窗口之间的短事件。要做实时触发就得换成常供电的低功耗检测方案。

## 6. Stop、唤醒、时钟与 GPIO 恢复

### 结论

一轮业务的收尾是一条固定顺序：**关外设 → 算好下一个绝对期限 → 写 RTC Alarm → 暂停 SysTick → 临界区复查 → WFI 进 Stop → 醒来恢复Tick及系统时钟 → 继续业务**。确认未使用的GPIO在启动时已设成模拟输入，Stop会保持配置。

### 源码证据

- 完整函数为`Core/Src/main.c`中的`Enter_Stop_Until()`。关键步骤：
  1. 期限已过直接返回，由主循环处理，避免设置过去的闹钟。
  2. 等`RTOFF`，以配置模式写`ALRH/ALRL`的32位绝对计数值，再等写完成。当前F1 HAL的`HAL_RTC_SetAlarm_IT()`按24小时时分秒换算，不能直接替代该绝对期限写法。
  3. 清旧`ALRAF`/EXTI17挂起位，使能RTC Alarm与EXTI17上升沿中断，清PWR唤醒标志。
  4. 关状态灯；未用脚已在启动时由`ConfigureUnusedPinsAnalog()`一次配置，不在此处反复保存/还原GPIO寄存器。
  5. `HAL_SuspendTick()`，再以关中断临界区复查“无按键事件且未到期”，满足才调用`HAL_PWR_EnterSTOPMode(PWR_LOWPOWERREGULATOR_ON, PWR_STOPENTRY_WFI)`。
  6. 返回后仅调用一次`HAL_ResumeTick()`，随后`SystemClock_Config()`恢复72MHz；清本次Alarm挂起位并关闭Alarm中断，主循环仍按原绝对期限处理业务。
- 中断入口：`RTC_Alarm_IRQHandler`直接调用`HAL_RTC_AlarmIRQHandler()`，由HAL清`ALRAF`和EXTI17挂起位；`EXTI15_10_IRQHandler`调用`HAL_GPIO_EXTI_IRQHandler(OLED_BUTTON_Pin)`。旧`rtc_alarm_wakeup`标志已删除，业务由RTC绝对期限与按键事件决定。
- 优先级：RTC Alarm = 0，EXTI15_10 = 1，DMA1 CH2/CH3 = 0（`Core/Src/rtc.c:70`、`Core/Src/gpio.c:105`、`Core/Src/dma.c:46`–`51`）。
- 时钟树：HSE + PLL×9 → 72MHz；RTC 时钟源 LSE；ADC = PCLK2/6 = 12MHz（`main.c:712`–`741`）。

### 讲解

- **为什么醒来必须重建时钟**：Stop 会关闭高速时钟，退出后芯片回到 HSI（内部 8MHz 级）。如果直接往下跑，UART 波特率、I²C 时序、`HAL_GetTick` 的节拍全部按错误的主频计算，表现为"串口乱码、I²C 通信失败、超时判断失真"。所以 `SystemClock_Config()` 必须排在外设使用之前。
- **为什么 `HAL_ResumeTick()` 在恢复时钟之前**：`HAL_RCC_OscConfig/ClockConfig` 内部用 Tick 做 HSE/PLL 启动超时判断；Tick 没跑起来，HAL 的超时判断就没有时间基准。
- **为什么现在只初始化一次未用引脚**：Stop保留GPIO配置，这组管脚在当前板上没有运行期用途，因此启动时用`HAL_GPIO_Init()`将它们设为模拟输入即可；每次睡前保存整口`CRL/CRH`和醒后还原属于冗余操作。仍不能把整个GPIO端口统一改成模拟输入，否则会误伤调试口、RTC晶振、通信和电源控制脚。
- **为什么清单里只有这几个脚**：`PA2/3/4/5/6/12`、`PB2/9/15` 是当前核对过的未分配引脚。保留的一侧包括：唤醒源（PC13、RTC 晶振）、调试口、通信口（PB10/PB11、PB6/PB7、PA10/PA11、PA8/PA9/PA1）、电源与模式控制（PB12/13/14）、以及预留的 PA0/PB8。改接线后必须重新核对这张清单，**禁止用"所有 GPIO 一刀切设模拟"这种写法**。
- **临界区堵的是什么窗口**：如果按键中断恰好发生在"最后一次检查标志"和"执行 WFI"之间，标志会被置起来但 CPU 已经睡了；`__disable_irq()` 包住"检查 + WFI"两步，保证事件不会丢。这是嵌入式里典型的 lost-wakeup 问题。
- **Sleep / Stop / Standby 的区别**：Sleep 只停 CPU 内核时钟，外设照跑；Stop 停掉高速时钟，SRAM 和寄存器保持，靠 RTC Alarm/EXTI 唤醒，醒来继续执行；Standby 主要保备份域，唤醒近似复位，不保 SRAM。这里选 Stop 是因为要"保留现场、按绝对时刻继续跑"。

2. 为什么不能写成"把所有 GPIO 设成模拟输入以降低功耗"？至少说出三类必须保留的引脚。
3. 如果醒来后忘了调 `SystemClock_Config()`，你会先观察到什么现象？为什么？

**答案要点**

## 7. LoRa 节点：协议与状态机

### 结论

节点侧就是"**组帧 → 唤醒模块 → 发 → 等匹配 ACK → 最多重发一次 → 让模块睡 → 回业务**"。协议是定长二进制 + CRC；完成事件分四层，不能互相替代。

### 源码证据

- 帧格式（`BSP/Inc/lora_protocol.h:11`–`12`、`BSP/Src/lora_protocol.c:79`–`105`）：
  | 偏移 | 字段 | 长度 |
  |---:|---|---:|
  | 0 | Magic `A5 5A` | 2B |
  | 2 | Version = 1 | 1B |
  | 3 | Type = 0x10 | 1B |
  | 4 | NodeID | 2B |
  | 6 | Sequence | 2B |
  | 8 | Flags | 1B |
  | 9 | Temp×10（有符号） | 2B |
  | 11 | Humidity×10 | 2B |
  | 13 | Light（lx） | 2B |
  | 15 | Rain（%） | 1B |
  | 16 | CRC16 | 2B |
  合计 18 字节，全部大端；CRC 覆盖前 16 字节。
- ACK 帧 11 字节：Magic、Version、Type=0x11、NodeID、Sequence、Status、CRC16（`BSP/Src/lora_protocol.c:133`–`173`）。
- CRC 算法：初值 `0xFFFF`、多项式 `0x1021`、不反射、无末尾异或，即 CRC-16/CCITT-FALSE（`BSP/Src/lora_protocol.c:49`–`74`）；网关侧 Python 实现逐位对齐（`tools/lora_gateway.py:56`–`63`）。
- 模式与 AUX：`M0/M1 = 00` 高时效（发送）、`11` 休眠；`WaitAuxIdle()` 等 AUX 变低，超时 `mode_timeout_ms = 100ms`（`BSP/Src/lora_node.c:10`–`50`、`main.c:483`）。
- 发送与 ACK：`LoraNode_SendTelemetry()`（`BSP/Src/lora_node.c:121`–`200`）：
  1. 组帧；
  2. `WakeRadio()`；
  3. 进入 `attempt = 0 .. max_retries(1)`：等 AUX 空闲 → DMA 发送并等完成 → `HAL_UART_Receive()` 轮询等 300ms ACK → 校验 CRC/NodeID/Sequence/Status；
  4. 无论成功失败，`next_sequence++` 并 `SleepRadio()`。
- DMA 发送等待（`BSP/Src/lora_node.c:54`–`99`）：启动返回 `HAL_BUSY` 时最多重试 3 次；成功后轮询"完成/错误"标志，`uart_timeout_ms = 500ms` 超时则 `HAL_UART_AbortTransmit`。
- 回调只认自己这一次传输：`active_uart` 比对句柄（`BSP/Src/lora_node.c:211`–`228`，`main.c:749`–`765`）。
- 状态灯在 LoRa 构建下反映无线结果：绿色 = 数据正常且 `LORA_NODE_OK`，红色 = 越阈值或发送失败（`main.c:603`–`606`）。

### 讲解

- **四层完成事件**：① `HAL_UART_Transmit_DMA` 返回 `HAL_OK` 只说明 DMA 请求排上了；② TX 完成回调说明 MCU 把字节交给了 UART；③ AUX 变低说明**模块**这边已经空；④ 匹配的 ACK 说明**对端应用**收到了这一帧。这四件事一层比一层强，绝不能把 ① 说成"数据已经到达网关"。
- **两层重试别混**：`TransmitDmaAndWait` 里的 3 次循环只是"UART 忙，重试启动 DMA"，硬件几微秒的事；`max_retries = 1` 才是"没等到合法 ACK，把整帧重发一次"的业务级重试。前者不影响序号，后者重用同一个序号。
- **重试为什么用同一个 Sequence**：同一帧重发仍属于"第 N 次上报"。网关按 `(NodeID, Sequence)` 判重复，第二次收到只回 ACK、不再当作新业务事件；节点的重发是为了拿 ACK，不是为了再报一次数据。
- **为什么允许失败后序号继续前进**：`next_sequence++` 在失败路径上也执行。这样网关看到序号跳变就知道中间丢过帧，而不是被"序号总是连续"掩盖。代价是节点重启会从 `initial_sequence = 0` 重新开始，可能撞上网关保留的近期键——这是已知边界，可以把 Boot/Session ID 纳入协议解决。
- **为什么不能无限重试**：链路长期异常时无限重试会把"通信故障"变成"电池耗尽"。一次重试后无论如何都要回到停当：`SleepRadio()` + 进 Stop，等下个周期再试。
- **为什么 ACK 校验要四件事**：CRC 保证字节没错，NodeID 保证是发给自己的，Sequence 保证对应本次上报（避免把上一次的迟到 ACK 当成成功），Status 保证对端业务认可。少一项都可能把"别人的 ACK"或"过期的 ACK"误判成成功。
- **透传模块的边界**：当前 18 字节是**直接**从 UART 交出去，假设两端模块处于透明传输、信道/速率/空速一致。`NodeID` 是应用层字段，不是模块的定点地址；模块本身不做寻址。

### 闭卷自测

1. 说出 18 字节帧每个字段的长度与含义；温度 −12.3℃ 对应的两个字节是什么？
2. `HAL_UART_Transmit_DMA` 返回 `HAL_OK`、TX 完成回调、AUX 变低、收到匹配 ACK，分别证明了什么？
3. 一次发送"没等到 ACK，重发了一次，第二次成功"，网关会收到几帧？业务侧算几次上报？序号变了吗？
4. 为什么 `-1℃` 的合法温度和"温度采集失败"在帧里可以区分？

**答案要点**

1. 见上表。−12.3 × 10 = −123，16 位补码 = `0xFF85`，大端发送 `FF 85`。
2. `HAL_OK` = DMA 启动请求被接受；TX 完成 = MCU 侧字节已全部发出（不代表模块调制成 LoRa）；AUX 变低 = 模块当前没有发送/接收/切模式动作；匹配 ACK = 对端应用收到并认可这一帧。
3. 网关收到 2 帧，Sequence 相同 → 第二帧标记 `duplicate: true`，仍是**一次**业务上报（`tools/lora_gateway.py:132`–`141`）；序号在整段发送结束后才 +1，重发过程中不变。
4. 温度字段永远发 `temp×10`（失败时是 `-10`），是否可信由 `Flags` 的 AHT valid 位决定；网关先看 valid 位，valid=1 才把 −1.0℃ 当正常值（`tools/lora_gateway.py:145`–`164`）。

## 8. PC 网关：把一个字节流还原成事件

### 结论

串口是**没有消息边界的字节流**，所以网关的核心是"攒字节 → 找 Magic → 凑满 18 字节 → 校验 → 才解释成数据"，然后**先回 ACK，再做打印和落盘**。

### 源码证据

- 入口与参数：`python tools/lora_gateway.py --port COM5`，可选 `--baud/--timeout/--fault-dir`（`tools/lora_gateway.py:221`–`232`）。当前 CLI **只有这四个参数**。
- 流式组帧 `TelemetryStreamDecoder.feed()`（`tools/lora_gateway.py:86`–`120`）：
  - 找 Magic，丢弃前面的垃圾字节；
  - 不足 18 字节就保留（半帧）；
  - 够 18 字节就解一帧；CRC 或字段非法则**只滑掉 1 字节**继续找下一个 Magic（避免跳过内部另一个合法帧头）；
  - 结尾恰好是 `A5` 时不能丢，因为它可能是下一帧的第一个字节。
- 去重与 ACK（`tools/lora_gateway.py:123`–`141`）：`deque(maxlen=1024)` 保留近期 `(NodeID, Sequence)`；重复帧**同样回 ACK**，只把事件标成 `duplicate`。
- 数值归一与故障记录（`tools/lora_gateway.py:145`–`188`）：按 valid 位还原字段，`sensor_errors` 非空才追加 `tools/异常记录/faults-YYYY-MM-DD.csv`（首行写表头），写失败只提示不中断接收。
- ACK 先于打印/落盘（`tools/lora_gateway.py:204`–`215`）：先对本批所有正确帧写回 ACK，再做 JSON 打印和故障 CSV。

### 讲解

- **为什么必须先 ACK 再落盘**：节点只等 300ms。如果先写文件再回 ACK，一次磁盘慢或杀毒扫描就可能让节点超时重发，白耗一次电池。所以 ACK 的语义必须收敛为"**我正确收到了这一帧**"，而不是"我已经持久保存了"。要追求不丢数据，就得改成"先本地可靠落盘再 ACK"（重新做时间预算），或者明确区分"接收 ACK"和"持久化确认"两层语义。
- **去重是有界内存，不是数据库**：1024 项的近期窗口解决的是重发与序号回绕的误判，进程重启即失效；它不是幂等入库，也不解决"节点重启后序号归零撞上旧键"。
- **时间戳的口径**：`received_at` 是**网关收到的本地时间（带时区）**，不是节点的采样时间。要用它做时间轴分析，得在协议里加上节点侧时间或周期性校时。
- **产品化缺口（当前是建议，不是实现）**：串口重连、掉线告警、SQLite 历史库、最新值/趋势界面、进程自启动、磁盘满保护；多节点还要加退避与会话去重；安全上再谈鉴权与抗重放（CRC 只能检错，不是身份认证）。

### 闭卷自测

1. 一次串口读取读到 7 字节，下一次读到 11 字节，网关会怎么处理？为什么不能"读到多少就处理多少"？
2. 为什么 CRC 校验失败时只滑掉 1 字节而不是丢掉这 18 字节？
3. 节点收到 ACK 就一定能保证数据不丢吗？为什么？

**答案要点**

1. 第一次只把 7 字节追加进缓存，因为不足 18 字节不解析；第二次追加 11 字节凑满 18 字节，再按 Magic/Version/Type/CRC 校验，通过才解释成数据并回 ACK。串口读取块与协议帧没有对应关系，拆包/粘包即使无干扰也会发生。
2. 因为"当前 18 字节"可能包含错位的头部：真正的帧头可能落在这 18 字节中间的某个位置，只滑 1 字节能让下一个 `A5 5A` 被重新找到，避免一次坏帧连带丢掉后续合法帧。
3. 不能。ACK 只证明"网关正确收到这一帧"（`tools/lora_gateway.py:209` 的注释也这么写）；故障 CSV 写入可能失败、进程可能被杀、机器可能断电。要更强保证就得先持久化再确认。

## 9. 故障树：现象 → 分层定位 → 证据 → 动作

| 现象 | 先查哪一层 | 可观察证据 | 常见根因与动作 |
|---|---|---|---|
| RTC 不唤醒，一直睡 | 时钟源 | RTC 计数器是否在走、LSE 是否起振 | LSE 未起振/电池域异常；先确认 `RTC->CNTL` 递增 |
| 醒后串口乱码、I²C 失败 | 时钟恢复 | 主频是否为 72MHz | 漏调或提前调 `SystemClock_Config()`；`HAL_ResumeTick` 顺序错 |
| 按键无反应 | 唤醒源 | `PC13` 电平、EXTI 挂起位 | 上拉/接法不是低有效、EXTI 未使能、被设成模拟输入 |
| 按键后屏幕不亮 | 电源/总线时序 | `PB12`、`PB13` 电平 | 只开了电源没接总线，或初始化在电源稳定前 |
| 传感器偶发 `ERR` | 驱动/总线 | AHT20 Busy 位、I²C 返回码 | 上电稳定不足、总线被 OLED 断电拖住、线长/上拉不当 |
| AUX 一直高 | 模块状态 | `PA1` 电平、M0/M1 电平 | 模式脚错、模块未预配置 `AT+SWITCH=1`、模块未供电 |
| 网关一直不回 ACK | 接收链路 | 串口是否有字节、Magic 是否出现 | 波特率/接线 TX-RX 交叉、节点每帧校验失败、网关未启动 |
| ACK 超时后功耗变高 | 重试与睡眠 | 每次是否重发两次、模块是否真的睡了 | 检查 `SleepRadio()` 返回值（当前被 `(void)` 丢弃）、链路质量 |
| 网关日志丢数据 | 持久化 | 故障 CSV 是否写入成功 | 先 ACK 后落盘的设计决定；写失败只在 stderr 提示 |
| 距离不足/丢包 | RF 参数与现场 | 是否有 RSSI/丢包统计 | 当前**没有**实测数据；先做距离-丢包曲线，再谈 SF/功率/BW 改配 |

面试回答结构固定为：**现象 → 分层定位（MCU/外设/模块/空口/网关）→ 可观察证据 → 修复 → 用什么验证**。

**闭卷自测**：从"节点上报后 PC 端没收到数据"出发，给出你的排查顺序和每一步的判据。

**答案要点**：① 节点侧是否真的发出（TX 完成标志/串口抓字节）；② 模块是否被唤醒且有发送动作（M0/M1 电平、AUX 波形）；③ 空口条件（两端信道/速率/空速是否一致、距离与遮挡）；④ 网关侧是否收到字节（串口占用、波特率、TX/RX 是否交叉）；⑤ 收到字节但没输出 → 逐层看 Magic 是否出现、CRC 是否失败、是否被判重复；⑥ 最后才怀疑代码逻辑。每一步都要有"看什么、看到什么算正常"的判据，不能一路猜。
