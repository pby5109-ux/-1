FreeRTOS 可以分为两部分： Free 和  RTOS ， Free 就是免费的、⾃由的、  不受约束的， RTOS 是  Real Time

RTOS 不是指某⼀个确定的系统，⽽是指⼀类系统。比如  UCOS ， FreeRTOS ， RTX ， RT-Thread 等这些都是

FreeRTOS 特点
FreeRTOS 是⼀个可裁剪的⼩型  RTOS 系统，其特点包括：
● FreeRTOS 的内核⽀持抢占式，合作式和时间片调度。
● SafeRTOS 衍⽣⾃  FreeRTOS ， SafeRTOS 在代码完整性上相比  FreeRTOS 更胜⼀筹。
● 提供了⼀个⽤于低功耗的  Tickless 模式。
● 系统的组件在创建时可以选择动态或者静态的  RAM ，比如任务、消息队列、信号量、  软件定时器等等。

● ⾼可移植性，代码主要  C 语⾔编写。
● ⽀持实时任务和协程 (co-routines 也有称为合作式、协同程序，本教程均成为协程 ) 。

2. 命名规则
RTOS 内核和演⽰例程源代码使⽤以下规则：
> 变量
uint32_t ：前缀  ul ， u 表⽰  unsigned ， l 表⽰  long
uint16_t ：前缀  us ， s 表⽰  short
uint8_t ：前缀  uc ， c 表⽰  char
非  stdint 类型的变量使⽤前缀  x ，比如基本的  Type_t 和  TickType_t 类型
非  stdint 类型的⽆符号变量使⽤前缀  ux ，比如  UbaseType_t （ unsigned BaseType_t ）
size_t 类型的变量使⽤前缀  x
枚举类型变量使⽤前缀  e
指针类型变量在类型基础上附加前缀  p ，比如指向  uint16_t 的指针变量前缀为  pus
char 类型变量前缀为  c
char * 类型变量前缀为  pc
举例：

uint8_t * pucQueueStorage;

1 、 Cortex-M 中断
Cortex-M 内核（ STM32 ）的  MCU 提供了⼀个 == ⽤于中断管理的嵌套向量中断控制器 (NVIC)== 。Cotex-M3 的
NVIC 最多⽀持  240 个  IRQ( 中断请求 ) 、 1 个不可屏蔽中断 (NMI) 、 1 个  Systick( 滴答定时器 ) 定时器中断和多个
系统异常。
**Cortex-M 处理器有多个⽤于管理中断和异常的可编程寄存器，这些寄存器⼤多数都在  NVIC 和系统控制块
(SCB) 中， CMSIS 将这些寄存器定义为结构体。 ** 以  STM32F103 为例，打开  core_cm3.h ，有两个结构体，
NVIC_Type 和  SCB_Type ，就存储了这些信息。
优先级分组定义

FreeRTOS 开关中断函数为  portENABLE_INTERRUPTS ()和  portDISABLE_INTERRUPTS()，这两个函数其实是

可以看出开关中断实际上是通过函数  vPortSetBASEPRI(0)和  vPortRaiseBASEPRI()来实现的。

寄存器可知，结果就是开中断。

3 、任务状态
FreeRTOS 中的任务永远处于下⾯⼏个状态中的某⼀个：
● 运⾏态
当⼀个任务正在运⾏时，那么就说这个任务处于运⾏态，处于运⾏态的任务就是当前正在使⽤处理器的任务。
如果使⽤的是单核处理器的话那么不管在任何时刻永远都只有⼀个任务处于运⾏态。
● 就绪态
处于就绪态的任务是那些已经准备就绪 ( 这些任务没有被阻塞或者挂起 ) ，可以运⾏的任务，但是处于就绪态的
任务还没有运⾏，因为有⼀个同优先级或者更⾼优先级的任务正在运⾏！
● 阻塞态
如果⼀个任务当前正在等待某个外部事件的话就说它处于阻塞态，比如说如果某个任务调⽤了函数
vTaskDelay() 的话就会进入阻塞态，直到延时周期完成。 == 任务在等待队列、信号量、事件组、通知或互斥信
号量的时候也会进入阻塞态。 == 任务进入阻塞态会有⼀个超时时间，当超过这个超时时间任务就会退出阻塞
态，即使所等待的事件还没有来临！
● 挂起态
像阻塞态⼀样，任务进入挂起态以后也不能被调度器调⽤进入运⾏态，但是进入挂起态的任务没有超时时间。

7 、任务堆栈
FreeRTOS 之所以能正确的恢复⼀个任务的运⾏就是因为有任务堆栈在保驾护航，任务调度器在进⾏任务切换的
时候会将当前任务的现场 (CPU 寄存器值等 ) 保存在此任务的任务堆栈中，等到此任务下次运⾏的时候就会先⽤
堆栈中保存的值来恢复现场，恢复现场以后任务就会接着从上次中断的地⽅开始运⾏。
创建任务的时候需要给任务指定堆栈，如果使⽤的函数  xTaskCreate() 创建任务 ( 动态⽅法 ) 的话那么任务堆栈就
会由函数  xTaskCreate() ⾃动创建。如果使⽤函数  xTaskCreateStatic() 创建任务 ( 静态⽅法 ) 的话就需要程序员⾃⾏

FreeRTOS （九）：软件定时器
定时器可以说是每个  MCU 都有的外设，有的  MCU 其定时器功能异常强⼤，比如提供  PWM 、输入捕获等功
能。但是最常⽤的还是定时器最基础的功能 —— 定时，通过定时器来完成需要周期性处理的事务。
MCU ⾃带的定时器属于硬件定时器，不同的  MCU 其硬件定时器数量不同，因为要考虑成本的问题。
FreeRTOS 也提供了定时器功能，不过是软件定时器，软件定时器的精度肯定没有硬件定时器那么⾼，但是对
于普通的精度要求不⾼的周期性处理的任务来说够了。当  MCU 的硬件定时器不够的时候就可以考虑使⽤
FreeRTOS 的软件定时器。
软件定时器简介
软件定时器允许设置⼀段时间，当设置的时间到达之后就执⾏指定的功能函数，被定时器调⽤的这个功能函数
叫做定时器的回调函数。回调函数的两次执⾏间隔叫做定时器的定时周期，简⽽⾔之，当定时器的定时周期到
了以后就会执⾏回调函数。

FreeRTOS （⼗⼆）：消息队列
在实际的应⽤中，常常会遇到⼀个任务或者中断服务需要和另外⼀个任务进⾏ “ 沟通交流 ” ，  这个 “ 沟通交流 ” 的
过程其实就是消息传递的过程。在没有操作系统的时候两个应⽤程序进⾏消息传递⼀般使⽤全局变量的⽅式，
但是如果在使⽤操作系统的应⽤中⽤全局变量来传递消息就会涉及到 “ 资源管理 ” 的问题。FreeRTOS 对此提供了
⼀个叫做 “ 队列 ” 的机制来完成任务与任务、任务与中断之间的消息传递，由于队列⽤来传递消息的，所以也称
为消息队列。
1 、队列简介
队列是为了任务与任务、任务与中断之间的通信⽽准备的，可以在任务与任务、任务与中断之间传递消息，队
列中可以存储有限的、⼤⼩固定的数据项⽬。任务与任务、任务与中断之间要交流的数据保存在队列中，叫做
队列项⽬。队列所能保存的最⼤数据项⽬数量叫做队列的⻓度，创建队列的时候会指定数据项⽬的⼤⼩和队列
的⻓度。
通常队列采⽤先进先出 (FIFO) 的存储缓冲机制，也就是往队列发送数据的时候 ( 也叫入队 ) 永远都是发送到
队列的尾部，⽽从队列提取数据的时候 ( 也叫出队 ) 是从队列的头部提取的。但是也可以使⽤  LIFO 的存储

缓冲，也就是后进先出， FreeRTOS 中的队列也提供了  LIFO 的存储缓冲机制。
数据发送到队列中会导致数据拷⻉，也就是将要发送的数据拷⻉到队列中，这就意味着在队列中存储的是数据
的原始值，⽽不是原数据的引⽤ ( 即只传递数据的指针 ) ，这个也叫做值传递。 UCOS 的消息队列采⽤的是引⽤传
递，传递的是消息指针。采⽤引⽤传递的话消息内容就必须⼀直保持可⻅性，也就是消息内容必须有效，那么
局部变量这种可能会随时被删掉的东⻄就不能⽤来传递消息，但是采⽤引⽤传递会节省时间啊！因为不⽤进⾏
数据拷⻉。
采⽤值传递的话虽然会导致数据拷⻉，会浪费⼀点时间，但是⼀旦将消息发送到队列中原始的数据缓冲区就可

的是数据拷⻉，但是也可以使⽤引⽤来传递消息啊 == ，我直接往队列中发送指向这个消息的地址指针不就可以
了！这样当我要发送的消息数据太⼤的时候就可以直接发送消息缓冲区的地址指针，比如在⽹络应⽤环境中，
⽹络的数据量往往都很⼤的，采⽤数据拷⻉的话就不现实。
1 、多任务访问
队列不是属于某个特别指定的任务的，任何任务都可以向队列中发送消息，或者从队列中提取消息。
2 、出队阻塞
当任务尝试从⼀个队列中读取消息的时候可以指定⼀个阻塞时间，这个阻塞时间就是当任务从队列中读取消息
⽆效的时候任务阻塞的时间。出队就是就从队列中读取消息，出队阻塞是针对从队列中读取消息的任务⽽⾔
的。
比如任务  A ⽤于处理串⼝接收到的数据，串⼝接收到数据以后就会放到队列  Q 中，任务  A 从队列  Q 中读取数
据。但是如果此时队列  Q 是空的，说明还没有数据，任务  A 这时候来读取的话肯定是获取不到任何东⻄，那该
怎么办呢？
任务  A 现在有三种选择，⼀：⼆话不说扭头就⾛，⼆：要不我在等等吧，等⼀会看看，说不定⼀会就有
数据了，三：死等，死也要等到你有数据！选哪⼀个就是由这个阻塞时间决定的，这个阻塞时间单位是
时钟节拍数。阻塞时间为  0 的话就是不阻塞，没有数据的话就⻢上返回任务继续执⾏接下来的代码，对
应第⼀种选择。如果阻塞时间为  0~ portMAX_DELAY ，当任务没有从队列中获取到消息的话就进入阻塞
态，阻塞时间指定了任务进入阻塞态的时间，当阻塞时间到了以后还没有接收到数据的话就退出阻塞
态，返回任务接着运⾏下⾯的代码，如果在阻塞时间内接收到了数据就立即返回，执⾏任务中下⾯的代
码，这种情况对应第⼆种选择。当阻塞时间设置为 portMAX_DELAY 的话，任务就会⼀直进入阻塞态等
待，直到接收到数据为⽌！这个就是第三种选择。
3 、入队阻塞
入队说的是向队列中发送消息，将消息加入到队列中。和出队阻塞⼀样，当⼀个任务向队列发送消息的话也可
以设置阻塞时间。比如任务  B 向消息队列  Q 发送消息，但是此时队列  Q 是满的，那肯定是发送失败的。此时
任务  B 就会遇到和上⾯任务  A ⼀样的问题，这两种情况的处理过程是类似的，只不过⼀个是向队列  Q 发送消
息，⼀个是从队列  Q 读取消息⽽已。

FreeRTOS （⼗三）：信号量
信号量是操作系统中重要的⼀部分， == 信号量⼀般⽤来进⾏资源管理和任务同步 == ，FreeRTOS 中信号量⼜分

1 、信号量⽤于控制对共享资源的访问
举⼀个很常⻅的例⼦，某个停⻋场有 100 个停⻋位，这  100 个停⻋位⼤家都可以⽤，对于⼤家来说这  100 个停
⻋位就是共享资源。假设现在这个停⻋场正常运⾏，你要把⻋停到这个这个停⻋场肯定要先看⼀下现在停了多
少⻋了？还有没有停⻋位？
当前停⻋数量就是⼀个信号量，具体的停⻋数量就是这个信号量值，当这个值到  100 的时候说明停⻋场满了。
停⻋场满的时你可以等⼀会看看有没有其他的⻋开出停⻋场，当有⻋开出停⻋场的时候停⻋数量就会减⼀，也
就是说信号量减⼀，此时你就可以把⻋停进去了，你把⻋停进去以后停⻋数量就会加⼀，也就是信号量加⼀。
这就是⼀个典型的使⽤信号量进⾏共享资源管理的案例，在这个案例中使⽤的就是计数型信号量。
再看另外⼀个案例：使⽤公共电话，我们知道⼀次只能⼀个⼈使⽤电话，这个时候公共电话就只可能有两个状
态：使⽤或未使⽤，如果⽤电话的这两个状态作为信号量的话，那么这个就是⼆值信号量。
信号量⽤于控制共享资源访问的场景相当于⼀个上锁机制，代码只有获得了这个锁的钥匙才能够执⾏。
2 、信号量的⽤于任务同步
任务与任务或中断与任务之间的同步。
在执⾏中断服务函数的时候可以通过向任务发送信号量来通知任务它所期待的事件发⽣了，当退出中断服务函
数以后在任务调度器的调度下同步的任务就会执⾏。
在编写中断服务函数的时候我们都知道⼀定要快进快出，中断服务函数⾥⾯不能放太多的代码，否则的话会影
响的中断的实时性。裸机编写中断服务函数的时候⼀般都只是在中断服务函数中打个标记，然后在其他的地⽅
根据标记来做具体的处理过程。
在使⽤  RTOS 系统的时候我们就可以借助信号量完成此功能，当中断发⽣的时候就释放信号量，中断服务函数
不做具体的处理。具体的处理过程做成⼀个任务，这个任务会获取信号量，如果获取到信号量就说明中断发⽣
了，那么就开始完成相应的处理，这样做的好处就是中断执⾏时间非常短。

2 、 Tickless 模式详解
1 、如何降低功耗？
⼀般的简单应⽤中处理器⼤量的时间都在处理空闲任务， ** 所以我们就可以考虑当处理器处理空闲任务的时候
就进入低功耗模式，当需要处理应⽤层代码的时候就将处理器从低功耗模式唤醒。 FreeRTOS 就是通过在处理器
处理空闲任务的时候将处理器设置为低功耗模式来降低能耗。 ** ⼀般会在空闲任务的钩⼦函数中执⾏低功耗相
关处理，比如设置处理器进入低功耗模式、关闭其他外设时钟、降低系统主频等等。
我们知道  FreeRTOS 的系统时钟是由滴答定时器中断来提供的，系统时钟频率越⾼，那么滴答定时器中断频率
也就越⾼。以前讲过，中断是可以将  STM32F103 从睡眠模式中唤醒，周期性的滴答定时器中断就会导致
STM32F103 周期性的进入和退出睡眠模式。因此，如果滴答定时器中断频率太⾼的话会导致⼤量的能量和时间
消耗在进出睡眠模式中，这样导致的结果就是低功耗模式的作⽤被⼤⼤的削弱。
为此， FreeRTOS 特地提供了⼀个解决⽅法 ——Tickless 模式，当处理器进入空闲任务周期以后就关闭系统节拍
中断 ( 滴答定时器中断 ) ，只有当其他中断发⽣或者其他任务需要处理的时候处理器才会被从低功耗模式中唤
醒。为此我们将⾯临两个问题：
问题⼀：关闭系统节拍中断会导致系统节拍计数器停⽌，系统时钟就会停⽌。
FreeRTOS 的系统时钟是依赖于系统节拍中断 ( 滴答定时器中断 ) 的，如果关闭了系统节拍中断的话就会导致系统
时钟停⽌运⾏，这是绝对不允许的！该如何解决这个问题呢？我们可以记录下系统节拍中断的关闭时间，当系
统节拍中断再次开启运⾏的时候补上这段时间就⾏了。这时候我们就需要另外⼀个定时器来记录这段该补上的
时间，如果使⽤专⽤的低功耗处理器的话基本上都会有⼀个低功耗定时器，比如  STM32L4 系列 (L 系列是  ST 的
低功耗处理器 ) 就有⼀个叫做  LPTIM( 低功耗定时器 ) 的定时器。 STM32F103 没有这种定时器那么就接着使⽤滴答
定时器来完成这个功能，具体实现⽅法后⾯会讲解。
问题⼆：如何保证下⼀个要运⾏的任务能被准确的唤醒？
即使处理器进入了低功耗模式，但是我的中断和应⽤层任务也要保证及时的响应和处理。中断⾃然不⽤说，本
⾝就可以将处理器从低功耗模式中唤醒。但是应⽤层任务就不⾏了，它⽆法将处理器从低功耗模式唤醒，⽆法
唤醒就⽆法运⾏！这个问题看来很棘⼿，既然应⽤层任务⽆法将处理器从低功耗模式唤醒，那么我们就借助其
他的⼒量来完成这个功能。如果处理器在进入低功耗模式之前能够获取到还有多⻓时间运⾏下⼀个任务那么问
题就迎刃⽽解了，我们只需要开⼀个定时器，定时器的定时周期设置为这个时间值就⾏了，定时时间到了以后
产⽣定时中断，处理器不就从低功耗模式唤醒了。这⾥似乎⼜引出了⼀个新的问题，那就是如何知道还有多⻓
时间执⾏下⼀个任务？这个时间也就是低功耗模式的执⾏时间，值得庆辛的是  FreeRTOS 已经帮我们完成了这个
⼯作。

● 将处理器降低到合适的频率，因为频率越低功耗越⼩，甚⾄可以在进入低功耗模式以后关闭系统时钟。
● 修改时钟源，晶振的功耗肯定比处理器内部的时钟源⾼，进入低功耗模式以后可以切换到内部时钟源，比如

● 关闭板⼦上其他功能模块电源，这个需要在产品硬件设计的时候就要处理好，比如可以通过  MOS 管来控制
某个模块电源的开关，在处理器进入低功耗模式之前关闭这些模块的电源。
有关产品低功耗设计的⽅法还有很多，⼤家可以上⽹查找⼀下，上⾯列举出的这⼏点在处理器进入低功耗模式

FreeRTOS （⼗八）：内存管理
内存管理是⼀个系统基本组成部分， FreeRTOS 中⼤量使⽤到了内存管理，比如创建任务、信号量、队列等会⾃
动从堆中申请内存。⽤户应⽤层代码也可以  FreeRTOS 提供的内存管理函数来申请和释放内存，本文学习⼀下
FreeRTOS ⾃带的内存管理。
1 、 FreeRTOS 内存管理简介
FreeRTOS 创建任务、队列、信号量等的时候有两种⽅法，⼀种是动态的申请所需的  RAM。⼀种是由⽤户⾃⾏
定义所需的  RAM ，这种⽅法也叫静态⽅法，使⽤静态⽅法的函数⼀般以 “Static” 结尾，比如任务创建函数
xTaskCreateStatic() ，使⽤此函数创建任务的时候需要由⽤户定义任务堆栈，我们不讨论这种静态⽅法。
== 使⽤动态内存管理的时候  FreeRTOS 内核在创建任务、队列、信号量的时候会动态的申请  RAM 。 == 标准  C
库中的  malloc() 和  free() 也可以实现动态内存管理，但是如下原因限制了其使⽤：
● 在⼩型的嵌入式系统中效率不⾼。
● 会占⽤很多的代码空间。
● 它们不是线程安全的。
● 具有不确定性，每次执⾏的时间不同。
● 会导致内存碎片。
● 使链接器的配置变得复杂。
不同的嵌入式系统对于内存分配和时间要求不同，因此⼀个内存分配算法可以作为系统的可选选项。 FreeRTOS
将内存分配作为移植层的⼀部分，这样  FreeRTOS 使⽤者就可以使⽤⾃⼰的合适的内存分配⽅法。
当内核需要  RAM 的时候可以使⽤  pvPortMalloc() 来替代  malloc() 申请内存，不使⽤内存的时候可以使⽤
vPortFree() 函数来替代  free() 函数释放内存。函数  pvPortMalloc() 、 vPortFree() 与函数  malloc() 、 free() 的函
数原型类似。
FreeRTOS 提供了  5 种内存分配⽅法， FreeRTOS 使⽤者可以其中的某⼀个⽅法，或者⾃⼰的内存分配⽅法。这
5 种⽅法是  5 个文件，分别为 :heap_1.c 、 heap_2.c 、 heap_3.c 、 heap_4.c 和 heap_5.c 。这  5 个文件再  FreeRTOS 源
码中，路径： FreeRTOS->Source->portable->MemMang 。

似乎毫⽆任何使⽤价值啊。千万不能这么想，有很多⼩型的应⽤在系统⼀开始就创建好任务、信号量或队列
等，在程序运⾏的整个过程这些任务和内核对象都不会删除，那么这个时候使⽤  heap_1 就很合适的。
heap_2 内存分配⽅法
heap_2 提供了⼀个更好的分配算法，不像  heap_1 那样， heap_2 提供了内存释放函数。 heap_2 不会把释放的
内存块合并成⼀个⼤块，这样有⼀个缺点，随着你不断的申请内存，内存堆就会被分为很多个⼤⼩不⼀的内存
( 块 ) ，也就是会导致内存碎片！
heap_2 的特性如下：
1 、可以使⽤在那些可能会重复的删除任务、队列、信号量等的应⽤中，要注意有内存碎片产⽣！
2 、如果分配和释放的内存  n ⼤⼩是随机的，那么就要慎重使⽤了，比如下⾯的⽰例：
● 如果⼀个应⽤动态的创建和删除任务，⽽且任务需要分配的堆栈⼤⼩都是⼀样的，那么  heap_2 就非常合适。
如果任务所需的堆栈⼤⼩每次都是不同，那么  heap_2 就不适合了，因为这样会导致内存碎片产⽣，最终导致
任务分配不到合适的堆栈！
● 如果⼀个应⽤中所使⽤的队列存储区域每次都不同，那么  heap_2 就不适合了，和上⾯⼀样。
● 应⽤需要调⽤  pvPortMalloc() 和  vPortFree() 来申请和释放内存，⽽不是通过其他  FreeRTOS 的其他  API 函数来
间接的调⽤，这种情况下  heap_2 不适合。
3 、如果应⽤中的任务、队列、信号量和互斥信号量具有不可预料性 ( 如所需的内存⼤⼩不能确定，每次所需的内
存都不相同，或者说⼤多数情况下所需的内存都是不同的 ) 的话可能会导致内存碎片。

1 、需要编译器提供⼀个内存堆，编译器库要提供  malloc() 和  free() 函数。比如使⽤  STM32 的话可以通过修改启

3 、可能会增加代码量。

heap_5 内存分配⽅法
heap_5 使⽤了和  heap_4 相同的合并算法，内存管理实现起来基本相同，但是  heap_5 允许内存堆跨越多个不
连续的内存段。比如  STM32 的内部  RAM 可以作为内存堆，但是  STM32 内部  RAM 比较⼩，遇到那些需要⼤容

heap_4 的话你就只能在内部  RAM 和外部 SRAM 或  SDRAM 之间⼆选⼀了，使⽤  heap_5 的话就不存在这个问

typedef struct HeapRegion

    uint8_t *pucStartAddress; // 内存块的起始地址

总结
FreeRTOS 官⽅的  5 种内存分配⽅法：
1. heap_1 最简单，但是只能申请内存，不能释放。
2. heap_2 提供了内存释放函数，⽤户代码也可以直接调⽤函数  pvPortMalloc() 和 vPortFree() 来申请和释放
内存，但是  heap_2 会导致内存碎片的产⽣！
3. heap_3 是对标准  C 库中的函数  malloc() 和  free() 的简单封装，并且提供了线程保护。
4. heap_4 相对与  heap_2 提供了内存合并功能，可以降低内存碎片的产⽣。
5. heap_5 基本上和  heap_4 ⼀样，只是  heap_5 ⽀持内存堆使⽤不连续的内存块。
